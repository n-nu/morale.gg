# ADR-20260914-001: Use the Next.js server-side application layer as the MVP backend boundary

- Status: Accepted
- Date: 2026-09-14
- Related tickets: TKT-20260914-000002-001

## Context

The morale.gg MVP requires one shared foundation for PostgreSQL persistence, Prisma ORM access,
Google website authentication, and server-side identity resolution. The repository currently
documents Next.js, React, TypeScript, Node.js application behavior, Prisma, PostgreSQL, and
Google authentication as the intended technology direction, but it does not establish the
detailed application/API topology.

Future Units, Players, Events, Participation, and Audit work must share one authoritative
server-side persistence and authentication boundary. The prior application-foundation ticket
intentionally excluded database, authentication, APIs, and product-domain behavior. Choosing
where browser requests are mediated is therefore a system-wide RED architecture decision.

## Proposed Decision

Use the Next.js server-side application layer as the MVP backend boundary:

```text
Browser / Next.js Client
        -> Next.js server-side application layer
        -> Prisma
        -> PostgreSQL

Google authentication
        -> Next.js server-side application layer
```

The Next.js server-side layer is responsible for integrating Google authentication, resolving
authenticated website identity, enforcing future server-side authorization, applying business
rules, and accessing persistence through Prisma. The browser must not connect directly to
PostgreSQL. All Prisma and PostgreSQL access must occur from server-side application code.
Client-side or browser code must not directly import, access, or depend on persistence
implementation. Server-only authentication logic, persistence access, secrets, credentials, and
privileged business logic must not be exposed to browser or client bundles. Google authentication
must not automatically create or equate a `Player` record with a `UserAccount`.

This decision does not approve a final authorization model, database schema, public API shape,
module boundary, permission matrix, historical snapshot strategy, specific authentication
library, Route Handlers versus Server Actions, or future contract shapes. Those remain subject to
the repository's normal RED-decision process when implementation requires them.

## Alternatives

- **Separate Express, Nest, or standalone Node service:** rejected for the MVP proposal because it
  adds a deployable service and an additional boundary without an established repository need.
- **Browser-to-database access:** rejected because it exposes persistence directly to the client
  and cannot provide an authoritative server-side application boundary for authentication,
  authorization, and business rules.
- **Client-only authentication with persistence handled later:** rejected because shared feature
  work requires server-side identity and persistence foundations together, and it would create
  incompatible temporary patterns for future modules.

## Consequences

Positive:

- One application boundary can centralize identity resolution, future authorization, validation,
  business rules, and Prisma access.
- Future domain work can remain inside the existing Next.js application rather than introducing
  a second service prematurely.
- PostgreSQL remains behind Prisma and the server-side layer, preserving a clear persistence
  boundary.

Negative and operational:

- The Next.js application owns both web-client delivery and server-side application behavior,
  so its server/client boundaries must remain explicit.
- Deployment, runtime, connection pooling, and environment configuration must support Prisma and
  PostgreSQL from the Next.js server runtime.
- Future shared contracts or module boundaries may still require BCRs and additional ADRs.
- This decision establishes the MVP topology only. A separately deployed backend service may be
  introduced later through a new ADR if concrete scaling, deployment, integration, security, or
  organizational requirements justify the additional boundary.

## Affected Modules / Contracts

- Modules: no modules currently exist; proposed owner is architecture/repository foundation.
- Contracts: none currently exist; no speculative contract is created by this proposal.

# ADR-20260915-003: Bounded Website-Administrator Identity Mechanism

- Status: Accepted
- Date: 2026-09-15
- Related tickets: TKT-20260915-000008-001

- Human approval: Approved by the human architectural owner on 2026-09-16

## Context

ADR-20260915-002 accepts a bounded website/system-administrator capability:
RootUnit creation or designation, initial RootUnit owner/Commander assignment,
and RootUnit ownership transfer. It explicitly defers the implementation
mechanism for recognizing website administrators.

The application uses Auth.js with Google, a Prisma adapter, and database
sessions. Auth.js `User` is website identity, has a stable generated `id`, and
has a unique but nullable email. Authentication alone must not create
administrator authority. Website administrators are distinct from Players,
Unit Commanders, and Unit-scoped authorized users.

Bootstrap authority must remain available independently of any future
admin-management UI or database-managed administrator. A future path for
regular managed administrators is needed without generalized roles or RBAC.

## Decision

Use a server-only deployment allowlist of stable Auth.js `User.id` values as
the MVP bootstrap website-administrator mechanism.

- Configure the allowlist in one deployment variable, `WEBSITE_ADMIN_USER_IDS`,
  containing comma-separated Auth.js `User.id` values. It is not committed and
  is never returned to the client.
- A bootstrap administrator must authenticate normally first, allowing the
  Prisma adapter to create their Auth.js User. A trusted deployer then records
  that stable User ID in deployment configuration.
- Resolve authority only on the server from the authenticated Auth.js User
  identity. A centralized server-only capability such as `isWebsiteAdmin(user)`
  returns true when that User ID matches the configured allowlist, and false
  for missing authentication, missing ID, malformed configuration, or a
  non-match.
- Protected server-side code must be able to resolve the authenticated Auth.js
  User ID reliably. The implementation may use the database-session Auth.js
  callback or another server-side Auth.js-supported approach; it must not
  expose User ID to client session state solely for authorization. Client-visible
  session data, request data, route values, and client-provided IDs are never
  authority inputs.
- Defer regular SiteAdmin persistence. No managed-admin operation or UI exists
  in MVP, so a `SiteAdmin` model would introduce shared schema and lifecycle
  design before a real consumer exists. Bootstrap administrators alone satisfy
  the accepted RootUnit bootstrap need.
- A later approved managed-admin ticket must use the smallest User-keyed
  representation required then and create immutable add/remove audit records
  with actor User, target User, timestamp, and operation. It must never modify
  bootstrap deployment configuration.
- When a User eventually qualifies through both bootstrap configuration and a
  managed-admin record, `effectiveWebsiteAdmin = bootstrapAdmin OR
  managedSiteAdmin`. The effective result remains one boolean capability.
  Bootstrap eligibility remains effective and cannot be removed or demoted by
  an application-managed path.
- The capability is limited to the three RootUnit operations accepted by
  ADR-20260915-002. It grants no Unit-scoped permission and does not imply
  Commander, AuthorizedUserMembership, PermissionGrant, role, or RBAC status.

No cross-module contract is created. A later RootUnit operation may consume
this capability only through the shared authentication/server boundary and
must establish any actual consumer boundary under repository governance.

## Alternatives

- Email allowlist: rejected because email is nullable and not the stable
  primary identity. A trusted operator may use email to locate a User, but it
  is not the configured authority key.
- Provider account ID allowlist: rejected because the authority boundary is
  Auth.js `User`; provider-specific configuration would couple the mechanism
  to Google and require Account traversal without a current need.
- `SiteAdmin` table now: deferred because there is no managed-admin operation
  or UI. It would prematurely establish a schema relationship and audit policy.
- `User.role` or generalized RBAC: rejected because the accepted capability is
  deliberately bounded.

## Consequences

Bootstrap eligibility survives email changes and is governed by deployment
configuration controls. It requires a trusted operator to obtain a User ID
after first sign-in and configure it outside application source. Rotation or
removal of bootstrap administrators is a deployment operation, not an
application-panel operation.

The initial implementation stays small: centralized configuration parsing,
server-side identity resolution, one boolean capability, and focused tests.
It needs no Prisma migration or admin-management UI. Managed-admin persistence
and lifecycle auditing remain a future approved concern.

## Affected Modules / Contracts

- Modules: shared Auth.js/server authentication boundary; future Units
  RootUnit-bootstrap operations.
- Contracts: none created.

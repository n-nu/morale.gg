# ADR-20260921-004: Standalone User-Owned Event Authorization

- Status: Accepted
- Date: 2026-09-21
- Related tickets: TKT-20260921-000016-001
- Human approval: Approved by the human architectural owner on 2026-09-21

## Context

The Events module owns standalone Event identity, information, persistence,
and creation. Ticket TKT-20260921-000015-001 added EventParticipation and the
Unit participation-request workflow but deliberately deferred Event-management
authority. The current Event model has no owner or explicitly authorized User.

ADR-20260915-002 established the Units-owned authority system and included
`MANAGE_EVENTS` among its Unit permissions. Its Event-specific description
suggests that Unit scope could authorize Event administration and
participation review. That interpretation cannot select an Event authority
boundary without coupling Events to a Unit, and it conflicts with the approved
product direction that Events are standalone User-owned objects.

The MVP needs three distinct questions:

1. whether an authenticated User may create a new Event;
2. whether a User may manage one existing Event; and
3. whether a User may administer that Event's explicitly authorized managers.

These questions have different owners. Units owns evaluation of effective
Unit permissions. Events owns Event identity, ownership, explicit Event
authorization, and management decisions after creation.

## Decision

### 1. Standalone User-owned Events

Every Event has exactly one real Auth.js `User` owner. The authenticated User
who creates the Event becomes its owner through a required relationship
conceptually equivalent to:

```text
Event.ownerUserId -> User.id
```

The owner identity is resolved server-side from the authenticated session. A
client-provided owner ID is never authoritative. Event creation and owner
assignment must commit atomically.

Events are not owned, organized, or authority-anchored by Units in MVP. No
`organizingUnitId`, `authorityUnitId`, Unit-owner relationship, or equivalent
Event-to-Unit authority relationship is introduced. The Unit authority that
permits creation is not persisted on the Event. Event ownership transfer is
not supported in MVP.

### 2. MVP meaning of `MANAGE_EVENTS`

This decision amends and supersedes only the Event-specific interpretation of
`MANAGE_EVENTS` in ADR-20260915-002. All unrelated Unit authority, hierarchy,
scope, RootUnit, Commander, delegation, revocation, and permission decisions
in ADR-20260915-002 remain unchanged.

For MVP, a currently effective `MANAGE_EVENTS` permission means that the User
is eligible to create a standalone Event. Eligibility exists when at least one
effective grant exists anywhere in the Units authority system. Its qualifying
Unit, scope, membership, grant, and lineage are not returned to Events or
stored on the Event.

`MANAGE_EVENTS` does not grant:

- automatic management of an existing Event;
- ownership of an Event by a Unit;
- authority over another User's Event;
- ancestor, Commander, RootUnit, or Unit-hierarchy oversight of Events; or
- authority derived from a participating Unit.

### 3. Explicit Event authorization

Events owns an explicit Event-to-User authorization relationship,
conceptually `EventAuthorizedUser`. It records the Event, authorized User,
User who added the authorization, and timestamps. Each Event/User pair is
unique.

The Event owner is authorized through ownership and does not need or receive a
duplicate explicit authorization row. Only the owner may add another Event
manager or revoke another Event manager. An explicitly authorized manager may
not administer other managers. A later GREEN implementation may allow an
invited manager to remove only their own authorization if that can be
supported without broadening manager-administration authority.

For MVP, the principals allowed to perform ordinary management of an existing
Event are exactly:

1. the Event owner; or
2. a User explicitly authorized for that Event.

Participation never confers Event-management authority. Units from different
RootUnits may participate in the same Event, and Event management remains
independent of every participating Unit's hierarchy.

### 4. Capability boundaries

Units provides a server-only semantic creation-eligibility capability
conceptually equivalent to:

```ts
canCreateEvent(userId: string): Promise<boolean>
```

It evaluates whether the User has any currently effective `MANAGE_EVENTS`
permission. It returns only a boolean, requires no Unit ID from Events, and
preserves the Units resolver's fail-closed behavior. The associated BCR and
contract define the cross-module boundary.

Events provides a server-only management capability conceptually equivalent
to:

```ts
canManageEvent(userId: string, eventId: string): Promise<boolean>
```

It returns true only for the Event owner or a User explicitly authorized for
that Event. It does not query Unit authority.

Events also provides an owner-only semantic check for Event-manager
administration. Its exact name is an implementation choice consistent with
Events conventions. It allows only the owner to add or revoke other Event
managers. `canManageEvent` must not be implemented as a Units capability.

All checks and protected mutations are enforced server-side. Frontend
visibility is not an authorization boundary.

### 5. Existing Event migration

Existing Event rows are development/test data. Before making
`Event.ownerUserId` required, the migration must assign every existing Event
to the one designated real existing authenticated development User selected
by the human owner.

The migration sequence must verify that the designated User exists, backfill
all existing Events, verify that every Event has a real owner, and only then
enforce the foreign key and final non-null invariant. The implementation must
use the safest migration mechanism consistent with current seed/database
conventions.

The migration must not create a sentinel or fake User, infer ownership from a
Unit, leave the final owner nullable, or embed a secret, email address, or
unstable identifier in reusable application logic. The designated development
User is deployment/migration input chosen by the human owner, not a new
application authority mechanism.

### 6. Deferred behavior

The following remain post-MVP and require a later approved decision:

- ancestor or inherited `MANAGE_EVENTS` oversight of existing Events;
- Unit hierarchy or RootUnit inheritance for Event management;
- Commander-based Event management;
- Event ownership transfer; and
- Event-to-Unit ownership or authority anchoring.

Event editing, EventParticipation approval/denial, Audit approval/denial, and
other ordinary Event-management workflows are later consumers of this
authorization foundation and are not implemented by this decision.

## Alternatives

- Unit-owned or Unit-anchored Events: rejected because Events are standalone
  and cross-organization participation must not select an authority hierarchy.
- Use `MANAGE_EVENTS` directly for all existing Event management: rejected
  because it grants unrelated Unit authority over another User's Event and
  makes Event authority depend on hierarchy after creation.
- Store the qualifying Unit or grant on Event: rejected because the source of
  creation eligibility grants no post-creation authority and is not Event
  ownership data.
- Treat every Event manager as a Unit authorized user: rejected because Event
  authorization is Event-specific and owned by Events.
- Add the owner to `EventAuthorizedUser`: rejected because ownership already
  grants authority and duplicate representations could diverge.
- Create a sentinel owner for existing rows: rejected because every owner must
  be a real authenticated User.

## Consequences

Event creation gains a narrow dependency on a Units-owned semantic boolean,
while management of existing Events remains wholly Events-owned. Unit
authority persistence stays private, and revoking the grant that originally
allowed creation does not change ownership or management of an already-created
Event.

Persistence requires a required Event-to-User owner relationship, an explicit
Event-to-User authorization relationship, uniqueness enforcement, suitable
referential behavior, and a staged development-data backfill. The owner-only
administration rule requires operation-level server enforcement in addition
to database constraints.

Future Event-management workflows can consume one stable Event capability
without learning Unit hierarchy or authorization internals. Post-MVP inherited
oversight or ownership transfer would be a new RED architecture change.

## Affected Modules / Contracts

- Modules: Events (owner and consumer), Units (creation-eligibility provider),
  shared Auth.js/server authentication (authenticated User resolution).
- Contract: `events-units-event-creation-authorization`.
- Boundary request: BCR-20260921-002.
- Supersedes: only the Event-specific `MANAGE_EVENTS` administration meaning
  in ADR-20260915-002; all other ADR-20260915-002 decisions remain active.

# ADR-20260928-008: Event Battlefield Sides, Results, and Public Battle Reads

- Status: Accepted
- Date: 2026-09-28
- Related ticket: TKT-20260928-000033-001
- Human approval: Approved by the product/architectural owner on 2026-09-28

## Context

The current Audit architecture provides approved EventParticipation-backed
atomic Event units, immutable finalized Audits, Event command groups, and
Statistics source reads. It does not define battlefield sides, Event result
history, Event-manager creation of atomic units, or an Event-scoped Battle
Statistics read. The public Event Battle surface must not infer any of those
facts from ordering, colors, Unit names, or derived metrics.

## Decision

### Battlefield sides and presentation

The only assigned battlefield sides are the fixed enum values `ATTACKER` and
`DEFENDER`. They are domain roles, not configurable names, coalitions, or
colors. A nullable side represents `UNSORTED` configuration state (and remains
compatible with legacy unconfigured rows). New atomic units and groups are
created with no side; placement in the organizer assigns a side. Unassigned
nodes are manager-visible only, cannot be attached beneath an assigned-side
parent, and never appear in public battlefield structure reads.

Every assigned group and descendant must have the same side. Organizer moves
are authoritative server mutations: placing a group on a side root, another
group, or Unsorted updates the whole descendant group/atomic-unit subtree in
one serializable transaction. Atomic placement derives its side from the
target. Invalid Event, cycle, and hierarchy targets are rejected server-side.

An Event may store optional validated image references for the Defender and
Attacker flags using the existing site-path/HTTPS image-reference behavior.
No upload, object-storage, or binary-media subsystem is introduced. Missing
images use presentation fallbacks: Defender blue and Attacker red. Colors are
never used as domain identity. Outcome accents are layered on top of readable
side identity styling.

### Participation, atomic units, and authority

EventParticipation remains an acceptance record: an approved persistent Unit
is accepted into an Event. It is not assigned to a side and is not itself a
battlefield placement.

Each AtomicEventUnit references exactly one approved EventParticipation. It
stores its own identity, human-readable battlefield name, nullable side
assigned by organizer placement, mandatory/optional state, and Audit Unit type
(`Regular`, `Rifles`, `Cavalry`, or `Artillery`) as the atomic result metadata.
The EventParticipation foreign
key is the sole authoritative represented/claiming Unit relationship.

Event owners and EventAuthorizedUsers authorized by `canManageEvent` may
create, configure, place, move, and remove eligible atomic units. Audits
retains ownership of atomic-unit invariants and persistence through a narrow
Events-to-Audits mutation seam. This Event-management authority does not imply
`canSubmitAudit`.

Atomic Commander remains the finalized Audit `COMMANDER` role. No duplicate
Commander field is added to AtomicEventUnit. A pre-battle visual Commander is
out of scope unless separately approved as a distinct domain fact; the manager
tree must not present it as the finalized Audit Commander.

EventCommandGroup remains Audits-owned. It stores a nullable organizer-assigned
EventParticipation foreign key as its sole represented/claiming Unit link, a
name, a designated Player commander, and an optional parent. The old
descriptive represented Unit identity is replaced by or migrated to the
authoritative participation relationship; duplicate persistent Unit identity
fields are not retained.

Both groups and atomic units may reference only an APPROVED participation in
the same Event. Requested, denied, foreign-Event, and arbitrary Unit records
are rejected server-side.

### Hierarchy and discovery

The existing strict tree invariants remain: same Event, no cycles, one
immediate parent, unique atomic contribution, unique flattened descendants,
and General qualification from at least two unique descendant atomic units.
Drag/drop and accessible `Move to...` use the same server mutation. Creation
does not require managers to decide a side or parent before the node exists.

Audits provides the `/audits` discovery read. It resolves the selected atomic
unit through its approved EventParticipation and exposes it to Unit users
authorized by the existing Unit-owned `canSubmitAudit(userId, unitId)`
decision. The user does not select or recreate the participating Unit. This
read does not expose unrelated atomic units and does not grant Event-manager
authority.

### Event result and history

The authoritative Event result is one of `ATTACKER_WIN`, `DEFENDER_WIN`, or
`DRAW`. It is not derived from Statistics. An Event manager may set the initial
result only after the Event is eligible to be concluded under existing Event
time semantics: its scheduled time has passed. The initial result becomes the
effective public result.

An effective result is never overwritten or deleted. A later manager change is
a history-preserving correction proposal with proposed value, proposer,
creation time, status, and approval/rejection metadata. Only one result is
effective at a time; approval supersedes the prior effective result while
retaining it as history. Rejection leaves the effective result unchanged.

Once an effective result exists, any currently authorized Event manager may
propose a correction whose value differs from the current effective result.
The proposal remains pending and does not change the public result. Another
currently authorized Event manager must approve or reject it; the proposer may
not approve or reject their own proposal. The Event owner may approve or reject
when they are not the proposer. There is no owner self-approval bypass. If an
Event has only one authorized manager, that manager may propose but the
correction remains pending until another authorized manager is available.

Approval supersedes the prior effective result while retaining every historical
effective result and proposal. Rejection leaves the current effective result
unchanged. Transactions must prevent concurrent correction races and preserve
exactly one effective result.

### Public Battle Statistics and identity

Statistics exposes a public Event-scoped reader such as
`getEventBattleStatistics(eventId)`. Events presentation consumes that reader
and never aggregates Audit data. The reader uses approved source facts and
returns atomic summaries, finalized/pending state, effective Audit Commander,
K/D/A, approved zero-death KDR, Tickets, Flag Captures, Flag Losses, Stars,
and expanded Player result rows with Audit position/role. Player display uses
a safely resolved Unit-local alias for the represented participation when
available, otherwise stable public PlayerID. No canonical global name is
invented.

Groups remain organizational by default. Optional raw group aggregates may be
provided only when Statistics can use unique flattened atomic descendants;
recursive ratio averages, nested double counting, and incompatible type
merging are forbidden. Historical Rank-at-Event is out of scope and is absent
from Player rows.

### Legacy events and public layout

Existing Events and relationships remain valid. No side is inferred from Units,
participation order, names, or color. A historical Event without explicit side
assignments renders `Battle sides not configured` and does not fabricate a
two-column battle. Existing EventParticipation, atomic-unit, group, and Audit
records remain valid during migration.

The Event page has one public `Battle Structure` section with side-separated,
responsive trees and atomic-unit `Battle details` disclosures. Unsorted nodes,
management actions, raw database IDs, and draft Audit Player rows are excluded.
Ticket 34 establishes pending Unit Statistics and Participating Players
placeholders; Ticket 35 supplies future finalized data. Without an Event result,
sides use normal identity styling. With a result, winner/loser use the current
site's readable success/danger accents; draw uses neutral treatment.

The Event manager surface embeds the Battle Structure organizer. Compact,
collapsed creation controls feed an Unsorted bin; tree rows expose drag handles,
visible drop targets, and a compact Move-to/edit/remove action menu. Side and
parent are determined by placement rather than creation forms. Event Result
status and permitted initial/correction actions remain separate Event
administration functions. Raw database IDs are not shown.

## Alternatives

- Configurable Side A/Side B or coalitions: rejected because the product
  domain has exactly two semantic roles.
- Assign side to EventParticipation: rejected because acceptance is distinct
  from battlefield placement and one participation may produce multiple
  atomic units.
- Keep a descriptive represented Unit alongside participation: rejected
  because duplicate identities can diverge; participation is authoritative.
- Store atomic Commander on the atomic unit: rejected because finalized Audit
  Commander is already authoritative and a pre-battle role is not approved.
- Derive result from K/D/A or Tickets: rejected because result is a manager
  fact, not a Statistics algorithm.
- Mutable `Event.result`: rejected because it destroys correction history.
- Add historical Rank-at-Event: rejected because current persistence cannot
  answer it truthfully.

## Consequences

The existing nullable side columns support Unsorted without a new enum,
column, or migration. Prior schema/migrations already provide fixed side
values, optional Event image references, participation-backed group claims,
and history-preserving result records. Cross-record side, Event,
participation, and result approval rules require transactional/server
validation where relational constraints are insufficient. Existing
unconfigured records remain valid and are excluded from public side trees
until a manager places them.

The Event manager gains only battlefield-structure authority through
`canManageEvent`; Audit submission and finalization remain Unit-authorized
through `canSubmitAudit`. Statistics gains one public read seam and owns all
derived metric semantics. No production implementation is authorized by this
ADR alone.

# ADR-20260927-006: Audit Domain and Event-Scoped Battlefield Structures

- Status: Accepted
- Date: 2026-09-27
- Related ticket: TKT-20260927-000020-001
- Human approval: Approved by the human architectural owner on 2026-09-27

## Context

The repository has standalone User-owned Events, immutable EventParticipation
requests/decisions, persistent Units and Player identities, and a reserved
`SUBMIT_AUDITS` permission. It has no Audit persistence. Existing module truth
explicitly excludes Audit lifecycle from Events and excludes Events/Audits from
Units and Players. Older conceptual documentation describes an Audit directly
per Unit/Event participation, but approved product requirements now require a
persistent Unit to produce multiple atomic battlefield units, each with at
most one Audit, and temporary Event command groups.

## Decision

Create the new `audits` module, owning:

- atomic Event-unit identity and its link to exactly one approved
  EventParticipation;
- Audit drafts, finalization, immutable results, player result rows, roles, and
  Unit type/statistics;
- mandatory atomic-unit metadata needed for later Unit/Event attendance; and
- Event-scoped command groups and their strict tree.

Events remains the owner of Event and EventParticipation and provides the
approved-participation and Event-management boundary through
`events-audits-event-participation-management`. Units remains the owner of
persistent Unit authority and provides `canSubmitAudit` through
`units-audits-submission-authorization`. Players remains the owner of Player
identity and provides resolve-or-create by stable game PlayerID through
`players-audits-player-resolution`. No module may use another module's private
persistence.

An atomic Event unit is created manually after the Event, is not created by
participation approval, belongs to exactly one approved participation, and may
have zero or one Audit. A finalized Audit is immutable. Its type is one of
Regular, Rifles, Cavalry, or Artillery. Audit player rows reference Player,
not UnitMembership, so mercenaries are valid and roster membership is never
changed by an Audit.

Audit command groups are historical Event structures, not persistent Unit
hierarchy objects. A group records Event, descriptive represented Unit,
Commander Player, optional parent, and child atomic units/groups. The tree
must reject cycles, duplicate parents, cross-Event edges, and overlapping
membership that double-counts an atomic unit. Nested future statistics flatten
to underlying Audits and partition combat values by Unit type.

MVP Audit state is a creator-owned draft followed by automatic finalization on
submit. The implementation may name the terminal state `FINAL` or `APPROVED`
as a GREEN choice; final state is immutable. Finalized result data and Event
command structure are public. Drafts and draft-management data are private,
and the submitting Auth.js User is not automatically public.

`Player.name` is nullable compatibility data. Existing values are preserved,
but an Audit-created Player may have no name or alias. UnitMembership-local
aliases remain the only source for future preferred display-name derivation.

## Future Statistics Compatibility

The source model must preserve these links without implementing statistics:

- PlayerResult -> Player and PlayerResult -> Audit;
- Commander role -> Player + Audit;
- Audit -> atomic Event unit -> EventParticipation -> Event + persistent Unit;
- Audit/atomic result -> Unit type;
- Event command group -> Commander Player and unique descendant atomic units.

Every Audit Player result is a future Ranker observation, including mercenary
and never-rostered Players. Ranker combat results remain partitionable by
Regular, Rifles, Cavalry, and Artillery while cross-type metadata may still be
derived. A Commander observation comes from the Player assigned the Commander
role in an atomic Audit, inherits that Unit type, and is independent of
persistent Unit Commander status. A General qualifies from at least two
underlying atomic units regardless of type; nested groups flatten to unique
Audits and partition combat values by Unit type rather than averaging child
group averages.

## History, Deletion, and Enforcement

Finalized Audits, Player results, and roles cannot be edited or deleted.
Finalized history protects referenced Event, EventParticipation, Unit, and
Player records from unsafe deletion. A creator may discard an unfinished draft.
An atomic unit with no finalized Audit and no command-group dependency may be
deleted under Audit authority. Event managers may edit, restructure, or delete
command groups, but those changes never mutate atomic units or finalized
Audits. Event deletion rejects any atomic-unit, group, or Audit history.

Database constraints enforce foreign keys, uniqueness, one Audit per atomic
unit, one Player result per Player/Audit, and direct-parent uniqueness.
Transactional/domain validation enforces complete finalization, role
cardinality, Regular Commander plus Flag Bearer rules, cycles, overlapping
atomic ancestry, and cross-Event tree edges. Triggers or stronger database
enforcement remain GREEN implementation options.

## Consequences

The new module and contracts are approved and current module manifests,
registries, and architecture documentation are synchronized under Ticket 20.
The older one-Audit-per-participation description is superseded by the
atomic-unit cardinality. Full statistics, attendance calculation, and
correction/rejection workflows remain deferred.

## Alternatives Rejected for This Proposal

- Put Audit lifecycle into Events: conflicts with the current Events
  non-ownership declaration and would make Events own a broader historical
  statistics domain without an approved boundary.
- Put atomic units/groups into Units: would conflate temporary Event history
  with persistent Unit hierarchy and authority.
- Put Audit player rows on UnitMembership: invalid for mercenaries and would
  mutate roster semantics from battlefield data.
- Make EventParticipation itself atomic: changes its established one
  persistent-Unit/Event meaning and prevents multiple battlefield units.
- Generate atomic units or groups from the persistent Unit hierarchy: actual
  post-Event organization is manually recorded and may differ from it.

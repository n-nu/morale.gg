# ADR-20260926-005: RootUnit Organization Catalogs and Management Authority

- Status: Accepted
- Date: 2026-09-26
- Last amended: 2026-09-27
- Related tickets: TKT-20260926-000019-001
- Human approval: Approved by the human architectural owner on 2026-09-26

## Context

ADR-20260915-002 establishes that a RootUnit is the boundary for future Ranks,
Medals, and organization-wide configuration, but explicitly leaves those models
outside its MVP scope. The current `RootUnit` record is keyed by its designated
Unit and has no separate owner column. The RootUnit owner is that Unit's
Commander. Commander status alone grants no operational Unit permissions.

The current Units authority boundary exposes target-Unit permission booleans,
but no RootUnit-only settings capability. `isWebsiteAdmin` is a separate,
bounded bootstrap capability for RootUnit creation/designation, initial owner
assignment, and ownership transfer; it is not an organization-settings role.

The current schema also has no Rank or Medal catalog or Unit profile fields
beyond name. `AuthorizedUserMembership` has no active/inactive state, is
permanently unique by `(userId, unitId)`, and is referenced restrictively by
PermissionGrant. Grants retain revocation and delegation lineage. This ADR
approves the necessary RootUnit catalogs, Unit profile metadata, and a
history-preserving authorized-membership lifecycle without changing the
operational permission model.

## Decision

### Unit Management Ownership and Structural Authorization

Units owns Unit profile management, authorized-user and grant administration,
Unit structural create/move/delete workflows, and the associated management UI.
No cross-module ownership is introduced. Protected mutations remain server-
enforced; the UI does not reproduce authority decisions.

Structural authorization is operation-specific and remains Units-owned. No
generic client-consumable `canManageStructure` boolean is the sole
authorization mechanism. Operations must preserve the existing
`MANAGE_STRUCTURE` strict-descendant anchor, same-RootUnit constraints, cycle
prevention, complete source/destination validation for moves, atomic child
creation, separate Commander and `MANAGE_AUTHORIZED_USERS` requirements for
initial Commander assignment, leaf-only hard deletion, and protected-history
checks. Creation does not add operational grants implicitly. Ordinary Unit
management still requires its applicable existing operational permission;
Commander/Unit-owner status is not a general bypass.

### Limited Hard Deletion for Unused Leaf Units

Human approval on 2026-09-27 authorizes limited Unit hard deletion for MVP;
archival, tombstones, and inactive Unit state remain out of scope. A Unit may be
deleted only when it is not a designated RootUnit, is a leaf, and has no Player
`UnitMembership`, `EventParticipation`, or other protected cross-domain
history. All authorized-user membership periods must be considered: the only
permitted row is exactly one active level-0 membership for the current
Commander. That mandatory bootstrap row may be deleted atomically with the
Unit, but it must not be removable through ordinary membership administration.
Any additional or ended membership, any PermissionGrant (including revoked or
delegated lineage), or any other protected reference rejects deletion. No
history may be cascaded or deleted to make a Unit eligible.

The Units workflow resolves the authenticated User server-side and enforces
the existing operation-specific `MANAGE_STRUCTURE` territory without a
Commander bypass. It verifies all structural and history conditions in one
transaction before removing the bootstrap membership and Unit. The deferred
Commander-consistency trigger skips validation only when its Unit no longer
exists at transaction completion; every surviving Unit retains the required
Commander and active level-0 membership invariant.

### RootUnit Settings Authority

Units owns a narrow server-side semantic capability/workflow conceptually
`canManageRootSettings(userId, rootUnitId)`. It allows only the current owner
of that RootUnit, where owner remains the Commander of its designated RootUnit
Unit under ADR-20260915-002. No second persisted owner field is added. This
capability authorizes the RootUnit Rank and Medal catalogs only; it grants no
ordinary Unit permissions and is not inferred from child Unit-management
grants. `isWebsiteAdmin` is not used for ordinary RootUnit settings. Owner
comparison is centralized in the Units capability/workflow, not scattered
through feature code. No cross-module contract is required for the Units-owned
consumer.

### Unit Profile Metadata

Units owns Unit `description`, flag/image/icon reference, Discord invite, and
external group link metadata alongside existing Unit `name`. These fields use
existing `MANAGE_UNIT` authorization semantics. Image/flag/icon configuration
is reference/value-based (for example, a URL, path, or identifier) and does
not introduce binary upload, object storage, third-party file hosting, or a
shared asset service. A real upload/storage system requires a future RED
decision.

### RootUnit Catalogs

- Rank definitions belong to exactly one RootUnit. Rank CRUD and meaningful
  ordering are in MVP. Ordinary fields and ordering representation are GREEN
  implementation choices. The persistence shape should not unnecessarily
  prevent possible future RootUnit-to-descendant use, but that future intent
  does not require inheritance behavior or schema machinery now.
- Medal definitions belong to exactly one RootUnit. Medal CRUD and ordinary
  presentation metadata are in MVP; exact fields remain GREEN choices.
- Catalog persistence must not silently disappear with a RootUnit deletion.
  Safe deletion/archive behavior is chosen within this invariant.
- No Rank inheritance/cascade, descendant overrides, Player Rank assignment
  or history, promotions, Rank-based permissions/authority, Player Medal
  assignment, award history/by tracking, Player Medal revocation/profile
  display, or Medal statistics are implemented by this decision.

### AuthorizedUserMembership Lifecycle and Grant History

`AuthorizedUserMembership` is a history-preserving membership period:

- An active membership has `endedAt = NULL`; an ended membership has a
  non-null `endedAt`.
- Ending access ends the current membership; it does not hard-delete or reuse
  that row. A later re-add creates a new membership row. Historical rows and
  their PermissionGrant rows remain queryable.
- At most one active membership may exist for a `(userId, unitId)` pair.
  Replace permanent pair uniqueness with a PostgreSQL partial unique index on
  `(userId, unitId)` for rows where `endedAt IS NULL`, using a forward migration.
- The current Commander/level-0 membership cannot be ended through ordinary
  authorized-user removal. Commander replacement/ownership transfer remains a
  separate operation subject to existing ADR-20260915-002/003 rules.
- Ending a membership and revoking its active grants occur transactionally.
  Grant rows and `delegatedFromGrantId` lineage are retained; do not delete
  PermissionGrant rows. Existing source-grant revocation semantics make
  dependent delegated grants ineffective while leaving unrelated grants and
  memberships untouched. An ended membership is not an effective grant
  membership, even if malformed or legacy data contains a non-revoked grant.
- Do not create a second delegation invalidation mechanism. The existing
  resolver remains fail-closed and must account for membership end state.

This lifecycle refines ADR-20260915-002's conceptual membership uniqueness and
its rule that membership removal removes or invalidates grants. For the current
schema, the permanent unique constraint is superseded by the single-active-row
invariant above. It does not change authority-level, permission, scope,
delegation narrowing, or Commander semantics.

This ADR approves the architectural/persistence boundaries only. Ticket
TKT-20260926-000019-001 owns the forward-only implementation and verification;
no feature implementation is performed by this decision record.

## Alternatives

- Store Rank/Medal definitions on each Unit: rejected because product
  ownership is RootUnit-wide and child overrides/inheritance are deferred.
- Put catalog ownership in Players: rejected because no Player assignment or
  relationship is in scope and Units owns RootUnit identity/isolation.
- Treat every Commander or website administrator as a general settings admin:
  rejected because Commander does not imply operational grants and website-admin
  authority is separately bounded by ADR-20260915-003.
- Reconstruct owner comparisons in each page/action: rejected because it
  duplicates a security-sensitive semantic decision.
- Reuse an ended membership on re-addition: rejected because each membership
  period must remain historically distinct.
- Delete membership/grant rows when access ends: rejected because membership
  history and delegated grant lineage must remain queryable.

## Consequences

Units owns the approved management surface and the RootUnit-only catalog
capability. Persistence work requires Unit metadata fields, RootUnit-scoped
Rank/Medal records, `AuthorizedUserMembership.endedAt`, and a partial unique
active-membership index. Limited hard deletion uses a forward migration and
removes only the mandatory bootstrap membership together with an otherwise-
unused leaf Unit. Migrations must build forward without resetting or deleting
existing protected Unit, membership, grant, or delegation history. The catalog
and membership schemas' ordinary field/index details remain GREEN within these
constraints.

## Affected Modules / Contracts

- Modules: units; shared Prisma persistence.
- Contracts: none proposed. No external consumer is identified; create a
  consumer-backed contract only if a real cross-module consumer is approved.

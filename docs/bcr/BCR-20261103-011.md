# Boundary Change Request: Cached Roblox Player Identity Presentation

- Request ID: BCR-20261103-011
- Requesting ticket: TKT-20261103-000051-001
- Requesting module: players
- Affected modules: players; units; audits; events; statistics; public application presentation
- Status: Approved
- Human approval: Approved by the requester through the explicit boundary-approval response on 2026-11-03

## Problem

Players currently has a manually supplied nullable global `Player.name` used
by the directory, profile, and roster as the preferred visible name. Roblox
username and avatar metadata are not cached. Player-facing surfaces therefore
do not provide reliable visual identification from the canonical game
identity, and existing public read contracts do not provide reusable cached
identity presentation for multiple Players.

Website `User`/Auth.js identity is a separate identity domain and must not be
used to represent game Players.

## Existing Contract

- `Player.playerId` is the unique, stable game Player identity; internal
  `Player.id` remains the relational key.
- `players-units-roster-read` exposes the stable `playerId` plus an optional
  global `displayName` sourced from `Player.name`.
- `players-audits-player-resolution` may resolve/create a Player from a
  stable game ID and returns the internal key only to Audits. Under this
  change, previously unknown IDs must be Roblox-verified before creation;
  existing IDs remain usable from persistence when Roblox is unavailable.
- `players-statistics-membership-history` uses `playerId` and preserves
  membership history semantics.
- `statistics-events-event-battle-reader` returns presentation names for
  Player rows and commanders.
- No UnitMembership-local alias field exists in the current schema.
- Auth.js `User.name`/`User.image` remain account fields and must not be
  substituted for Player presentation.

## Missing Capability

1. Nullable, Players-owned cached Roblox username, avatar/headshot URL, and
   last-synchronization time.
2. A server-only, batch-capable Players-owned read for cached Player
   presentation metadata, keyed solely by stable `playerId`.
3. A server-owned Roblox resolution/enrichment path that validates identity
   before new Player creation, supports batches for maintenance, and keeps
   external lookups out of ordinary reads.
4. Consistent Player presentation across the public profile, directory,
   roster, Events, Audits, Statistics/Leaderboard, and relevant management
   selectors.
5. Roblox verification and visible identity confirmation before Audit
   finalization creates a previously unknown Player, while preserving drafts
   and existing Players when Roblox is unavailable.

## Proposed Change

- Keep `Player.playerId` as the sole canonical game identity, all existing
  Player foreign keys and membership history unchanged, and all public profile
  links derived from `playerId`.
- Add nullable `robloxUsername`, `robloxAvatarUrl`, and `robloxSyncedAt`
  fields to `Player` in a forward-only migration. Preserve legacy `Player.name`
  internally during compatibility/migration; remove it from global Player
  presentation and search. Do not add membership aliases or Roblox display
  names.
- Add `players-player-identity-presentation`, a server-only batch read
  returning stable Player IDs and optional cached username/headshot metadata
  without exposing `Player.id`. Update the roster-read and Event Battle DTOs
  only as necessary to carry presentation metadata.
- Use Roblox's official Users `POST /v1/users` endpoint for batched canonical
  account lookup and official Thumbnails `GET /v1/users/avatar-headshot` for
  headshot URLs. Validate IDs, response shape, username length, and approved
  `rbxcdn.com` image hosts; ignore `displayName`. Treat external responses as
  untrusted.
- Require a server resolution/preview and manager confirmation before the
  registration and roster-add workflows create a new Player from a supplied
  ID. Reuse an existing Player by `playerId`; do not replace IDs or histories.
- Extend the Players-to-Audits resolution boundary so Audit finalization
  batches and verifies all distinct previously unknown Player IDs and shows
  their Roblox username/avatar in the Audit editor before finalization.
  Existing Players remain resolvable by `playerId` from cached identity data
  without Roblox availability. Draft creation/editing remains independent of
  Roblox; finalization involving new IDs fails retryably when Roblox is
  unavailable and rejects IDs Roblox reports as nonexistent. Mercenary and
  never-rostered Players remain supported after verification.
- Set a 14-day stale-cache threshold. Refresh on creation/manager workflows
  and through explicit maintenance only. Do not fetch Roblox metadata during
  ordinary page rendering. Existing verified cache remains usable when Roblox
  is unavailable; new unresolved IDs cannot be created through the normal
  registration/roster UI.
- Use cached username where available and otherwise `Roblox ID {playerId}`;
  use a neutral placeholder avatar whenever no valid headshot URL is cached
  or the image fails. Derive profile URLs from the canonical ID and use safe
  external-link attributes.
- Add a bounded, retry-safe, idempotent manual backfill command that uses
  batched official APIs, does not overwrite IDs, reports success/invalid/
  failure counts, and is never run at startup.
- Keep any existing Auth.js User names/images only in account/manager UI where
  the represented identity is explicitly the website User.

## Alternatives Considered

- Replace `Player.playerId` with username: rejected because usernames are
  mutable and existing references rely on stable IDs.
- Query Roblox during normal page rendering: rejected because it makes public
  pages depend on external availability and creates unnecessary request
  volume.
- Use Google/Auth.js identity as a fallback: rejected because the website User
  and game Player are distinct identities.
- Add membership-local aliases: rejected because no such field exists and
  the requester explicitly excluded this feature.
- Introduce a scheduled job framework: rejected because freshness is low
  priority and a bounded manual backfill plus opportunistic refresh is
  sufficient.
- Store downloaded avatar binaries: rejected; store only a validated URL.

## Affected Consumers

- Players registration, directory/search, profile, and Player queries.
- Units roster, roster management, and Award-associated Player surfaces.
- Audit Player results, roles, and identity presentation while preserving
  internal relational keys. Audit editors preview Roblox metadata for new
  IDs before finalization; existing Players do not require a live lookup.
- Event Battle Player/commander presentation.
- Statistics Ranker/Commander/General leaderboard Player rows and profile
  presentation.
- Public application Player links and any management selector that represents
  a game Player.

## Compatibility / Risk

The migration adds only nullable presentation columns and preserves every
existing `playerId`, internal key, foreign key, membership, Audit result, and
history record. Legacy `Player.name` values remain stored during the
compatibility period but are no longer used as global Player names or search
matches. Public DTOs gain optional identity metadata; existing ID-based routes
and consumers remain stable.

The main risks are invalid external data, temporary Roblox outages, stale
cached URLs, accidentally treating Auth.js accounts as Players, and
unintended N+1 calls. Server-only validation, fixed CDN-host checks, database
batch reads, cached fallback behavior, and mocked integration/presentation
tests mitigate these risks. No normal page request generates Roblox API
traffic.

## Approval Decision

Approved for the bounded additive schema, Players-owned batch identity
presentation read, official Roblox enrichment flows, registration/roster
confirmation, controlled backfill, and affected Player presentation consumers
described above. The requester explicitly confirmed `Player.playerId` and all
existing Player relationships remain canonical, authorized nullable metadata
fields, authorized retirement of `Player.name` from global presentation while
retaining it internally for compatibility, excluded membership-local aliases,
and prohibited synchronous Roblox page lookups. The requester also explicitly
approved batched Roblox identity preview and verification before Audit
finalization creates new Player records, while keeping Audit drafts available
and allowing existing Players to finalize from cached identity when Roblox is
unavailable.

No Roblox display-name model, authentication redesign, new membership alias
system, automatic production backfill, or scheduled job system is approved.

## Decision Owner

The human requester.

## Result

Implemented under TKT-20261103-000051-001. The accepted boundary is preserved:
`Player.playerId` remains canonical, Roblox metadata is cached and optional,
ordinary rendering performs no Roblox requests, and new Player creation is
verified before persistence.

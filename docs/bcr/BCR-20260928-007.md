# Boundary Change Request: Public Player Identity and Roster Read DTO

- Request ID: BCR-20260928-007
- Requesting ticket: TKT-20260928-000037-001
- Requesting module: players
- Affected modules: players; units; statistics; audits; events; public application presentation
- Status: Approved
- Human approval: Approved by the requester through the explicit boundary-approval task on 2026-09-28

## Problem

The public Player profile route and several links currently use internal
`Player.id`. Demo data masks the defect because `Player.id` currently happens
to equal stable game identity `Player.playerId`. The Player directory, roster,
registration-success navigation, and profile route therefore confuse public
identity with a persistence key. The roster read is composed across the
Players/Units presentation boundary without a registered read contract, and
its current ORM-shaped row includes the internal Player key in client-bound
props.

## Existing Contract

| Contract/read seam | Current Player identifier | Decision |
|---|---|---|
| `players-audits-player-resolution` | Server-only resolver returns `{ id, playerId }`. | Keep both. `id` is the internal key Audits needs for relational writes; `playerId` is stable game identity. This is not a public navigation DTO. |
| `audits-statistics-effective-finalized-audit` | Audits source observations identify Player results by stable `gamePlayerId`; persistence joins use internal keys inside Audits. | No change. Preserve internal joins and stable source output. |
| `players-statistics-membership-history` | `playerId` is the stable game Player identifier. | No change. |
| `statistics-events-event-battle-reader` | Public Player rows use stable PlayerID, falling back to stable public identity when no safe alias exists. | No change. Consumers use the stable value for any profile link. |
| `players-units-roster-authorization` | Semantic `canManageRoster` authorization only; no Player read DTO. | No change to authorization semantics. |
| `audits-events-public-battlefield-structure` | Public battlefield DTO excludes unnecessary raw persistence IDs and does not define Player profile identity. | No change. |
| Players current-roster query consumed by Unit roster presentation | Direct `getCurrentRoster` returns an ORM Player record containing both `id` and `playerId`; no registered read contract exists. | Establish `players-units-roster-read` with a presentation-safe Player reference. |

The Players directory/profile/action flow is otherwise within Players and
application presentation. Statistics readers and the Event Battle public
reader already use stable game identity. No evidence requires changing those
existing stable contracts.

## Missing Capability

The Players-owned current-roster read needs a documented Players-to-Units
read boundary that distinguishes public Player identity from internal
membership/persistence identifiers. Public presentation must not need or
receive `Player.id` to render or navigate to a Player profile.

## Proposed Change

Approve the following minimum rule and changes:

1. Public/external Player identity is the unique stable `Player.playerId`.
   Use it in `/players/[playerId]`, public Player DTOs, public search results,
   navigation links, and any Statistics/Event/Battle profile links.
2. Internal relational identity remains `Player.id`. Prisma relations,
   foreign keys, `UnitMembership`, Audit PlayerResult/role relations, internal
   persistence operations, and internal joins continue using it.
3. A public-facing DTO that identifies a Player for display or navigation
   exposes the stable PlayerID and does not expose `Player.id` as that
   identity. Existing public DTO field names such as `gamePlayerId` may remain
   when they already carry the stable value; do not rename fields for
   consistency alone.
4. Conversion from an internal key to public `playerId`, when needed, occurs
   at the Players-owned read boundary. UI components must not query or infer
   the mapping from persistence IDs.
5. Establish and register the focused `players-units-roster-read` contract.
   Its public Player reference is `playerId`; `Player.id` is excluded. An
   opaque membership reference may remain only where needed for the existing
   server-authorized roster action and is not a Player identity.
6. Keep the server-only Players-to-Audits resolver's internal `{ id,
   playerId }` result because Audits requires the relational key. Keep the
   existing Players-to-Statistics and Statistics-to-Events identity
   semantics unchanged.
7. Do not add an internal-ID URL fallback or redirect. A route parameter is
   resolved as public `playerId`; internal IDs are not canonical public IDs.

No schema, migration, membership/history behavior, authorization behavior,
metric semantics, or new Player identity model is approved.

## Alternatives Considered

- Continue routing by `Player.id` because demo values currently match:
  rejected; this makes public identity data-dependent and fails for distinct
  IDs.
- Accept either internal ID or public PlayerID in the profile route:
  rejected; it makes an implementation key a second public identity and
  prevents a reliable public not-found boundary.
- Rename every `id` in source contracts and DTOs:
  rejected; internal source seams need relational keys and existing public
  Statistics/Event values already carry stable game identity.
- Change the roster-authorization contract to include read data: rejected;
  authorization and roster read are distinct boundaries. Add a focused read
  contract instead.
- Add a schema alias, migration, or new identity table: rejected;
  `Player.playerId` already exists, is unique, and is the stable external
  game identity.

## Affected Consumers

- Players profile route, directory/search, registration navigation, and
  roster presentation.
- Unit public roster composition through the new Players-to-Units read
  contract.
- Statistics and Event/Battle presentation only where Player profile
  navigation exists; current stable identity outputs remain unchanged.
- Audits retains its server-only internal Player key for relational writes.

## Compatibility / Risk

The route segment shape remains `/players/<value>`, but its meaning is
explicitly the stable public `playerId`. Previously generated URLs containing
only a database `Player.id` are not guaranteed to resolve after correction;
there is no internal-ID fallback. This is intentional to keep the public
boundary unambiguous. Existing valid stable PlayerIDs, including mercenary
and never-rostered Players where profile support exists, remain addressable.

No persistence migration or data rewrite is needed. UnitMembership and Audit
foreign keys remain attached to `Player.id`. A deliberately mismatched test
fixture is required before implementation can be considered verified.

## Approval Decision

Approved for the exact identity rule and minimum boundaries in this request:
public routes and public Player references use `Player.playerId`; internal
relational operations retain `Player.id`; and the Players-to-Units roster
read is documented as `players-units-roster-read`. Existing internal source
seams and already-correct Statistics/Event public identity contracts remain
unchanged. Ticket 37 may proceed to READY under this boundary after its
required mismatched-ID regression fixture is recorded. This approval does not
authorize the Player identity implementation in this task.

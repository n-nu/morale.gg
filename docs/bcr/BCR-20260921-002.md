# Boundary Change Request: Events Consumer of Unit Event-Creation Authorization

- Request ID: BCR-20260921-002
- Requesting ticket: TKT-20260921-000016-001
- Requesting module: events
- Affected module: units
- Status: Approved

## Problem

The Events module must determine whether an authenticated User may create a
standalone Event. Eligibility depends on whether the User has at least one
currently effective `MANAGE_EVENTS` permission anywhere in the Units authority
system, but Events must not inspect or reproduce Units authority persistence.

The existing Units capability resolver answers permission questions against a
specific target Unit. Events has no legitimate Unit ID to supply because the
qualifying Unit is not Event ownership or authority data and must not be
stored on the Event.

## Existing Contract

None for Event creation eligibility. Units currently exposes module-level
semantic Unit-targeted capabilities and one stable Players consumer contract
for roster authorization. No Events consumer contract answers whether a User
has effective `MANAGE_EVENTS` anywhere.

## Missing Capability

A server-only boolean decision conceptually equivalent to:

```ts
canCreateEvent(userId: string): Promise<boolean>
```

The decision is true only when the User has at least one currently effective
`MANAGE_EVENTS` permission in Units authority. Missing or empty identity,
missing User, malformed hierarchy/RootUnit state, revoked grants, invalid
membership, and broken or invalid delegation lineage must fail closed.

## Proposed Change

Units will expose the semantic capability through the
`events-units-event-creation-authorization` contract. Events supplies only a
server-resolved Auth.js User ID and receives only `Promise<boolean>`.

Events does not supply a Unit ID. Units selects and evaluates all potentially
qualifying authority internally. It returns neither the qualifying Unit nor
any membership, grant, scope, RootUnit, Commander, hierarchy, delegation,
revocation, or authority-level data.

Events uses a true result only as permission to continue its own validated
Event-creation workflow. Events resolves the owner from the authenticated
session and persists that User as owner. The qualifying Unit/grant is not
stored on Event and grants no authority after creation.

Management of an existing Event is outside this contract and remains
Events-owned. `canManageEvent` and owner-only Event-manager administration must
not be implemented by Units or derived from `MANAGE_EVENTS`.

## Alternatives Considered

- Require Events to pass a Unit ID: rejected because an Event has no owning or
  authority Unit and the qualifying Unit is irrelevant after eligibility.
- Return the qualifying Unit or grant: rejected because it exposes private
  authority state and encourages prohibited Event-to-Unit coupling.
- Let Events query `PermissionGrant` directly: rejected because Units owns
  current hierarchy, scope, revocation, and delegation evaluation.
- Put `canManageEvent` in Units: rejected because existing Event authority is
  based only on Event ownership and explicit Event authorization.
- Create generalized RBAC: rejected because one narrow semantic capability is
  sufficient.

## Affected Consumers

- Events module Event-creation workflow only.

## Compatibility / Risk

The contract is additive and server-only. Existing Unit-targeted capabilities
and EventParticipation request authorization remain unchanged. The principal
risk is accidentally broadening an any-Unit eligibility check into existing
Event authority; the contract explicitly prohibits that use.

Producer changes must preserve fail-closed effective-authority semantics and
must not expose Prisma authority records. Revocation may remove eligibility to
create future Events but does not alter ownership or management of Events
already created.

# Boundary Change Request: Players Consumer of Units Roster Authorization

- Request ID: BCR-20260921-001
- Requesting ticket: TKT-20260921-000014-001
- Requesting module: players
- Affected module: units
- Status: Approved

## Problem
The Players module must protect roster membership mutations using the Units-owned
semantic authorization boundary without importing Units authority persistence or
reproducing authority logic.

## Existing Contract
`src/modules/units/server/authorization.ts` exposes the server-only semantic
capability `canManageRoster(userId, unitId): Promise<boolean>`. Its result is
Unit-scoped and hides PermissionGrant, PermissionScope, RootUnit, Commander,
delegation, revocation, and authority-level internals.

## Missing Capability
A documented consumer-backed contract is required so Players can depend on the
semantic capability as a stable cross-module boundary.

## Proposed Change
Register the smallest contract: Players may call `canManageRoster` with a
server-resolved Auth.js User ID and target Unit ID and receive a boolean allow
or deny result. The contract exposes no persistence records or resolver
internals.

## Alternatives Considered
- Import Units Prisma queries or authority types: rejected because it couples
  Players to private persistence and duplicates authorization semantics.
- Move roster persistence into Units: rejected because Players owns game
  identity, memberships, and roster derivation.
- Create a broader authorization service: rejected because the approved seam is
  already sufficient for this consumer.

## Affected Consumers
- Players module roster mutation workflows.

## Compatibility / Risk
This is a server-only additive contract. Existing Units authority behavior is
unchanged. Player schema and migration work must build forward from the local
schema baseline that includes completed Tickets 15 and 16.

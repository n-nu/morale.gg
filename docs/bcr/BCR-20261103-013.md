# Boundary Change Request: Event Scheduling and Participation Metadata

- Request ID: BCR-20261103-013
- Requesting ticket: TKT-20261103-000060-001
- Requesting module: events
- Affected modules: events; public Player presentation (consumer); units (existing request-authorization provider, unchanged)
- Status: Approved
- Human approval: Approved by the requester through the explicit boundary-approval response on 2026-11-03

## Problem

The Event model stores a single optional `opponent`, a free-text type, and a
scheduled start. It cannot represent Event-side labels, rally offset, planned
duration, or whether Units may request participation. The Event manager and
public presentation therefore cannot communicate these parts of the Event.
The persisted opponent is ambiguous because no invariant establishes which
Event side the host represents.

The Event request operation is Events-owned and consumes Units'
`canRequestEventParticipation` capability. It does not currently have a
user-facing request action or invitation lifecycle.

## Existing Contract

- Events owns Event identity, schedule, metadata, persistence, manager
  authorization, Event presentation, and participation request review.
- `events-public-presentation-batch` supplies Event identity, type, time, map,
  and opponent to the public Player-profile consumer.
- `events-audits-event-participation-management` exposes approved
  participation context and Event-manager authorization to Audits.
- `events-units-event-creation-authorization` supplies creation authority;
  Units also provides the existing server-only
  `canRequestEventParticipation` eligibility decision.
- Event Battle Structure already distinguishes `ATTACKER` and `DEFENDER`
  nodes; Event-level side labels are not Unit identities or replacements for
  that structure.
- Event type is currently persisted as a free-text `String`, not a database
  enum.

## Missing Capability

1. Persisted attacker/defender display names, rally offset, planned duration,
   and explicit OPEN/CLOSED invite policy.
2. Event-owned validation of those fields in both create and update paths.
3. Public Event metadata in the existing batched Event presentation DTO.
4. Server enforcement that a Closed Invite Event cannot accept a new
   participation request.

## Proposed Change

- Add nullable `attackerName` and `defenderName` text fields; they are
  descriptive Event-side labels and do not reference Units.
- Add `rallyMinutesBeforeStart` as a non-negative integer, defaulting to `0`
  for existing and new Events. Derive Rally timestamp from scheduled start.
- Add nullable `durationMinutes`: legacy duration is unknown and remains null;
  new creates/updates require a positive bounded integer. Derive expected end
  from scheduled start plus duration.
- Add an `EventInvitePolicy` enum with `OPEN` and `CLOSED`. Existing Events
  migrate to OPEN, preserving the current ability to request participation.
- Keep the existing `opponent` column and values unchanged. Do not infer a
  side mapping; retain the field as legacy data and preserve it in the
  existing public batch DTO for backward compatibility.
- Keep `eventType` as free text and add Ceremony and Other as available
  options. Do not rename or reorder stored values.
- Extend `events-public-presentation-batch` additively with side labels,
  rally offset, duration, and invite policy; keep existing output fields.
- Enforce CLOSED policy in the Events request service after resolving Event
  and before persisting a request. Preserve Units authorization, Event-manager
  authorization, and all existing participation status transitions.
- Keep Statistics metrics/contracts and Audit authority unchanged. No
  invitation lifecycle or request UI is introduced.

## Alternatives Considered

- Map `opponent` to Defenders: rejected because the current Event model does
  not establish which side the creator represents.
- Delete `opponent` or migrate its value: rejected because that would discard
  potentially meaningful data or guess its semantics.
- Persist rally and expected-end timestamps independently: rejected because
  they can contradict scheduled start and duration.
- Require every legacy Event to have a duration: rejected because no reliable
  duration can be derived from its stored start time.
- Change Units authority or participation states: rejected because the
  current Unit eligibility capability and Event request/decision lifecycle
  already express those responsibilities.
- Integrate planned duration into Statistics: deferred; planned duration is
  not actual battle duration and no new statistics metric is in scope.

## Affected Consumers

- Event creation and management workflows.
- Public Event list, detail, and calendar presentation.
- Events' EventParticipation request service.
- Public Player profile's consumer of `events-public-presentation-batch`.
- Units remains the provider of request eligibility; its capability contract
  and authorization semantics are unchanged.
- Audits and Statistics contracts remain unchanged.

## Compatibility / Risk

This is additive. `opponent` remains stored and remains available through the
existing public batch field, while the Create/Edit UI no longer treats it as a
current Event field. Legacy sides remain null; rally offset defaults to zero;
legacy planned duration remains null; legacy invite policy defaults to OPEN.
Existing Events remain readable, and existing public batch fields and
participation statuses remain unchanged.

The forward-only migration adds nullable/defaulted columns and an enum; it
does not reset or rewrite existing Event data. New requests are blocked only
when the Event policy is CLOSED. Pending requests remain reviewable and no
participation history is deleted. Managers continue to use existing Event
authorization.

Security impact is limited to a server-side policy check in the existing
request path; client visibility is not authoritative. The Unit capability
continues to be checked, and no Event-management permission is broadened.
The public DTO exposes only intentionally public Event metadata, never
manager or pending-participation data.

Testing must cover migration preservation, legacy defaults, create/update
validation, request-policy enforcement, unchanged manager authorization,
public DTO compatibility, and relevant responsive presentation.

The request service has no user-facing request action, and Closed Events have
no invitation lifecycle. Policy enforcement is still correct at the current
server entry point; a future request/invitation workflow requires separate
authorization and UI design.

Approved for the bounded additive Event persistence and public presentation
contract change, plus server-side enforcement of Closed Invite policy.
The requester also confirmed no conflicting edits were in progress and
authorized coordinated changes to the shared schema, migrations, and

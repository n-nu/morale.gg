# Boundary Change Request: RootUnit Awards and Scoped Award Management

- Request ID: BCR-20261102-010
- Requesting ticket: TKT-20261102-000050-001
- Requesting module: units
- Affected modules: units; players
- Status: Approved
- Human approval: Approved by the requester through the Awards feature authorization and explicit MANAGE_AWARDS scope decisions on 2026-11-02

## Problem

The Units module owns RootUnit-scoped Rank and Medal definitions, but the
Medal implementation currently contains definitions only. It has no Player or
Unit grant records, grant workflows, or Player profile presentation. A
coherent Player/Unit Awards system needs persistent grant records and a safe
cross-module boundary for Player membership scope and Player Award display.

## Existing Contract

- `ADR-20260926-005` assigns Rank/Medal catalog ownership to Units and limits
  catalog management to the current RootUnit owner. It explicitly deferred
  Player Medal assignment and display.
- `players-units-roster-read` provides public active roster rows and
  count-only Unit roster reads. It does not expose a Player's current Unit IDs
  for authorization scope validation.
- `canManageRootSettings` is a Units-owned RootUnit-owner capability.
- Ordinary Unit permissions use Unit hierarchy scopes and are revalidated
  server-side. The current permission enum has no `MANAGE_AWARDS`.

## Missing Capability

1. A generic RootUnit-scoped Award definition with independent Player/Unit
   category ordering.
2. Current Player Award and Unit Award associations and derived recipient
   counts.
3. A Units-to-Players public Award read for Player profiles.
4. A Players-to-Units minimal read of active Unit IDs for a Player, so
   hierarchy-scoped Award authorization does not query Players internals.
5. A scoped permission covering both categories and their grants.

## Proposed Change

- Keep Award definitions and both grant relations in Units. This preserves
  RootUnit catalog ownership and keeps Award authorization with the existing
  Units authority resolver; it does not transfer Player identity or roster
  ownership.
- Replace `MedalDefinition` with `AwardDefinition`, scoped to one RootUnit and
  categorized as `PLAYER` or `UNIT`. Preserve existing definition IDs,
  RootUnit IDs, names, descriptions, and image references. Since Medal order
  was not previously stored, assign deterministic initial Player Award order
  from the existing name/ID ordering. Add independent `sortOrder` values for
  both categories.
- Add current `PlayerAwardGrant` and `UnitAwardGrant` associations. Each
  Award/recipient pair is unique; counts derive from those rows. Remove
  operations remove current associations. Award definition deletion is
  rejected while any grant exists.
- Add `MANAGE_AWARDS` as an ordinary Unit permission with existing
  `SELF`, `SELF_AND_CHILDREN`, and `SELF_AND_DESCENDANTS` semantics and
  existing delegation/narrowing rules. A RootUnit-wide grant with
  `SELF_AND_DESCENDANTS` authorizes definition CRUD and assignments across
  that RootUnit. A narrower grant authorizes assignments only within its
  coverage. Existing current RootUnit owner definition access is preserved.
- Unit Award assignment/removal requires effective `MANAGE_AWARDS` at that
  Unit. Player Award assignment/removal requires at least one active
  Player/Unit membership in the Award's RootUnit and effective
  `MANAGE_AWARDS` for a membership Unit within the actor's scope. A Player
  with no current membership in that RootUnit cannot receive its Player
  Awards through this workflow. If a Player later has no active membership in
  that RootUnit, only its current owner or a `MANAGE_AWARDS` grant scoped
  `SELF_AND_DESCENDANTS` at the RootUnit may remove the orphaned grant; this
  cleanup path cannot grant an Award.
- Extend `players-units-roster-read` with a minimal active-Unit-ID read for a
  stable public Player ID. Add `units-players-awards` for the public Player
  Award read consumed by the Players profile. Neither contract exposes
  `Player.id`.
- Keep image reference validation and handling consistent with Rank images:
  safe site paths or HTTPS URLs, no upload/storage system.

## Alternatives Considered

- Keep only `MedalDefinition` and add a separate `UnitAwardDefinition`:
  rejected because it duplicates definition fields and CRUD while making the
  requested shared Awards management less coherent.
- Put Awards persistence and permission checks directly in Players: rejected
  because RootUnit catalog ownership and Unit Award grants are Units-owned,
  and it would split one Awards permission/domain across modules.
- Introduce a new top-level Awards module: rejected for this bounded change;
  existing organization catalogs, RootUnit settings, and permission authority
  are already Units-owned. The new stable read contracts preserve module
  separation for Player presentation and membership scope.
- Store recipient counts on definitions: rejected because counts are derived
  from current grant rows.
- Cascade-delete grants with an Award definition: rejected because it would
  silently remove current recipient associations. Managers must remove grants
  explicitly before deleting the definition.
- Give `MANAGE_AWARDS` global cross-RootUnit authority: rejected because
  existing authority is isolated by RootUnit and hierarchy scope.

## Affected Consumers

- Units RootUnit management page and its Player/Unit Award definition lists.
- Unit management grant controls and public Unit Award presentation.
- Public Player profile Award presentation and grant controls.
- Players active-membership read consumed by Units for authorization.
- Existing Units permission grant/delegation UI and server enforcement.

## Compatibility / Risk

The Medal table is transformed forward-only into Award definitions. Existing
definition IDs and persisted display fields remain unchanged; no current
Player/Unit grant rows exist to migrate. Existing Medal name-sorted order is
reproduced deterministically as initial `sortOrder`. Public terminology changes
from top-level Medals to Awards, while the Player profile may label its Player
Awards section “Player Awards”.

`MANAGE_AWARDS` is additive to the permission enum and uses the existing
hierarchy/scope/delegation invariants. It does not grant Unit profile,
structure, roster, Event, or other permissions. RootUnit owner access to Award
definitions is preserved; Unit/Player assignment requires the new permission.
The main risks are migration correctness, category leakage, and applying
scoped permission to multiple Player memberships; migration, category,
authorization, and multi-membership tests are required.

## Approval Decision

Approved for the bounded Awards domain, migration, contracts, grants,
presentation, and `MANAGE_AWARDS` behavior above. The requester explicitly
approved hierarchy-scoped permission behavior and the active-membership rule
for Player Award grants on 2026-11-02. The requester also approved
RootUnit-owner/full-root-manager cleanup of orphaned Player Award grants, as
narrowly described above.

No award date, citation, issuer, Event source, historical revocation,
repeat-award device, or broader reputation behavior is approved.

## Decision Owner

The human requester.

## Result

Implemented under TKT-20261102-000050-001. The forward migration, scoped
workflows, cross-module contracts, management UI, public Player/Unit
presentation, and focused regression coverage are in place. Domain and
presentation tests, Prisma validation/generation, lint, type-check, production
build, and `git diff --check` pass. Responsive Playwright verification remains
pending a local QA database with the Awards migration applied; the configured

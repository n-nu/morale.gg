# Boundary Change Request: Event Battlefield Management and Battle Reads

Request ID: BCR-20260928-006
Requesting ticket: TKT-20260928-000033-001
Requesting module: architecture
Affected modules: events; audits; statistics; players; units; application presentation
Status: Approved
Human approval: Approved by the product/architectural owner on 2026-09-28

## Problem

Ticket 33 requires a truthful two-side Event Battle surface, Event-manager
construction of atomic battlefield units, history-preserving Event results,
Audit discovery from the selected participation, and Event-scoped Battle
Statistics. Existing contracts separate Event management, Audit submission,
Audit persistence, and derived Statistics but do not expose these minimum
integration seams.

## Existing Contract

Events owns Event, EventParticipation, and `canManageEvent`. Audits owns
atomic units, finalized Audits, command groups, and public finalized reads.
Units owns `canSubmitAudit`; Statistics consumes four approved source seams and
owns derived metric semantics. `EventParticipation` is approved acceptance,
not side placement. The existing command-group represented Unit field is
descriptive and not an authoritative participation claim.

## Missing Capability

1. Events must authorize an Event-manager mutation seam for Audits-owned
   atomic battlefield structure without granting Audit submission/finalization.
2. Audits must expose public Event hierarchy facts and Unit-authorized atomic
   discovery without leaking private persistence or unrelated units.
3. Statistics must compose an Event-scoped Battle reader from approved source
   facts and return a presentation-safe DTO.
4. Event and Audits need bounded support for fixed sides, participation-backed
   claims, optional Event flag references, and result history.

## Proposed Change

Approve the following minimum boundaries:

- `events-audits-event-battlefield-management`: Events supplies approved
  participation validation and `canManageEvent` authorization for Audits
  atomic-unit creation/configuration/placement. Audits performs invariant
  validation and persistence. The seam never authorizes Audit submission or
  finalization.
- `audits-events-public-battlefield-structure`: Audits supplies public,
  presentation-safe side-separated hierarchy data and manager-safe options;
  Events consumes it for public Event and manager views. Draft/private Audit
  details remain protected.
- `statistics-events-event-battle-reader`: Statistics supplies
  `getEventBattleStatistics(eventId)` and owns all aggregation/ratio semantics;
  Events consumes the DTO for public Battle presentation. The DTO includes
  atomic, pending/finalized, Player, and optional safe group summaries, never
  internal authorization data or Rank-at-Event.

The existing Events -> Audits participation context and Units -> Audits
`canSubmitAudit` contracts remain authoritative. No new Unit authorization
lookup is required: Audits resolves the represented Unit from the approved
participation and applies `canSubmitAudit` for `/audits` discovery. The user
does not reselect a Unit.

## Alternatives Considered

- Let Audits call private Event authorization persistence: rejected because it
  bypasses Events ownership.
- Reuse `canSubmitAudit` for Event-manager structure writes: rejected because
  Audit submission and Event management are independent authorities.
- Let Event pages query Audit/Statistics persistence directly: rejected because
  it bypasses public module contracts and duplicates aggregation.
- Add a generalized upload/media subsystem for flags: rejected because the
  existing validated image-reference behavior is sufficient.
- Add a new generic RBAC capability: rejected because `canManageEvent` is the
  approved Event-manager authority.

## Affected Consumers

- Event public detail and Event management presentation
- Audits atomic-unit management and `/audits` discovery
- Statistics Event Battle reader
- Public Battle presentation
- Existing Statistics source contracts, without changing their ownership

## Compatibility / Risk

The change is additive but RED. Existing Events have no side values and must
not receive inferred assignments. Existing atomic units/groups require a
forward migration that preserves their participation links and allows an
explicit legacy-unconfigured state. Existing command-group represented Unit
data must be migrated transactionally to approved participation references or
left unavailable only where no truthful mapping exists; no duplicate identities
may remain authoritative.

For this revision, null is not converted to an assigned side by migration or
inference. Legacy null-side trees remain manager-configurable and are excluded
from public side trees until explicitly placed. The existing nullable columns
and enum already represent the revised configuration; durable behavior remains
in PostgreSQL rather than client-only state.

Result history introduces immutable effective/revision records and a pending
correction workflow. Any currently authorized Event manager may propose a
different correction; another currently authorized Event manager must approve
or reject it. Proposers cannot approve or reject their own proposals, including
when they are the Event owner. A single-manager Event may leave a correction
pending until another authorized manager is available. Approval supersedes the
prior effective result, rejection leaves it unchanged, and all history is
retained. Concurrent correction races must be rejected transactionally.

Security risk is authority confusion. Server checks must keep
`canManageEvent` separate from `canSubmitAudit`, and public DTOs must exclude
private manager rows, Auth.js submitter identity, and pending sensitive
metadata.

## Approval Decision

Approved for the documented boundary, schema design, contracts, two-ticket
implementation decomposition, and the explicit correction approval rule:
proposer self-approval is forbidden; a different currently authorized Event
manager reviews; the owner has no bypass; and one-manager corrections remain
pending.
The product/architectural owner also authorized the Ticket 34 review revision
on 2026-09-28. Existing nullable `side` columns use `null` as durable
`UNSORTED` manager configuration state; no schema migration is required. New
nodes are created without side or parent. Placement is an Audits-owned
authorized mutation, and moving a group updates all descendant group and
atomic sides in one transaction. Unassigned nodes are available only through
an Event-manager read and are omitted from the public structure contract. The
public Event and manager editor use one conceptual Battle Structure surface;
the old route is retained only as a redirect.

# Boundary Change Request: Audit Module and Event-Scoped Audit Contracts

- Request ID: BCR-20260927-004
- Requesting ticket: TKT-20260927-000020-001
- Requesting scope owner: architecture
- Affected modules: proposed audits; events; units; players
- Status: Approved
- Human approval: Approved by the human architectural owner on 2026-09-27

## Problem

The next MVP capability needs Audit persistence, atomic Event units, and
Event-scoped command groups. No current module owns that complete responsibility
and no existing contract permits the required cross-module decisions. Events
owns EventParticipation and Event management but explicitly excludes Audits;
Units owns authority but explicitly excludes Events and Audits; Players owns
identity and roster history but exposes no Audit-facing identity operation.

## Approved Boundary

Create the new `audits` module. It consumes only documented
contracts and owns Audit/atomic-unit/group data and workflows. It must not
inspect Units grants, mutate Player memberships, or reproduce Event
authorization.

Three minimal contract seams are approved:

1. **Events -> Audits:** validate/load an Event's approved
   `EventParticipation` and expose the Events-owned `canManageEvent` semantic
   decision for command-group administration. The contract must not expose
   private Event manager rows or permit Audits to change participation state.
2. **Units -> Audits:** a server-only target-Unit Audit submission capability,
   conceptually `canSubmitAudit(userId, unitId)`, based on effective
   `SUBMIT_AUDITS` authority. It must return only the semantic decision and
   must define whether it covers atomic-unit creation, draft mutation, and
   finalization.
3. **Players -> Audits:** a server-only resolve-or-create operation by stable
   game PlayerID. It must return persistent Player identity, reuse existing
   records, create missing identity where permitted, and never create or alter
   UnitMembership or aliases as a side effect.

The exact operation names and payload details are recorded in the three
approved contract documents. DTO/UI shape and SQL decomposition remain GREEN.

## Current Boundary

- Events owns `Event`, `EventParticipation`, `canManageEvent`, and public
  Event reads.
- Units owns Unit authority and the `Permission` enum including
  `SUBMIT_AUDITS`, but no Audit capability.
- Players owns `Player` and `UnitMembership`; `Player.name` is nullable
  compatibility data so an Audit-created Player may have no alias or canonical
  name. Existing values are preserved.
- Stable contracts now also cover the approved Audit seams.

## Compatibility and Migration Impact

The approved change is additive to module ownership but requires new Prisma foreign
keys and forward migrations. It explicitly preserves EventParticipation's
unique `(eventId, unitId)` meaning and introduces a separate one-to-many
atomic-unit relationship. Existing Event management and roster semantics must
remain unchanged. Older documentation claiming one Audit per participation is
superseded by the atomic-unit model. Events/Units/Players manifests and
registries are synchronized under Ticket 20.

Finalized Audit history requires restrictive deletion or explicit transactional
protection for Event, Unit, Player, atomic-unit, group, and Audit relationships.
The Player required-name mismatch is resolved by making the legacy `Player.name`
field nullable through a forward migration, without adding a placeholder or
canonical alias requirement.

## Security and Authority

Audit draft identity comes from the authenticated website User, not a Player
and not client-provided ownership. Unit submission authority and Event group
administration are separate decisions. The represented Unit in a group is
descriptive and never grants authority. Finalized records cannot be edited in
MVP. Public finalized-read behavior is approved, while drafts and
management-only data remain protected.

## Future Statistics Compatibility

The approved boundary preserves, without implementing statistics:

- Ranker observations from every Audit Player result, including mercenaries
  and never-rostered Players, with K/D/A and Event identity derivable and
  combat populations partitionable by Regular, Rifles, Cavalry, and Artillery.
- Commander observations from the Player assigned the Commander role in each
  atomic Audit, inheriting that result's Unit type and remaining independent
  of persistent Unit Commander status.
- General eligibility from at least two unique underlying atomic Event units,
  regardless of type. Nested groups flatten to unique atomic Audits, and
  combat/result aggregation remains partitioned by Unit type rather than
  averaging child-group averages.

Required links are PlayerResult -> Player, PlayerResult -> Audit, Commander
role -> Player + Audit, Audit -> atomic Event unit -> EventParticipation ->
Event + persistent Unit, result -> Unit type, and command group -> Commander
Player plus unique descendant atomic units.

## Testing and Verification Impact

The implementing ticket must test all parser, Player resolution, mercenary,
draft/finalization, role cardinality, EventParticipation integrity,

## Approval Result

The human architectural owner approved:

- creation and registration of the `audits` module;
- all three cross-module contract seams and their compatibility guarantees;
- `SUBMIT_AUDITS` coverage for atomic-unit creation, draft creation, and
  finalization, with creator-only existing-draft edits;
- Event-manager authority for command groups through `canManageEvent`;
- nullable legacy Player name handling;
- public finalized-Audit and command-structure reads with private drafts;
- deletion/history rules and the database/transaction enforcement split; and
- amendment of current architecture documentation and registries.

This BCR authorizes the planning artifacts and a separate implementation
handoff. It does not itself authorize feature code, schema migration, or an
ACTIVE implementation ticket.

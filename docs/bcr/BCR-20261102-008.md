# Boundary Change Request: Batch Current Roster Counts for Unit Directory

- Request ID: BCR-20261102-008
- Requesting ticket: TKT-20261102-000048-001
- Requesting module: units
- Affected modules: players; units
- Status: Approved
- Human approval: Approved by the requester through the explicit boundary-approval choice on 2026-11-02

## Problem

The public Unit directory needs active member counts for many Units. The
existing Players-to-Units read returns complete roster rows for only one Unit
per call. Repeating that read for every directory card is unnecessarily
expensive and returns Player display data that the count presentation does not
need.

## Existing Contract

`players-units-roster-read` provides the active roster rows for one persistent
Unit at a time. Its semantics count only current `UnitMembership` periods
(`endedAt = NULL`) and preserve Players ownership of membership persistence
and reads.

## Missing Capability

A batch read that returns current active roster counts for a set of Units,
without returning Player identities or membership details.

## Proposed Change

Add `getCurrentRosterCounts(unitIds)` to the Players-owned public roster read.
It accepts persistent Unit IDs and returns one `{ unitId, memberCount }` row
for every distinct requested ID, including zero for Units with no active
roster. Counts derive only from existing active `UnitMembership` rows with
`endedAt = NULL`. The implementation performs one grouped read; it adds no
schema, stored count, migration, Player identity, or mutation capability.

Update the existing `players-units-roster-read` contract additively from
version 0.1 to 0.2. Existing single-Unit roster reads and their DTOs remain
unchanged.

## Alternatives Considered

- Call the existing full-roster reader once per Unit: rejected because it
  performs N queries and transfers unnecessary roster fields.
- Read UnitMembership directly from Units or the route: rejected because
  Players owns roster persistence and current-roster derivation.
- Persist or cache member counts: rejected because the count is derived data
  and no persistence change is needed.

## Affected Consumers

- Units public directory and public Unit hierarchy presentation.
- Existing roster consumers remain compatible and need no behavior change.

## Compatibility / Risk

The contract addition is backward-compatible: the existing operation and DTO
are unchanged. The new operation exposes only Unit IDs already supplied by
the caller and aggregate counts; it does not expose Player or membership IDs.
Public read access does not change, and no authorization semantics are
introduced. The only data source remains the existing active-membership
predicate.

## Approval Decision

Approved for the bounded additive batch-count operation and contract update.
No schema, membership semantics, authorization, or identity changes are
approved.

## Decision Owner

The human requester.

## Result

Implemented under TKT-20261102-000048-001: added the grouped Players-owned
query and focused tests, updated the contract and registry, and consumed the
read from the Units-owned directory query.

# Boundary Change Request: Units Management Workflows and Administration Surface

- Request ID: BCR-20260926-003
- Requesting ticket: TKT-20260926-000019-001
- Requesting module: units
- Affected module: units
- Status: Approved

## Problem

The Units module owns Unit identity, hierarchy, RootUnit isolation, Commander
persistence, authorized-user and permission persistence, and authority
resolution. Its current manifest explicitly excludes authority-management
workflows/UI and says Unit creation and structural workflows are unimplemented.
The requested Unit Management Panel places Unit profile, authorized-user and
grant administration, and hierarchy workflows in a Units-owned application
surface. No current operation-specific structural workflow exists, and
`canManageAuthorizedUsers` is only a permission-coverage check; neither may be
reconstructed as client authorization.

## Existing Contract

No new cross-module contract is proposed. Existing Units capabilities remain
server-only and retain their current semantics:

- `canManageUnit(userId, unitId)` checks effective `MANAGE_UNIT` coverage.
- `canManageAuthorizedUsers(userId, unitId)` checks effective permission
  coverage only; mutation workflows must additionally enforce hierarchy,
  scope, authority-level, delegation, and Commander rules.
- The authority resolver does not grant operational permissions from Commander
  status.

ADR-20260915-002 already defines structural territory, creation prerequisites,
move invariants, and safe leaf deletion. The ticket asks for operation-specific
Units-owned server enforcement and workflows that implement those rules.

## Missing Capability

A reviewed Units-owned application boundary for the requested management
workflows, including operation-specific authorization for structural create,
move, and delete; authorized-user and permission-grant mutations; and a
server-enforced route/action surface. The current module manifest treats these
workflows/UI as outside the Units module boundary.

## Approved Change

Units owns Unit profile management, authorized-user administration,
authority-level and permission-grant administration, structural create/move/
delete workflows, and their management UI. These workflows remain inside the
Units module; no cross-module ownership or consumer contract is introduced.

Structural operations are Units-owned server workflows with operation-specific
authorization. Do not introduce a generic client-consumable
`canManageStructure` boolean as the sole policy. Creation, movement, and
deletion have distinct contextual checks. Preserve `MANAGE_STRUCTURE`
strict-descendant territory, same-RootUnit checks, cycle prevention,
source/destination validation, initial Commander plus level-0 membership,
separate `MANAGE_AUTHORIZED_USERS` authority for Commander assignment,
leaf-only hard deletion, protected-history restrictions, and no implicit
operational grants. Hard deletion is allowed only for an otherwise-unused
non-RootUnit leaf with no children or protected Player/Event/history references
and exactly one active current Commander/level-0 bootstrap membership with no
PermissionGrant history. That bootstrap membership is removed atomically with
the Unit; all other membership and grant/delegation history blocks deletion.
No archive/tombstone state is introduced. The UI calls these workflows and
does not reconstruct authority or deletion-safety rules.

Ordinary Unit operations continue to require their existing operational
permissions. Commander/Unit-owner identity does not grant operational
permissions. RootUnit catalog authority is the narrow exception approved by
ADR-20260926-005 and is not generalized to other Unit operations.

Synchronize `src/modules/units/MODULE.md` and repository architecture/registry
indexes under TKT-20260926-000019-001. Do not alter Players or Events ownership.

This request does not transfer Player/Roster ownership from Players, Event
ownership from Events, or shared authentication ownership. It does not create a
new cross-module contract. RootUnit-only organization settings and catalog
ownership are addressed separately by ADR-20260926-005.

## Alternatives Considered

- Keep these workflows outside Units without an identified owning module:
  rejected as an incomplete ownership boundary for Unit-owned data and rules.
- Authorize through client-visible controls or generic boolean checks alone:
  rejected because visibility is not authorization and structural operations
  require source/destination territory checks.
- Treat every Commander as an unrestricted administrator: rejected because
  ADR-20260915-002 explicitly separates Commander identity from operational
  grants.
- Move roster or Event workflows into Units: rejected because Players and
  Events own those workflows and existing contracts remain unchanged.

## Affected Consumers

- Units management routes and server workflows only.
- No Players or Events consumer is authorized or proposed.

## Compatibility / Risk

The proposal expands the documented Units application responsibility but does
not alter existing capability results, permission enums/scopes, delegation,
revocation, authority levels, RootUnit ownership, or data ownership in Players
and Events. The main risk is treating a semantic permission-coverage check as a
complete operation policy. Structural operations must follow the approved
strict-anchor, same-RootUnit, cycle, transaction, Commander, and history rules.

No new public cross-module API is required for the proposed internal consumer.
If a later real consumer needs one, obtain a consumer-backed BCR/contract before
exposing it.

## Approval Decision

Approved by the human architectural owner on 2026-09-26. This approves the
Units-owned workflows and operation-specific structural authorization boundary
above without changing existing permission, delegation, revocation, Commander,
RootUnit, Player, or Event semantics.

Project maintainers / human RED approval authority.

## Result

The Units module manifest, architecture overview, and module registry have been
synchronized under TKT-20260926-000019-001. The human architectural owner

# Ticket: Expand Event scheduling and participation policy

## Main Success Scenario

1. An authorized Event creator enters the Event's type, start, rally offset,
   planned duration, optional side labels, and invite policy.
2. The Event persists these values without losing legacy opponent data, and
   authorized managers can edit them.
3. Public and management Event surfaces present the metadata consistently;
   the server rejects participation requests for Closed Invite Events.

## Assumptions

| Statement | Status | Evidence or decision |
|---|---|---|
| `opponent` must remain persisted and must not be guessed into either side field. | CONFIRMED | Requester-approved requirements; Event model has no established host-side semantics. |
| Existing Events receive OPEN policy to preserve the current ability to request participation. | CONFIRMED | Requester approved the additive change; current Events have no policy field. |
| Legacy planned duration is unknown and remains null; newly created or edited Events require a valid duration. | CONFIRMED | Existing Event model has only a scheduled start and no actual/end duration. |
| Event side labels are optional display names, not Unit references. | CONFIRMED | Requester-approved requirements and current independent Event/Battle Structure ownership. |
| Event type remains free text; Ceremony and Other are additive options. | CONFIRMED | Current schema stores `eventType` as `String`. |
| Participation request UI and invitation lifecycle are not expanded in this ticket. | ACCEPTED-AS-LIMITATION | Existing request service has no user-facing request action; the authorized scope covers policy enforcement and Event presentation only. |

## Acceptance Criteria

- [x] Create and Edit Event expose schedule, rally offset, planned duration, side labels, invite policy, map, and description.
- [x] Creation/update validate integer rally minutes in `[0, 1440]`, integer duration in `[1, 1440]`, safe timestamps, and a valid invite policy.
- [x] Rally and expected-end timestamps derive from the canonical scheduled start and durations, including day rollover and time-zone-safe presentation.
- [x] Attackers and Defenders are nullable text labels; no Unit foreign key or inferred side mapping is introduced.
- [x] `opponent` values remain intact and readable in legacy persistence; no value is silently mapped or deleted.
- [x] New records default to OPEN when no policy is supplied; existing records migrate to OPEN.
- [x] Closed Invite participation requests are rejected in the Events server domain path; existing pending/approved/denied rows and the decision lifecycle are preserved.
- [x] Ceremony and Other can be created with empty side labels and without requiring Battle Structure data.
- [x] Public Event detail, management, list cards, and calendar presentation use the new metadata where appropriate and omit empty side sections.
- [x] `events-public-presentation-batch` adds the new public fields while preserving its existing fields and semantics.
- [x] Demo fixtures cover Open and Closed policies, Ceremony, Other, varied rally offsets, and varied planned durations without replacing unrelated synthetic battle data.
- [x] No Statistics metric/semantics, Audit authority, Unit membership, or participation transition changes are introduced.
- [x] Relevant tests cover creation, update, validation, legacy compatibility, policy enforcement, contract output, and Event presentation.

# Ticket: Authority Persistence Implementation - Expand and Backfill

## Implementation Owner

Lead

## Objective

Implement the non-destructive expansion and structural backfill phase of the
accepted RootUnit authority persistence design. This ticket establishes durable
RootUnit, authority-membership, permission-grant, enum, audit, and delegation
lineage structures while preserving legacy Units that cannot yet be assigned
to an existing Auth.js User as Commander.

This is the first of two coordinated RED tickets. The follow-on bootstrap and
constraint-tightening ticket is TKT-20260920-000012-001.

## RED Reason

This work changes shared PostgreSQL schema relationships, Unit ownership,
authority persistence, and system invariants. It is authorized by:

- ADR-20260915-002 (RootUnit Authority and Delegated Unit Permissions);
- ADR-20260915-003 (Bounded Website-Administrator Identity Mechanism).

## Main Success Scenario

1. Existing Units remain readable without reset or data loss.
2. Every existing Unit is backfilled to exactly one RootUnit designation/tree.
3. Authority persistence tables and exact permission/scope enums exist.
4. Legacy Units may temporarily have no Commander only during the approved
   bootstrap conversion state.
5. The database is prepared for a trusted website administrator to assign an
   existing Auth.js User as Commander and atomically create level-0 membership.

## In Scope

- RootUnit persistence and RootUnit/Unit association;
- transitional nullable `Unit.commanderUserId` and final-state schema support;
- AuthorizedUserMembership and PermissionGrant persistence;
- exact seven-value Permission enum and ordinary PermissionScope enum;
- `delegatedFromGrantId`, `createdByUserId`, timestamps, and soft-revocation
  metadata (`revokedAt`, `revokedByUserId`);
- required foreign keys, ordinary uniqueness, checks, partial indexes, and
  raw PostgreSQL structures that do not require Commander bootstrap data;
- RootUnit/root-association backfill for existing Unit trees;
- migration, Prisma generation, persistence-level migration validation, and
  seed/bootstrap preparation only where required by the approved model;
- update of Units module truth for accepted authority-persistence ownership.

## Explicitly Out of Scope

- final non-null Commander enforcement and Commander/level-0 consistency
  activation; that is TKT-20260920-000012-001;
- trusted bootstrap operation implementation;
- capability engine or `canManage*` functions;
- authorization middleware, permission-aware UI, authorized-user UI,
  delegation workflows, structural CRUD workflows, Event/Roster/Audit
  enforcement, generalized RBAC, ranks, medals, or contracts.

## Migration Strategy

1. Add enum and authority tables plus nullable Unit transition fields.
2. Create one RootUnit designation for each existing top-level Unit and
   backfill every Unit's root association using the existing parent tree.
3. Preserve Units without a Commander until an existing Auth.js User is
   explicitly selected by a trusted website administrator.
4. Add soft-revocation storage so grant lineage can remain auditable.
5. Do not make Commander required or activate the deferred Commander
   consistency trigger until the follow-on bootstrap succeeds for every Unit.

## Invariant Enforcement

| Invariant | Expand/backfill enforcement | Final enforcement owner |
|---|---|---|
| Unit belongs to a designated RootUnit | RootUnit FK, composite parent/root relation, root backfill validation | This ticket plus deferred root trigger where needed |
| User has one membership per Unit | unique `(userId, unitId)` | This ticket |
| Authority level is non-negative | PostgreSQL CHECK | This ticket |
| One level-0 member per Unit | partial unique index | This ticket; no legacy Unit is required to have one yet |
| Commander matches level-0 membership | deferred during transition | TKT-20260920-000012-001 transaction and deferred trigger |
| Structural grant has null scope | PostgreSQL CHECK and partial unique index | This ticket |
| Ordinary grant has ordinary scope | PostgreSQL CHECK and partial unique index | This ticket |
| Delegation lineage is preserved on revocation | soft-revocation fields and source FK | This ticket; effectiveness evaluation later |
| Strict delegation and cross-root delegation | not implemented as an evaluator | later authorization implementation |

  PostgreSQL migration deployment/status, persistence-level tests, `npm run

- Expected result: the expand/backfill migration preserves current Units and
  rejects direct invalid persistence states within the transitional model.
- Actual result: PASS. Prisma validation and generation, migration deployment,
  migration status, lint, type-check, and production build all passed.

- Command/check: transaction-scoped direct PostgreSQL persistence verification
  using temporary records and savepoints.

  lineage states are rejected while revoked grants remain stored.

  duplicate level-0 membership, both invalid permission/scope combinations,

  delegation FK were rejected. Revoked grant lineage was retained. Existing
  Unit IDs, names, parent links, root associations, and RootUnit designations
  were unchanged. The outer transaction rolled back all temporary records.

## Rollback and Risk Notes

- Use expand/backfill/contract migrations; never reset or reseed production
  data.
- Backfill RootUnit associations before creating final RootUnit-bound FKs.
- Do not contract nullable Commander fields until every Unit has an explicit
  existing-User assignment.
- RootUnit/Unit cyclic references and deferred Commander checks require raw
  PostgreSQL migration SQL beyond Prisma schema expression.
- A failed backfill must leave the existing Unit hierarchy readable and must
  not fabricate or delete Auth.js Users, Units, memberships, or grants.

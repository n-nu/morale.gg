# Ticket: Stable Public Player Identity Across Routes and Statistics Navigation

## Objective

Make the stable game identity `Player.playerId` the only Player identity used
in public URLs and public Player DTOs, while retaining `Player.id` exclusively
for internal persistence, relational foreign keys, and internal membership
operations. Audit every public Player navigation and read surface before
changing it. Do not change membership or history semantics, and do not change
the schema unless inspection proves a schema change is genuinely necessary.

## Investigation Context

This defect was discovered incidentally while investigating Unit Statistics
and Player profile failures. Those failures came from the stale Ticket 32
branch using the old EventCommandGroup shape; merging current `main` resolved
them. The Player identity defect is unrelated to that resolution and is not a
reason to block PR #20 or Ticket 32. Do not modify PR #20 or Ticket 32; these
records may be referenced for investigation context only.

Seeded demo records currently have `Player.id === Player.playerId`, masking
the boundary error. Current code inspection found that `getPlayer` resolves
the profile route by internal primary key; the Player directory and Unit
roster build public profile links with internal IDs; and the registration
success link receives the internal ID returned by its server action. The
roster component test currently asserts the internal-ID URL. Players owns
identity and profile resolution; Unit roster presentation and Statistics/Event
readers consume public identity across module boundaries.

## Required Identity Boundary

```text
PUBLIC URL / PUBLIC DTO
    -> Player.playerId

INTERNAL RELATIONAL FK
    -> Player.id
```

Do not expose or use internal IDs in public Player routes, public DTOs, or
navigation merely because they currently happen to equal public PlayerIDs in
demo data. Internal joins, membership FKs, and server-side operations may
continue to use `Player.id` within their owning persistence boundary.

## Main Success Scenario

1. A visitor opens a public Player route using the stable game PlayerID.
2. Players resolves that public identity and uses the internal Player key only
   for membership/history and relational reads inside the server boundary.
3. A visitor follows a Player link from any supported public directory,
   roster, Statistics, Attendance, search, or Event/Battle result surface and
   reaches the same profile using `Player.playerId`.
4. A known mercenary or otherwise unrostered Player still resolves wherever
   public profile support permits; an unknown public PlayerID renders the
   normal not-found response.

## Required Surface Audit

Inspect all public Player-link and navigation paths, including:

- Unit roster links and roster read DTOs;
- Player directory results, exact-match/search results, and any other public
  search results;
- Ranker, Commander Statistics, and General Statistics rows or destinations;
- Attendance surfaces wherever Player navigation exists;
- Event/Battle Statistics Player rows or destinations;
- registration/creation success links and other Player profile entry points;
- `/players/[id]` route resolution and normal unknown-ID handling.

Current source inspection confirms the directory, Unit roster, registration
success link, and profile route use internal IDs. Statistics readers and the
Event Battle contract expose stable game identity; audit their presentation
and any links rather than assuming every row is currently navigable.

## Requirements

- Public profile route resolution uses stable `Player.playerId`.
- Every public Player URL/link and public Player DTO uses `Player.playerId`,
  including action results used to navigate.
- `Player.id` remains internal to Players persistence and relational
  operations; membership and other FK values are not redefined as public IDs.
- Audit and correct the public read/navigation paths listed above. Where a
  surface does not currently support Player navigation, record that finding
  and do not add navigation unless it is required by an approved contract.
- Preserve lookup and profile support for mercenary/unrostered Players where
  currently supported; profile availability must not require active
  membership.
- Preserve all membership, attendance-obligation, and history semantics.
- Do not change the schema unless implementation inspection demonstrates a
  genuine persistence requirement and separately obtains approval.

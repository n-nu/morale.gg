# Ticket: Event Command Structure and Battle Statistics Architecture Review

## Objective

Inspect and bound the next implementation work for a public Event command
structure integrated with finalized Audit results. The intended experience is a
read-only public battlefield organization view and an authorized Event-manager
editor using the existing atomic Event-unit, EventParticipation, Audit,
command-group, authorization, and Statistics architecture.

This is a planning and architecture-review ticket only. It creates no
production implementation, schema, or migration. It creates the approved
architecture artifacts and follow-up implementation tickets recorded below.

## Main Success Scenario

1. The architecture owner reviews the repository findings and distinguishes
   existing capability from missing durable domain or read-boundary decisions.
2. The owner approves the smallest decomposition for side/outcome semantics,
   command-structure presentation/editing, and Event-scoped finalized-result
   presentation.
3. Follow-up implementation tickets can be created without inventing side,
   outcome, authorization, hierarchy, identity, rank, or aggregation semantics.

## Current-State Findings

### Event side/team model

No persisted Event, EventParticipation, AtomicEventUnit, or EventCommandGroup
field models a team, side, coalition, attacker/defender designation, or custom
side name. `Event.opponent` is free text and is not a durable two-side model.
The public two-column layout therefore cannot be truthfully implemented by
CSS, ordering, names, or arbitrary strings. A durable side model is a RED
schema/domain decision.

### Battle outcome model

No persisted authoritative Event or Audit outcome represents winner, loser,
draw, victory, or defeat. The current Audit source contains unit metrics but
does not define a winner algorithm. The UI must not infer an outcome from K/D/A,
Tickets, Stars, or any other statistic. Outcome presentation is deferred until
an explicit domain decision exists.

### Atomic Event units and EventParticipation

`AtomicEventUnit.eventParticipationId` is a required foreign key to exactly one
`EventParticipation`. The participation is unique by Event and persistent Unit
and must be `APPROVED` for atomic-unit creation. Multiple atomic units may be
created for one approved participation. The identity later referenced by an
Audit is the same atomic-unit identity; Audit has a unique
`atomicEventUnitId` and therefore at most one Audit in the current MVP.

The existing creation path is `createAtomicEventUnit` in the Audits module, but
it currently authorizes through Units-owned `canSubmitAudit`, exposes only
mandatory/optional state, and is surfaced from `/audits`. It does not yet
provide Event-manager creation from the Event management surface, a name,
represented-Unit selector, or Audit type/team selector. Creating a name or side
field would require domain/schema review; an Event-manager workflow must not
silently replace the existing Audits authority boundary.

### Command groups and hierarchy

`EventCommandGroup` is Audits-owned, Event-scoped, and stores name,
descriptive represented persistent Unit, designated Commander Player, and an
optional parent group. `EventCommandGroupAtomicUnit` gives an atomic unit at
most one immediate group parent through a unique `atomicEventUnitId`.

The existing server workflows support create, edit, delete, attach/detach,
child-group attach, and group reparenting. Public reads are provided by
`getPublicEventCommandStructure`; manager options and mutations are protected
through Events-owned `canManageEvent`. The current page already offers a
non-drag select-and-move fallback, but no drag-and-drop interaction and no
atomic-unit create/edit workflow in the command editor.

Existing validation preserves same-Event edges, no cycles/self-parenting, one
immediate parent per group or atomic unit, no duplicate atomic contribution in
the tree, and unique descendant flattening. Groups may contain child groups and
atomic units. General qualification remains at least two unique descendant
atomic units; nested groups flatten uniquely, and Regular/Rifles/Cavalry/
Artillery populations remain partitionable. These semantics must not change for
drag-and-drop or visual reorganization.

### Audit lifecycle and public data

Audit drafts are creator-private. Finalized Audits are immutable and publicly
readable. The existing public Audit read returns finalized Unit type, Tickets,
Flag Captures, Flag Losses, Stars, PlayerID-based K/D/A rows, and Audit role
assignments. Drafts are filtered from public result rows and should present only
as a safe pending state where the public reader permits the atomic unit to be
seen.

The finalized source preserves the raw facts required for Statistics:
effective finalized Audit identity, atomic Event unit, Event and participation
context, represented persistent Unit, mandatory state, Unit type, Unit results,
Player K/D/A, Commander role, and command-group descendants. It does not
provide a ready-made Event hierarchy-plus-results DTO.

### Statistics boundary

Statistics owns derived aggregation, ratio semantics, type partitioning, and
the shared time-window policy. Existing public readers are Ranker, Commander,
General, persistent Unit performance, and Player+Unit attendance. None is an
Event-scoped Battle Statistics reader. Ticket 28 explicitly deferred replacing
the Event Battle Statistics placeholder because a new Event-scoped Statistics
seam requires separate design approval.

The implementation must not query private Audit/Player/Unit persistence from a
React page or reproduce aggregation in Event UI code. An Event-scoped reader
must either be added to Statistics through a new approved read boundary or the
presentation must consume a suitably extended existing public contract without
duplicating semantics. This is at least YELLOW and likely RED because it adds a
cross-module public read capability.

### Identity, role, commander, and rank

- Atomic-unit Commander comes from the finalized Audit `COMMANDER` role.
- Group Commander is the separately persisted `EventCommandGroup.commanderPlayer`
  designation and is not the persistent Unit Commander.
- Player public identity is the stable game `Player.playerId`; `Player.name` is
  nullable compatibility data. Unit-local aliases are the only approved source
  for a preferred display alias when available, and no canonical global Player
  name may be invented.
- `UnitMembership` currently stores membership periods but does not persist a
  Rank assignment. `RankDefinition` is a RootUnit catalog only. Historical
  Rank-at-Event cannot currently be resolved. The ticket must omit rank from
  historical Battle Statistics or label an explicitly approved current/catalog
  value; it must not silently display current Rank as historical rank.
- Audit positions are currently `COMMANDER` and, for Regular, `FLAG_BEARER`.

## Public Information Architecture

The current Event detail page has an Event header, details, participating-unit
side panel, a Battle Statistics placeholder, and a link to command structure.
The proposed future public section should replace the duplicate placeholder and
separate command structure from ordinary Event details only once side semantics
are approved:

1. Event header and schedule/map/details.
2. One Battle section containing the command hierarchy and its compact result
   summaries, with two side columns only when a persisted side model exists.
3. Group nodes show name, designated Commander, and descendant count by
   default; they remain organizational-only unless a Statistics reader safely
   supplies group results.
4. Atomic-unit nodes show name/represented Unit, Audit type where finalized,
   Commander, and a compact K/D/A plus approved zero-death ratio display.
5. `<details>/<summary>` or the established disclosure primitive reveals
   Tickets, Flags, Stars, finalized state, and compact Player result rows.
6. No draft/private Audit details are exposed. Missing finalized results use
   `Results pending` or equivalent.

On mobile, sides stack vertically or use an accessible side selector. The
layout must remain readable at approximately 390px, 768px, and 1440px without
body-level horizontal overflow. Existing Events-derived dark surfaces,
typography, separators, gold/green/red status conventions, and compact
disclosures remain authoritative; the reference sketch is structural only.

## Manager Editor UX

The manager surface should be integrated into the existing Event management /
command-structure route rather than creating a second authorization system.
It may provide:

- a Battle Structure section with approved participation-backed atomic units;
- explicit atomic-unit creation only from the Event's accepted
  EventParticipations;
- group creation/edit/delete and group Commander selection using existing
  supported fields;
- tree rows with group/unit distinction, indentation/connectors, and clear
  manager actions;
- drag handle plus valid-drop feedback as an enhancement over server mutations;
- `Move to...` or equivalent keyboard/non-drag fallback;
- server-rejection recovery and no authoritative optimistic mutation;
- no raw database identifiers in the user-facing form.

Atomic-unit name, represented Unit, Audit type, and side controls may not be
added to the form until their domain ownership and persistence semantics are
approved. The accepted participation selector must reject requested/denied
participations and arbitrary persistent Units server-side.

## Authorization

Public Event and command-structure reads are unauthenticated and read-only.
Every protected command-group mutation uses Events-owned
`canManageEvent(userId, eventId)`, which means Event owner or explicitly
authorized Event manager. Participation does not grant Event authority;
persistent Unit ownership, persistent Unit Commander status, and
`SUBMIT_AUDITS` do not authorize command-group editing. Existing server actions
remain authoritative. Any new atomic-unit Event-manager action must explicitly
choose whether it remains Audits `canSubmitAudit` authority or requires a
separate approved Event-manager mutation boundary; UI visibility cannot decide.

## Architecture Questions and Answers

1. Two teams/sides? **No persisted model.**
2. If yes, how? **Not applicable.**
3. Durable change? **New approved side assignment/name semantics and schema/read/mutation ownership.**
4. Victory/draw/defeat? **No authoritative model.**
5. Atomic units tied to EventParticipation? **Yes, required foreign key; approved participation only.**
6. Atomic unit from Event management? **No; current creation is Audits `/audits` and uses `canSubmitAudit`.**
7. Command groups persisted? **Yes, Audits-owned.**
8. Nested groups? **Yes.**
9. Move/reparent? **Yes, server-side group reparenting and attach/detach; atomic units move through group membership operations.**
10. Group Commander persisted? **Yes, Player foreign key.**
11. Atomic Commander source? **Finalized Audit role assignment, not a separate atomic-unit field.**
12. Public command hierarchy read? **Yes, `getPublicEventCommandStructure`.**
13. Public effective finalized Audit read by Event? **Source operation accepts Event filters, but no Event-page-ready public DTO/Statistics reader exists.**
14. Historical Rank? **No.**
15. Display alias? **Only UnitMembership-local alias where an approved public roster read supplies it; otherwise stable PlayerID.**
16. Duplicate aggregation safe? **Only if Statistics-owned raw aggregation is reused; Event UI must not calculate it.**
17. `canManageEvent`? **Owner or explicit EventAuthorizedUser; owner alone administers manager rows.**
18. Draft visibility? **Private; public state is pending until effective finalized results exist.**

## Decomposition Recommendation

This is not one implementation ticket under current repository truth.

1. **Architecture decision ticket:** resolve whether Events support two durable
   sides and how side names/assignment/inheritance work; separately decide
   whether Event outcome is in scope. Create an ADR, and a BCR if the decision
   adds or changes module contracts. Do not bundle historical Rank into the UI
   decision.
2. **Command structure presentation/editor ticket:** after side decision (or
   with sides explicitly deferred), integrate the existing public tree into the
   Event page, modernize the manager editor, add accessible move fallback and
   optional drag/drop, and implement only approved atomic-unit workflow fields.
3. **Event Battle Statistics read/presentation ticket:** after Statistics
   boundary approval, add the minimum Event-filtered read operation/DTO or use
   an approved existing seam, then present finalized atomic-unit rows and
   disclosures without duplicating aggregation. Keep group statistics
   organizational-only unless a safe group reader exists.
4. **Separate future decision/ticket only if product requires it:** historical
   Rank-at-Event and authoritative victory/outcome semantics. These are not
   implementation prerequisites for a minimal command tree with pending
   results.

The implementation tickets should remain blocked until the architecture owner
resolves side semantics, the Statistics read boundary, and the authority for
Event-manager atomic-unit creation. If sides and outcome are explicitly
deferred, command-tree presentation and finalized-result integration can still
be separate implementation tickets, with no two-column or outcome claims.

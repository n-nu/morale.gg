# Ticket: Event Ownership and Management Authorization Boundary

## Implementation Owner

Lead

## Objective

Establish the shared MVP architecture, persistence, and server-side capability
boundary for User-owned Events. An authenticated User with any currently
effective Unit `MANAGE_EVENTS` permission may create an Event and becomes its
owner. After creation, only that owner and Users explicitly authorized for the
Event may manage it; Unit authority and Event participation grant no
post-creation Event-management authority.

This boundary must unblock a later Developer B vertical slice for Event
management, authorized-user administration, participation approval/denial,
management UI, and tests without implementing those workflows here.

## RED Reason and Approval Gate

This ticket changes Event ownership, shared Prisma relationships and
cardinality, authorization semantics, cross-module dependencies, public
server-side capabilities, and registry truth. It is RED and may not enter
implementation until the human architectural owner approves both required
decision records:

- an ADR that establishes standalone User-owned Events and amends the
  Event-specific interpretation in ADR-20260915-002. That ADR currently
  describes Unit-scoped `MANAGE_EVENTS` as Event-administration authority;
  under this ticket it supplies creation eligibility only and never authority
  over another User's existing Event;
- a BCR and minimal contract allowing Events to consume a Units-owned semantic
  creation-eligibility decision without exposing `PermissionGrant`, scopes,
  hierarchy records, delegation lineage, revocation data, memberships, or
  other authority persistence.

The approved product decisions in this ticket are requirements for those
records, not permission for an agent to approve or implement the RED change.
ADR-20260921-004 and BCR-20260921-002 were explicitly approved by the human
architectural owner on 2026-09-21. The
`events-units-event-creation-authorization` contract is stable. The RED gate
is satisfied. The human owner authorized implementation on 2026-09-21, and
this ticket is now `ACTIVE`.

## Main Success Scenario

1. An authenticated User asks to create a future Event.
2. The server verifies through the Units authority boundary that the User has
   a currently effective `MANAGE_EVENTS` permission somewhere.
3. The Event is created without a Unit ownership/authority relationship, and
   the authenticated creator is persisted as `ownerUserId`.
4. The owner explicitly authorizes another existing website User to manage
   that Event.
5. Event management checks allow the owner and explicitly authorized User,
   deny every other User, and expose no Unit authority internals.
6. Only the owner can administer the Event's authorized-user list.

## Product Invariants

### Event ownership

- An Event is a standalone object owned by exactly one authenticated website
  User through `ownerUserId`.
- The authenticated creator becomes the owner; a client-supplied owner ID is
  never authoritative.
- Event ownership is not held by a Unit. No `organizingUnitId`,
  `authorityUnitId`, or equivalent Event-to-Unit authority relationship may be
  added for MVP.
- The Unit or grant that establishes creation eligibility is not stored on the
  Event and grants no Event authority after creation.
- Ownership transfer is unsupported in MVP.

### Explicit Event authorization

- Events owns an explicit Event-to-User authorization relationship,
  conceptually `EventAuthorizedUser`.
- The relationship identifies the Event, authorized User, User who added the
  authorization, and creation/update timestamps.
- An Event/User pair may be authorized at most once.
- The owner is authorized by ownership and must not require or receive a
  duplicate authorized-user row.
- Only the owner may add or revoke another Event manager.
- An explicitly authorized manager gains ordinary Event-management authority,
  not authority to administer other Event managers.
- An authorized manager may remove only their own authorization if the GREEN
  implementation supports that cleanly; self-removal is optional and may not
  broaden manager-administration authority.

### Event authority

- `MANAGE_EVENTS` is a Unit-authority permission used only to establish Event
  creation eligibility for this MVP boundary.
- Possessing `MANAGE_EVENTS` does not permit management of an Event owned by
  another User.
- An Event is manageable only by its owner or a User explicitly authorized for
  that Event.
- Event authorized-user administration is owner-only.
- Participation by a Unit never grants Event-management authority.
- Event authorization is independent of participating Unit hierarchy and
  RootUnit identity. Units from different RootUnits may participate in the
  same Event.
- All authorization decisions and protected mutations are enforced server-side;
  UI visibility is not an authorization boundary.

## Required Shared Persistence

- Add a required Event owner relationship from `Event.ownerUserId` to the
  Auth.js `User` identity, including reciprocal Prisma relations and indexes
  justified by actual query paths.
- Add an explicit Event-authorized-User relationship with Event, authorized
  User, adding User, timestamps, and uniqueness for the Event/User pair.
- Preserve the rule that the owner has no duplicate authorization row through
  database enforcement where practical and mandatory transactional
  application validation otherwise.
- Choose restrictive or explicit transactional deletion behavior so User or
  Event deletion cannot silently erase ownership or authorization history in
  conflict with repository invariants. Exact referential actions are an
  implementation decision to be recorded in the approved persistence design.
- Provide a forward migration for existing Events. The approved ADR/BCR or
  implementation plan must define how every existing Event receives a real
  owner before `ownerUserId` becomes required. Do not invent a sentinel User,
  infer an owner from a Unit, or deploy an orphaned/nullable final state.

Exact model names, primary-key shape, relation names, indexes, and transaction
structure remain GREEN implementation choices unless they alter these shared
contracts or invariants.

## Required Capability Boundaries

### Event creation eligibility

Provide a server-only semantic capability conceptually equivalent to:

```ts
canCreateEvent(userId: string): Promise<boolean>
```

It returns true only when the User has at least one currently effective
`MANAGE_EVENTS` permission in the Units authority system. Current effectiveness
must retain the existing resolver's fail-closed treatment of missing Users,
malformed hierarchy/RootUnit data, revoked grants, invalid delegation lineage,
and invalid membership/grant state.

Units owns the authority evaluation; Events consumes only the semantic result.
The approved BCR may choose a better name or a minimally reusable semantic
shape, but it must not expose authority persistence or require Events to select
or retain a Unit ID.

### Event management

Provide an Events-owned server-only capability conceptually equivalent to:

```ts
canManageEvent(userId: string, eventId: string): Promise<boolean>
```

It returns true only for the Event owner or a User explicitly authorized for
that Event. Missing Users, missing Events, empty identifiers, and absent
authorization deny safely. Unit permissions, Unit hierarchy, RootUnit
hierarchy, EventParticipation, and participating-Unit authority are not inputs
to this decision.

### Authorized-user administration

Provide an Events-owned owner-only semantic check for authorized-user list
mutations, conceptually `canManageEventAuthorizedUsers(userId, eventId)` or an
equivalent owner check consistent with the final approved architecture. Exact
naming is intentionally left open. It must allow the owner and deny explicitly
authorized managers and all other Users.

Future ordinary Event operations, including editing Event information,
accepting/declining EventParticipation requests, Audit approval/denial, and
other Event-management actions, must consume `canManageEvent` or its approved
equivalent. Those workflows are not deliverables of this ticket.

## Focused Authorization Tests

At minimum verify:

- creation eligibility allows a User with one valid effective
  `MANAGE_EVENTS` grant and denies no grant, revoked grant, invalid delegation,
  malformed authority data, missing User, and empty identity;
- Event creation persists the authenticated creator as owner and cannot accept
  a forged owner or retain the qualifying Unit/grant;
- owner management is allowed; explicit manager management is allowed;
  unrelated User management is denied;
- a User with `MANAGE_EVENTS` but no ownership/explicit authorization is
  denied management of another User's Event;
- participating-Unit authority, including authority from a different RootUnit,
  neither grants nor blocks Event management;
- only the owner may add/revoke managers; duplicate authorization and adding
  the owner are rejected; revoked authorization stops management;
- missing Event/User and malformed identifiers fail closed;
- concurrent duplicate authorization attempts preserve uniqueness; and
- existing Units resolver and EventParticipation request tests remain green.

If manager self-removal is implemented, test that it affects only the actor's
own authorization and cannot remove the owner or another manager.

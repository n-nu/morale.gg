# Ticket: EventParticipation Persistence and Unit Participation Request Workflow

## Implementation Owner

Lead

## Objective

Establish the EventParticipation persistence model and the server-side Unit participation request workflow required for future Audits. This ticket owns the minimal EventParticipation lifecycle required to represent a Unit's request for an Event and the resulting request state, while intentionally deferring Event-management approval authority.

## Main Success Scenario

1. An authenticated User requests participation for an existing Unit at an existing Event.
2. The server validates the Event and Unit, then calls `canRequestEventParticipation(userId, unitId)`.
3. The authorization check allows the request, and a single `EventParticipation` row is created in the `REQUESTED` state.
4. The persisted record is queryable by Event and by Unit, and its status is visible only through server-side read helpers.
5. Invalid requests, duplicate requests, and unauthorized requests are denied without inventing any Event-management authorization.

## Assumptions

| Statement | Status | Evidence or decision |
|---|---|---|
| EventParticipation is a one-to-one Unit/Event relationship with lifecycle state. | CONFIRMED | Architecture and ticket requirements define a single request/approval object per Unit/Event pair. |
| `canRequestEventParticipation(userId, unitId)` is the only authorization seam used. | CONFIRMED | Ticket 13 and Units module capability boundary. |
| Event-manager approval remains intentionally deferred. | CONFIRMED | ADR and ticket requirements. |
| Events may only accept participation requests while they remain eligible. | ACCEPTED-AS-LIMITATION | Event creation rule forbids past scheduling; participation requests are rejected for ineligible past Events without redefining Event semantics. |

## Main Success Scenario

1. An authorized User opens an eligible atomic Event unit.
2. The server creates a draft owned by the authenticated website User.
3. The User pastes raw `playerId,kills,deaths,assists` rows and reviews the
   parsed virtual leaderboard.
4. The User selects Unit type, assigns required roles, enters Tickets, Flag
   Captures, Flag Losses, and Stars, then submits.
5. The server validates and finalizes the Audit atomically; public readers can
   view finalized results while drafts remain private.

## Required Implementation

### Lifecycle and authority

Use a lifecycle equivalent to `DRAFT -> FINAL`; exact terminal naming is GREEN.
Creation and finalization require authenticated session identity,
`canSubmitAudit` for the represented Unit, and approved atomic-unit context.
Only the creator may edit an existing draft. Submission validates the complete
payload and automatically finalizes it. Finalized Audits, K/D/A rows, roles,
type, and Unit statistics cannot be edited or deleted. Enforce zero/one Audit
per atomic unit.

### Parser and Player resolution

Parse repeated `playerId,kills,deaths,assists` rows. Reject malformed structure,
invalid PlayerID, invalid numeric values, duplicate PlayerIDs within one Audit,
and incomplete final submissions. Resolve every Player through the Players
contract; never create UnitMembership or aliases. Mercenaries and
never-rostered Players are valid.

### Results, types, and roles

Persist one historical type: Regular, Rifles, Cavalry, or Artillery, without
moving type to persistent Unit. Persist finalized Tickets, Flag Captures, Flag
Losses, and Stars. Default role is implicit. Every type has exactly one
Commander; Regular additionally has exactly one Flag Bearer. The same Player
may hold Commander and Flag Bearer in Regular. Roles reference Players already
present in the Audit.

### Reads and future compatibility

Provide private draft management and public finalized result reads without
automatically exposing submitting Auth.js User identity. Preserve PlayerResult
-> Player/Audit, Commander role -> Player/Audit, Audit -> atomic unit ->
EventParticipation -> Event/Unit, result -> Unit type, and all source data
needed for future Ranker and Commander observations. Do not calculate
statistics or attendance; retain mandatory atomic-unit metadata for later
Unit/Event attendance derivation.

# Ticket: Application Presentation Harmonization and Unit UX

## Objective

Bring the public and management-facing morale.gg pages into one coherent visual
language based on the existing Events experience. Simplify Statistics through
progressive disclosure and redesign the Units directory, Unit hierarchy, and
roster presentation. Preserve all route identities and domain behavior.

## Main Success Scenario

1. A visitor moves between Events, Players, Units, Statistics, and public Audit
   results and recognizes one consistent application presentation.
2. A visitor can scan the important Player Statistics summary, then expand
   secondary Ranker, Commander, General, and Unit-type detail when needed.
3. A visitor can browse the Unit directory as an expandable organization tree,
   understand a Unit's descendant structure, and scan its roster as a compact
   data table on desktop and mobile.
4. Existing management and authentication actions retain their current
   authorization and behavior while adopting the same visual conventions.

## Requirements

- Derive shared page width, typography, surfaces, separators, links, actions,
  focus states, and muted text from Events; avoid a second visual system.
- Keep Events behavior and visual design authoritative; change its pages only
  when needed to consume a genuinely shared convention.
- Reuse and visually refactor Ticket 29/30 Statistics components. Do not change
  calculation, window, type-partition, attendance, or ratio semantics.
- Player Statistics must lead with identity, selected window, and compact
  Ranker values; secondary metrics and Commander/General detail use accessible
  disclosure. Keep type populations separate and do not add explanatory prose
  to primary surfaces.
- Units directory keeps working hierarchy semantics and adds compact rows,
  clear depth, direct-child counts, accessible expansion, and Expand all /
  Collapse all actions.
- Unit detail uses the existing Unit hierarchy as a visual descendant tree,
  adapting to narrow screens without page-level horizontal overflow.
- Roster columns may use only existing Player/Unit roster data and approved
  public Statistics readers. There is no Unit-scoped Player-combat reader:
  any displayed combat data must be explicitly labeled as overall Player data
  for the selected window and retain type partitions. Attendance may use only
  the existing Player + Unit reader. Do not add or imply Unit-scoped combat
  semantics, a new contract, or a new Statistics reader.
- Keep forms, empty/error states, auth, admin, Event, and Audit actions
  functional and server authorization unchanged.
- Do not change route identities, database schema, migrations, domain
  contracts, Player identity, hierarchy, Event/Audit ownership, or persistence.
- The supplied materials contain no reference image; use the textual directory
  structure in the request as the structural reference, with no invented art.

### Result

Implemented an Events-derived shared page shell, typography, separators,
navigation and action styling. Statistics now use compact summaries and
accessible progressive disclosure. The Units directory is an expandable
organizational table, Unit detail presents a nested connector tree, and the
roster is a compact responsive data table. Events behavior remains unchanged.

Roster Statistics available through approved readers are overall Player Ranker
K/D/A/KDR and distinct Events for the selected 14-day/30-day/all-time window,
partitioned by Regular/Rifles/Cavalry/Artillery, plus Player + Unit attendance.
Combat data is explicitly labeled overall, not Unit-scoped. No approved
Unit-scoped Player combat reader, membership alias, or role field exists, so
none was invented.

The provided attachments included no reference image; the directory follows
the textual hierarchy wireframe. The one full-suite failure is the existing
calendar-grid React/Next runner mismatch recorded above.

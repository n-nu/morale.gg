# Ticket: Authority Bootstrap and Constraint Tightening

## Implementation Owner

Lead

## Objective

Complete the final-state authority invariants after authority persistence
expand/backfill succeeds: a trusted website administrator assigns existing
Auth.js Users as Commanders, creates matching level-0 memberships atomically,
and activates required Commander and RootUnit consistency constraints.

## RED Reason

This ticket activates required Unit authority invariants and uses the bounded
server-only website-administrator capability approved by ADR-20260915-003.
Authority persistence and Commander rules are approved by ADR-20260915-002.

## Dependency

TKT-20260920-000011-001 must be completed. Every legacy Unit must have an
operator-approved mapping to an existing Auth.js User before the contract
migration can make `commanderUserId` required.

## In Scope

- trusted server-side bootstrap operation limited to RootUnit designation,
  initial RootUnit owner/Commander assignment, and legacy Commander backfill;
- atomic Commander plus level-0 AuthorizedUserMembership assignment;
- required `Unit.commanderUserId` constraint and deferred Commander/level-0
  consistency trigger activation;
- final RootUnit boundary validation and rollback-safe constraint tightening;
- persistence-level tests and migration validation.

## Explicitly Out of Scope

- generalized RBAC, SiteAdmin persistence, permission evaluator/capability
  engine, non-bootstrap delegation workflows, management UI, structural CRUD,
  Event/Roster/Audit authorization, and contracts.

## Acceptance Criteria

- [x] Only an authenticated existing User recognized by the ADR-003 website
  administrator capability can execute bootstrap assignment.
- [x] Every Unit has exactly one non-null Commander.
- [x] Every Commander has exactly one matching authority-level-0 membership.
- [x] No non-Commander membership can remain at level 0.
- [x] Commander replacement and level-0 membership changes commit or roll
  back together.
- [x] RootUnit owner resolves only through its designated Unit Commander.
- [x] Required constraints are activated only after the complete legacy mapping
  is validated.
- [x] No SiteAdmin model, provider-ID authority, email authority, or RBAC is
  introduced.
- [x] Lint, type-check, build, db validation, Prisma generation, and migration
  validation pass.

## Verification

- Command/check: configured PostgreSQL migration deployment/status, atomic
  bootstrap transaction tests, direct invalid-state rejection tests, `npm run
  db:generate`, `npm run db:validate`, `npm run lint`, `npm run type-check`,
  and `npm run build`.
- Expected result: all Units satisfy the final Commander and RootUnit
  invariants; failed bootstrap leaves transition data intact.
- Actual result: PASS. The approved Commander mapping was committed atomically,
  the final contract migration applied, and all static/database validations
  passed. Public routes `/`, `/units`, `/units/root-morale-gg`, and `/events`
  rendered successfully.

- Command/check: transaction-scoped final-state persistence verification.
- Expected result: invalid Commander and level-0 states reject at commit while
  valid matching state, non-Commander level >= 1 memberships, and existing
  grant lineage remain valid.
- Actual result: PASS for the available database cases: non-null Commander,
  exact matching level-0 membership, no Commander grants, NULL Commander
  rejection, duplicate level-0 rejection, RootUnit invariants, invalid
  delegation FK, and revocation lineage preservation. Alternate-user mismatch
  and non-Commander membership cases were not executable because the database
  contains only the approved Auth.js User and no synthetic Users were created.

## Rollback and Risk Notes

- Abort before contract migration if any Unit lacks an approved existing User.
- Preserve the expand/backfill schema and public Unit reads if bootstrap cannot
  complete.
- Do not remove Users, Units, memberships, grants, or RootUnit records through
  rollback automation.

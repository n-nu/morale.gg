# Ticket: Unit Management Surface Modernization and Access Presentation

## Objective

Modernize the Units-owned Unit Management page so Rank and Medal catalogs,
Unit image management, and Unit-scoped authorized-user administration are
compact, scannable, and consistent with the Events-derived morale.gg visual
language. Preserve all existing Unit, RootUnit, membership, permission,
hierarchy, and server-authorization semantics. This ticket is planning and
implementation authorization for the Units module only; it does not introduce
a second authorization system or binary media storage.

## Main Success Scenario

1. A permitted Unit administrator opens `/units/[unitId]/manage` and sees a
   compact information architecture with profile/image, organization,
   structure, and access concerns easy to scan.
2. The RootUnit owner can scan existing Rank and Medal definitions, then add,
   edit, reorder where already supported, or remove a definition through a
   compact row/list interaction or disclosure/dialog without a permanently
   expanded form for every item.
3. A user with applicable `MANAGE_UNIT` authority can preview the Unit image,
   set or replace its existing image reference, or clear it; the public Unit
   surfaces continue to show the resulting image consistently.
4. A user with effective `MANAGE_AUTHORIZED_USERS` authority can add an
   existing website account, inspect its active Unit membership and grants,
   update permitted authority/grants, or end access. The server rejects any
   operation outside the actor's authority, scope, hierarchy, or Commander
   constraints.

## Current-State Findings

- The Units management route is `src/app/units/[unitId]/manage/page.tsx` and
  already composes Unit profile, authorized-user, hierarchy, and RootUnit
  catalog surfaces.
- `src/modules/units/components/management.tsx` currently renders Rank and
  Medal create forms plus a full edit form inside every catalog list item. Rank
  rows expose only name, description, and `sortOrder`; no abbreviation or rank
  image field exists. Medal rows expose name, description, and existing
  `imageRef`; no new Medal properties are approved.
- Rank and Medal definitions are RootUnit-scoped. Only the current designated
  RootUnit Commander's `canManageRootSettings` capability authorizes catalog
  CRUD. Commander status does not become a general Unit permission.
- Unit persistence already has nullable `Unit.imageRef`, and validation accepts
  only a safe site path or HTTPS URL. There is no upload, object-storage,
  shared-asset, or invitation-media architecture. Public Unit table/tree and
  detail surfaces already render `imageRef`.
- `AuthorizedUserMembership` already associates an Auth.js `User` with a Unit,
  stores an authority level, and preserves ended membership periods. A partial
  active-membership uniqueness rule prevents more than one active User/Unit
  period. The current Commander is the protected level-0 membership.
- `PermissionGrant` already stores the fixed Unit permission enum, scope,
  delegation lineage, creation, and revocation. The seven existing
  permissions are `MANAGE_UNIT`, `MANAGE_STRUCTURE`, `MANAGE_ROSTER`,
  `REQUEST_EVENT_PARTICIPATION`, `MANAGE_EVENTS`, `SUBMIT_AUDITS`, and
  `MANAGE_AUTHORIZED_USERS`.
- Current authorized-user entry uses an existing website-account email; the
  target account must have signed in once. No separate invitation flow is
  required or proposed.

## Proposed Unit Management Information Architecture

Keep the existing route and Units ownership. Reorganize the page into compact
sections, tabs, or accessible disclosures according to existing application
conventions:

- **Overview:** Unit identity, basic profile configuration, and Unit image.
- **Organization:** parent/root context and organization settings only where
  the current operation authority permits them.
- **Roster:** retain links or existing entry points; do not move roster
  persistence or mutation ownership from Players.
- **Structure:** Rank Structure and Medals as compact RootUnit catalog
  surfaces, without duplicating catalog semantics in UI code.
- **Access:** Authorized Users and their existing Unit-scoped permission
  grants.
- **Danger/lifecycle:** retain currently supported structural/destructive
  actions and their existing safeguards.

The implementation may choose tabs, compact sections, or disclosures after
checking current Events-derived conventions. It must not create a second
management shell or hide critical errors, identity, or navigation behind an
inaccessible disclosure.

## Rank Structure Redesign

- Replace the current repeated large edit forms with a compact table/list or
  equivalent dense rows.
- Show the existing Rank name, description only when useful in the compact
  state, and `sortOrder`/hierarchy position.
- Do not add abbreviation, short label, rank image, promotion, assignment, or
  inheritance fields; none exists in the current Rank model.
- Provide concise add, edit, delete, and ordering controls using the existing
  Rank CRUD operations. Detailed editing belongs in inline editing, a compact
  disclosure row, or a modal/dialog.
- Preserve RootUnit scoping, duplicate-name validation, ordering semantics,
  and owner-only server enforcement.
- Provide a clear compact empty state and keep the add-rank action available.

## Medal Redesign

- Present existing Medal definitions as a compact table/list with image/icon
  preview when `imageRef` exists, name, and concise supported metadata.
- Move detailed name, description, and image-reference editing behind an
  inline/disclosure/dialog interaction rather than rendering every form
  permanently.
- Provide compact add, edit, and remove actions and a clear empty state.
- Preserve the existing RootUnit-owned fields and validation. Do not invent
  award history, Player assignment, revocation, statistics, or other Medal
  properties.

## Unit Image Behavior

- Reuse the existing nullable `Unit.imageRef` field and
  `validateImageReference` behavior. Treat the value as a validated site path
  or HTTPS URL reference, not as an uploaded file.
- Add a compact Overview control with current image preview, an add/change
  action, and a clear/remove action that resets the reference to empty/null.
- Show a useful empty state when no reference exists and preserve the existing
  public Unit image rendering dimensions/behavior unless a presentation-only
  adjustment is required for consistency.
- Authorize image changes with the existing `MANAGE_UNIT` semantics and keep
  identity resolution and mutation enforcement server-side.
- Do not add a media table, upload endpoint, object storage, third-party asset
  service, or new image contract. A future binary-upload request requires a
  separate RED architecture decision.

## Unit-Authorized-User Behavior

- Keep the Access section explicitly Unit-scoped and distinct from Auth.js
  identity, organization-wide roles, Player identity, and roster
  `UnitMembership`.
- List active and, where the existing management view exposes them, historical
  membership state with user name/email, authority level, active/ended state,
  and current grants.
- Allow adding an existing application User through the current account lookup
  mechanism; do not imply that roster membership grants management access.
- Allow ending a non-Commander authorized membership through the existing
  history-preserving workflow. Do not hard-delete membership history.
- Make grant state visible per User and provide the existing revoke operation.
- Keep Commander replacement/ownership transfer in its separate workflow. The
  current level-0 Commander membership cannot be changed or ended through
  ordinary authorized-user management.
- Preserve the existing error/notice behavior for missing accounts,
  duplicate active memberships, ended memberships, stale rows, and rejected
  authority changes.

## Permission Behavior

- Render only the existing `Permission` values and valid scope choices. Do not
  invent checkbox labels or capabilities for UI convenience.
- For ordinary permissions, preserve `SELF`, `SELF_AND_CHILDREN`, and
  `SELF_AND_DESCENDANTS`; preserve the null structural-anchor semantics for
  `MANAGE_STRUCTURE`.
- Show active/revoked state and scope clearly enough for a user to understand
  effective management coverage without implementing a second resolver in
  client code.
- Use the existing grant and delegation workflows for grant/revoke actions.
  A delegated user may grant only the same permission with a strictly narrower
  supported scope, or a valid descendant structural anchor, according to the
  existing resolver.
- Preserve additive grants, retained revocation/delegation history, and
  fail-closed behavior for ended memberships or invalid lineage.

## Authorization Rules

- `MANAGE_UNIT` authorizes Unit profile/image changes; the current RootUnit
  owner-only `canManageRootSettings` capability authorizes Rank/Medal catalog
  operations. Neither capability may be broadened by UI visibility.
- Adding, changing, or ending another authorized User and granting/revoking
  their permissions requires the existing effective
  `MANAGE_AUTHORIZED_USERS` authority plus its target coverage, authority-level,
  scope, hierarchy, delegation, and transaction checks.
- Commander/owner identity does not automatically grant ordinary operational
  permissions. Organization/bootstrap administrator authority remains bounded
  to its approved RootUnit operations.
- Server-side workflows remain authoritative for every mutation. Unauthorized
  controls must not be presented as usable actions, and direct requests must
  still be rejected server-side.
- Preserve RootUnit isolation, hierarchy semantics, Player/roster separation,
  and all existing structural deletion protections.
- Do not add a final-administrator, self-removal, or lockout rule unless the
  existing workflow/architecture explicitly supports it. The current protected
  level-0 Commander rule and authority-level/delegation checks are mandatory.

## Responsive Expectations

Validate the management surface around 390px, 768px, and 1440px. On narrow
screens, catalog tables may stack rows or scroll within their own bounded
container; permission controls and image actions must remain usable, labels
must fit, and no body-level horizontal overflow may be introduced. Add/edit
interactions must remain practical at narrow widths and must not overlap
identity, status, errors, or destructive actions.

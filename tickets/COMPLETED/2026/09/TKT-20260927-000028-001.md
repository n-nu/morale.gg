# Ticket: MVP Statistics Presentation and Public Results Integration Plan

## Objective

Define the public MVP presentation and navigation plan for the completed
Statistics query/read services. This ticket is planning and UX integration only.
It does not implement pages, components, routes, leaderboards, or new metric
semantics.

Statistics remains the only owner of derived metric semantics. Presentation
consumes Statistics-owned public readers and DTOs; it must not recalculate
metrics, query private Audit/Player/Unit persistence, reinterpret attendance,
merge Unit-type populations, persist derived values, or expose authorization
internals.

## Main Success Scenario

1. A visitor can identify the public Player, Unit, Event, Audit/results, and
   Statistics destinations from the existing application navigation.
2. A future implementation can present Player and Unit Statistics through the
   existing server-side application pattern using the approved Statistics
   readers, one shared 14-day/30-day/all-time window selector, explicit
   type-partitioned sections, and source-history links.
3. Users can distinguish direct, organizational, and equal-Unit-weight Unit
   perspectives; understand attendance pending/no-obligation states; and trace
   results to relevant Events and finalized Audits where existing public
   identifiers permit it.
4. The implementation can be split into small reviewable tickets without
   changing approved Statistics ownership or metric semantics.

## Architecture / Implementation Review

This is a GREEN planning outcome. The existing Statistics module already
exposes public query-time readers for Ranker, Commander, General, Direct Unit
Performance, Organizational Unit Performance, Average Unit Performance, and
Player + Unit attendance. Existing async App Router Server Components can call
these server-side readers directly. No new module, HTTP API, source contract,
schema, migration, cache, materialized view, or persistence seam is needed.

Future route/UI work is expected to be YELLOW because it adds public routes and
navigation, but it remains within existing boundaries. A change to metric
meaning, source ownership, private persistence access, or a new event-scoped
statistics contract would be RED and requires separate approval.

## Information Architecture

### Player Statistics

Player identity is the stable game PlayerID. A known Unit-local alias may be
shown when safely exposed by the existing Player/roster architecture; there is
no invented global canonical name. If no readable alias exists, show the
PlayerID cleanly. A profile does not require current roster membership, so
mercenaries and never-rostered Players remain discoverable.

The Player page has one shared window control, defaulting to 14 Days, and these
sections:

- Ranker: Kills, Deaths, Assists, KDR, (K+A)/D, average Kills/Deaths/Assists
  per Audit appearance, and distinct Events participated.
- Commander: shown only when observations exist; battles commanded, total
  K/D/A, pooled KDR, Tickets, Flag Captures, Flag Losses, Stars, averages for
  those measures, and average Player count. Persistent Unit Commander status
  is irrelevant.
- General: shown only for qualifying command-group observations; qualifying
  groups commanded, distinct Events commanded, total atomic units commanded,
  and Regular/Rifles/Cavalry/Artillery unit counts. Combat/result performance
  remains separate by Unit type; no mixed-type General KDR is shown.

A Player may have Ranker without Commander, Commander without General, or any
other valid partial combination. Sections with no observations use an explicit
state rather than rows of zeros.

### Unit Statistics

Unit pages use a selected persistent Unit and the shared window control. The
three perspectives are visibly and textually distinct:

- Direct Performance: observations directly representing the selected Unit.
- Organizational Performance: the selected Unit plus all descendants, pooled
  from raw observations.
- Average Unit Performance: equal-Unit-weight averages for qualifying Units;
  averaged KDR is not displayed.

Applicable outputs preserve Regular, Rifles, Cavalry, and Artillery partitions.
A Unit with no direct observations but descendant observations must show the
empty Direct state while still showing available Organizational results.

### Attendance

Attendance is exposed for a Player + Unit view, with optional Unit aggregate
summaries only when the existing Statistics service supports them. Show
obligations, present, absent, pending, and resolved attendance percentage.
Pending never counts as absent. With zero obligations, show “No attendance
requirement” or “Not applicable”. With obligations greater than zero and zero
resolved observations, show “Pending” / “No resolved attendance yet”, not 0%.
No private roster machinery or authorization data is displayed.

## Presentation Rules

### Window selector

Every applicable Statistics section uses the same keyboard-accessible control
with 14 Days, 30 Days, and All Time. The default is 14 Days. Changing it
updates the current Statistics view without changing metric meaning. The
selected value is passed to the Statistics query layer; the UI does not
calculate date boundaries.

### Ratios and Unit types

Use the existing ratio DTO/domain state. When deaths are greater than zero,
show the normal ratio. When deaths are zero, show the approved numerator form,
such as `10 K` and `14 K+A`; never show infinity or fabricate a denominator.

Regular, Rifles, Cavalry, and Artillery are separate populations wherever the
Statistics DTO supplies the partition. Mixed types must not be merged for
combat ratios, averages, or a General KDR.

### Traceability

Use lightweight public links, not historical charts: Player statistics to
relevant Event and finalized Audit history; Commander/General observations to
Event and Audit or command structure; and Unit statistics to Event/Audit
history. Links may only use identifiers and destinations already exposed by
public contracts and pages. The existing `/audits` page is management-oriented,
so it must not become a Statistics source or an implicit authorization surface.
Event-detail “Battle statistics” replacement is deferred because current
Statistics readers are not event-scoped and a new event-scoped seam would need
separate design approval.

## Navigation Impact

Add an active global `Statistics` entry pointing to `/statistics`. Keep existing
Players, Units, Events, and public result/history destinations reachable without
duplicating them. The current `Leaderboards` “Coming soon” item remains deferred
until ordering and discovery requirements are settled; it is not silently
converted into a score-based feature. Player search remains the entry to Player
profiles, and Unit directory links remain the entry to Unit statistics.

## Leaderboard / Discovery Decision

Include only simple discovery in the MVP integration: a Statistics landing
route, links from Player and Unit directories, and optional lists ordered by an
already-defined public raw metric where a product owner has approved the
ordering. Do not invent a composite score or ranking formula. Percentiles,
ELO, weighted scores, predictive ranking, premium filtering, advanced sorting,
and historical charts are excluded.

A dedicated leaderboard ticket is not required for the initial split. Basic
Ranker/Commander/General discovery and cross-linking can be included as final
integration/polish in the Player and Unit presentation tickets. If product
needs a separately ordered leaderboard, create a later ticket with explicit
ordering acceptance criteria.

## UI States and Accessibility

Implementations must define semantic loading, no observations, no observations
in the selected window, partial Player sections, no direct Unit observations
with descendant results, no attendance obligation, attendance pending, zero
resolved attendance, invalid Player/Unit, and server/read failure states.
“Loading” is not “zero”; absence of observations is not a zero-valued metric.

Use semantic headings, readable tables/cards, keyboard-accessible window
controls, labels that do not depend on color, and mobile-readable layouts.
The layout must remain usable on narrow/mobile, tablet, and desktop viewports;
responsive work is limited to the Statistics surfaces and does not become a
broad visual redesign.

## Implementation Ticket Decomposition

1. **Player Statistics presentation**: add the Player profile Statistics
   sections, shared window control, Ranker/Commander/General type partitions,
   zero-death display, partial/empty/error states, and Player -> Event/Audit
   links. Use existing `/players/[id]` identity routes and Statistics readers.
2. **Unit Statistics and Attendance presentation**: add Direct,
   Organizational, and Average Unit Performance sections, Unit-type partitions,
   Player + Unit attendance, window control, attendance states, and Unit ->
   Event/Audit links. Reuse Unit directory/detail routes and public identities.
3. **Integration/polish within tickets 1 and 2**: add `/statistics` discovery,
   active global navigation, simple raw-metric discovery only when ordering is
   explicitly approved, responsive layout, and route/presentation tests. Do not
   create a separate leaderboard ticket unless unresolved ordering becomes a
   separately reviewable product decision.

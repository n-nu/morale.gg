# Ticket: Implement Bounded Website-Administrator Identity Capability

## Implementation Owner

Emil Estrada (Authentication/architecture owner).

## Objective

Implement the smallest secure server-side mechanism that recognizes morale.gg
website administrators for only the RootUnit operations accepted in
ADR-20260915-002: create or designate a RootUnit, establish the initial
RootUnit owner/Commander, and transfer RootUnit ownership.

Website-administrator authority is distinct from authentication, `Player`,
Unit Commander status, AuthorizedUserMembership, and Unit-scoped permission
grants.

## RED Decision Record

Human architectural approval accepted ADR-20260915-003 on 2026-09-16. It
selects the bootstrap identity key, configuration mechanism, server-side
identity-resolution requirement, and deferral of regular SiteAdmin persistence.
The approved decision is the authorization for this ticket to proceed through
the normal `READY -> ACTIVE` implementation workflow.

No BCR is currently required: this work creates no contract and has no
implemented consumer. Do not create a migration, SiteAdmin persistence,
site-admin UI, or a RootUnit operation under this ticket.

## Scope Owner

```yaml
scope_owner:
```

Rationale: this establishes shared website-level authorization identity at the

## Main Success Scenario

1. A trusted bootstrap administrator authenticates through the normal Auth.js
   Google flow, creating an Auth.js User when necessary.
2. A trusted deployer configures that User's stable ID in central bootstrap
   deployment configuration.
3. A future server-side RootUnit bootstrap operation resolves the authenticated
   User and calls the centralized website-administrator capability.
4. The capability recognizes the configured User as a website administrator.
5. The operation proceeds only when its separate RootUnit-specific conditions
   also pass.
6. An authenticated but unconfigured User is denied; no client value can alter
   that result.

## Approved-Only Design Target

After ADR-20260915-003 is accepted, implement only:

- server-only parsing of `WEBSITE_ADMIN_USER_IDS` as a comma-separated stable
  Auth.js `User.id` allowlist;
- a centralized server-only semantic capability such as `isWebsiteAdmin(user)`
  that returns a boolean without leaking configuration implementation details;
- reliable resolution of the authenticated Auth.js User ID by protected
  server-side code, without exposing User ID to client session state solely for
  authorization;
- tests for configured and unconfigured authenticated Users; missing User ID;
  missing, malformed, duplicate, and whitespace configuration entries; and
  proof that client-provided identity data does not determine authority;
- concise deployment documentation for configuration and the trusted flow to
  obtain a User ID after first sign-in.

No RootUnit operation is implemented by this ticket. A later governed ticket
will consume the capability and independently enforce its RootUnit and
Commander requirements.

## Regular Site Administrators

Regular database-managed SiteAdmins are deferred: MVP has no management panel,
add/remove operation, or persistence consumer, and bootstrap configuration
must continue to work with no database-managed administrator.

When a future approved ticket adds regular SiteAdmins, it must key them to
authenticated Auth.js Users; preserve one boolean result for Users that qualify
through both sources; prohibit any application path from changing bootstrap
configuration; and record immutable add/remove audit events containing actor,
target, timestamp, and operation. It must not introduce roles, tiers,
per-admin permissions, or generalized RBAC.

## Explicitly Out of Scope

- administrator-management UI, panel, dashboard, add/remove endpoint, and
  regular SiteAdmin persistence or migration;
- generalized roles, RBAC, tiers, and per-administrator permissions;
- Unit authority, RootUnit/Commander persistence, and RootUnit operations;
- every Unit-scoped permission, including `MANAGE_UNIT`, `MANAGE_STRUCTURE`,
  `MANAGE_ROSTER`, `REQUEST_EVENT_PARTICIPATION`, `MANAGE_EVENTS`,
  `SUBMIT_AUDITS`, and `MANAGE_AUTHORIZED_USERS`;
- Events, Audits, Players, and client-side authorization.

  tests were rerun after the correction and passed all 7 tests.

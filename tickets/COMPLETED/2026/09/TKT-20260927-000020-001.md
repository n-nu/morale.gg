# Ticket: Audit Submission, Atomic Event Units, and Event Command Groups

## Objective

Define the approved implementation boundary for the next MVP capability:
Audit Submission, Atomic Event Units, and Event Command Groups. This ticket is
planning and architecture work only. It reconciles the approved product
requirements with current Events, Units, Players, authorization, and Prisma
truth, and prepares the RED decisions and contracts needed before feature
implementation.

The approved implementation owner is the new `audits` module. It owns the
Audit and the Event-scoped historical structures that give an Audit its stable
battlefield context. Events would continue to own Event identity,
EventParticipation, and Event management authority; Units would continue to
own Unit authority and roster authorization; Players would continue to own
Player identity and UnitMembership history.

## Main Success Scenario

1. An approved Event has one or more persistent Units represented by
   `EventParticipation` records.
2. After the Event, an authorized submitter creates one or more manually
   recorded atomic Event units, each linked to exactly one approved
   `EventParticipation` and marked mandatory or optional.
3. The submitter pastes raw `playerId,kills,deaths,assists` rows. The server
   resolves existing Players or creates missing Player identities without
   creating UnitMembership rows.
4. The submitter reviews the virtual player leaderboard, assigns valid Audit
   roles, enters Unit type and Unit statistics, and saves a creator-owned
   draft.
5. Submission validates all invariants and atomically changes the Audit to
   immutable final state. A second Audit for the same atomic Event unit is
   rejected.
6. An Event manager records a strict, non-overlapping command tree over atomic
   Event units and child groups. The represented persistent Unit remains
   descriptive and does not become an authority anchor.
7. Public readers may view finalized Audit and command-group results according
   to the final privacy contract; drafts and management-only data remain
   protected.

## Current Repository Truth

- `src/modules/events/MODULE.md` owns Event identity, Event persistence,
  Event-authorized Users, `canManageEvent`, and EventParticipation review. It
  explicitly excludes Audit lifecycle and statistics and marks new persistent
  Event relationships, Unit/Event coupling, contracts, and changes to
  `canManageEvent` as RED.
- `src/modules/units/MODULE.md` owns Unit identity/hierarchy, authority,
  permission grants, and Unit structural workflows. It explicitly excludes
  Events, EventParticipation, Audits, and statistics. `SUBMIT_AUDITS` exists
  in the Prisma `Permission` enum and Units management UI, but no documented
  `canSubmitAudit` capability or Audit contract exists.
- `src/modules/players/MODULE.md` owns persistent Player identity,
  case-sensitive stable game `Player.playerId`, UnitMembership periods, and
  roster mutations. It explicitly excludes Events and Audits. The approved
  Player contract now permits identity-only Players with nullable legacy
  `name` data and exposes resolve-or-create by game PlayerID.
- The Auth.js `User` is a website identity and is separate from `Player`.
- `EventParticipation` currently has exactly one row per `(eventId, unitId)`;
  its lifecycle is `REQUESTED -> APPROVED` or `REQUESTED -> DENIED`, and
  terminal records are immutable. Only approved participation may support the
  new structures. Its one-per-Event/per-persistent-Unit meaning must remain
  unchanged.
- `Event` is standalone and User-owned. Existing Event management is allowed
  only to its owner or explicitly authorized Event User through
  `canManageEvent`; `MANAGE_EVENTS` supplies creation eligibility only and is
  not existing-Event authority.
- Prisma currently has no Audit, atomic Event-unit, Audit-player-result,
  Audit-role, or Event-command-group models. No current schema assumption
  provides one Audit per EventParticipation, although `BACKLOG.md` and
  `docs/architecture.md` contain an older conceptual one-Audit-per-unit/event
  description that this ticket must explicitly supersede for implementation.
- Current architecture states that submitted Audits are immutable historical
  source data, but exact Audit ownership, persistence, cardinality, role
  constraints, and module boundary remain undecided.
- Unit deletion already rejects EventParticipation history. The approved
  Audit boundary additionally protects atomic-unit, group, and finalized
  Audit history; unfinished creator drafts may be discarded and dependency-free
  empty atomic units may be deleted under Audit authority.

## Approved Domain Decisions

The following are product requirements supplied with this ticket and are not
being re-approved by the planning agent:

- A persistent Unit may produce one or many atomic Event units. Atomic Event
  units are created manually after the Event and each belongs to exactly one
  approved EventParticipation.
- An atomic Event unit has zero or one Audit; the atomic unit is the stable
  battlefield identity and the Audit is its result record.
- The creator owns a draft; only the creator edits it. Submission automatically
  finalizes it, and finalized data is immutable. Rejection/replacement remains
  post-MVP but the design must preserve future transactional replacement.
- Raw rows resolve by stable game PlayerID. Existing Players are reused;
  missing Players are created; no UnitMembership is created from Audit data.
- Mercenaries are valid and need not be rostered in the represented Unit or
  anywhere. Audit result rows reference Player identity, never membership.
- Player display aliases remain UnitMembership-local; a canonical global name
  is not required for Audit creation.
- Every Audit has one historical type: Regular, Rifles, Cavalry, or Artillery.
  The type must not be stored on persistent Unit merely because it is used in
  one Event appearance.
- Every Audit Player is Default unless assigned special roles. Every type has
  exactly one Commander; Regular additionally has exactly one Flag Bearer.
  One Player may hold both Regular special roles.
- Finalized Audits record Tickets, Flag Captures, Flag Losses, and Stars.
- Mandatory status belongs to each atomic Event unit and is not inherited from
  a persistent Unit. Attendance is later calculated per rostered Player,
  persistent Unit, and Event, with at most one obligation per Unit/Event and
  credit from any mandatory atomic Audit for that Unit.
- Event command groups form a strict tree over atomic Event units and child
  groups. Each atomic unit and child group has at most one immediate parent;
  cycles and overlap are forbidden. A group has an Event, descriptive
  represented Unit, Commander Player, and optional parent.
- General eligibility later depends on at least two underlying atomic units,
  regardless of type. Future combat statistics flatten to underlying Audits
  and remain partitionable by Unit type; child-group averages are never
  averaged recursively.

## Approved Module Ownership

### `audits` module (approved)

Own Audit drafts/finalization, atomic Event-unit identity, Audit result rows,
Audit role assignments, Event command groups, mandatory participation metadata,
and Audit/command-group read behavior. It owns the historical relationships
because they exist to preserve battlefield results, not to mutate persistent
Units or EventParticipation.

The module is registered by this amendment and must not copy Unit authority,
Player roster state, or Event management logic.

### Existing Events module

Remains owner of Event identity, EventAuthorizedUser, EventParticipation and
`canManageEvent`. It supplies approved-participation and Event-management
  contracts to Audits. Audits cannot mutate participation.

### Existing Units module

Remains owner of `SUBMIT_AUDITS` authority evaluation and Unit identity. A
  approved server-only `canSubmitAudit(userId, unitId)` capability authorizes
  atomic-unit creation, Audit draft creation, and Audit finalization for that
  Unit, without exposing grants, scopes, hierarchy, or private authority rows.

### Existing Players module

Remains owner of Player identity and UnitMembership. It supplies a minimal
resolve-or-create-by-game-PlayerID operation for the Audit parser. Audit use
  must not grant roster membership or alter aliases. `Player.name` is nullable
  compatibility data, not a canonical-name requirement.

## Proposed Persistence Concepts

Exact table and field names remain GREEN after the RED boundary is approved.
The persistence design must conceptually include:

- **Atomic Event unit:** Event-scoped stable battlefield appearance; exactly
  one approved EventParticipation parent; mandatory flag; historical Unit
  reference for display/aggregation; one-to-many relation to command-group
  ancestry and zero/one Audit.
- **Audit:** one atomic-unit foreign key with database uniqueness; creator
  website User; draft/final lifecycle; created/submitted timestamps; immutable
  final payload; type; Tickets, Flag Captures, Flag Losses, and Stars.
- **Audit Player result:** one persistent Player per Audit at most once, with
  K/D/A. It must allow a Player absent from the represented Unit roster.
- **Audit role assignment:** role records or an equivalent constrained model
  that supports multiple special roles on one Player and validates the exact
  Commander/Flag Bearer cardinalities at finalization.
- **Event command group:** Event-scoped group with descriptive represented
  Unit, Commander Player, optional parent group, and membership edges to child
  atomic units and/or groups. The design must make duplicate parents,
  cycles, and overlapping atomic ancestry rejectable transactionally.
- **Future-stat source shape:** every group path must be flattenable to unique
  underlying atomic units and their Audits, retaining each Audit's Unit type.

Foreign keys and restrictive behavior must protect finalized history. No
current persistent Unit hierarchy, Event ownership, roster membership, or
EventParticipation row may be silently cascaded or rewritten by this model.

## Authorization Boundaries

- **Audit creation/edit/finalization:** authenticated website User plus the
  approved Units `canSubmitAudit(userId, unitId)` capability for the
  represented persistent Unit and the approved EventParticipation context.
  The creator identity is resolved from the server session.
- **Draft ownership:** only the creator may edit or submit that draft. Event
  managers do not automatically edit a draft unless a future approved policy
  says so.
- **Event command-group administration:** use Events' `canManageEvent`, not
  the represented Unit's authority and not `SUBMIT_AUDITS`. Event managers may
  administer groups for that Event; the Unit is descriptive only.
- **Finalized records:** no edit or delete in MVP. Any future correction must
  be a new approved replacement workflow, not in-place mutation.
- **Public reads:** finalized Audit result data and Event command structure are
  public. Drafts and draft-management data are private. The submitting Auth.js
  User identity is not automatically public. Exact DTO/UI shape is GREEN.

## Audit Lifecycle and Parsing

The implementation design should use a two-state MVP lifecycle equivalent to
`DRAFT -> FINAL` or `DRAFT -> APPROVED`, with submission as the only finalizing
transition. Draft writes validate shape but may be incomplete; finalization
validates complete parser output, type, required Unit statistics, roles, and
atomic-unit integrity in one transaction.

The parser accepts the compact repeated `playerId,kills,deaths,assists` form,
rejects malformed rows, invalid numeric values, duplicate PlayerID rows within
one Audit, and invalid identifiers according to the Players boundary. Review
renders a virtual leaderboard from parsed rows before submission. Resolution
must be idempotent and must not create UnitMembership.

## Attendance Data Requirements

The model must retain, per atomic Event unit, the represented persistent Unit,
the Event through approved participation, and explicit mandatory status. It
must support the later query:

`(persistent Unit, Event) -> one obligation when any atomic unit is mandatory`

and credit from any mandatory finalized Audit containing that rostered Player.
Mercenary appearances remain combat participation only unless a separate
rostered Unit obligation is independently satisfied. A Player rostered in two
Units has separate Unit-specific obligations. Attendance calculation itself is
out of scope.

## Command-Group Invariants

- Every group and atomic unit belongs to one Event.
- A group Commander is a persistent Player identity, not a website User or
  persistent Unit Commander substitution.
- A child group has at most one parent group; an atomic unit has at most one
  immediate group parent.
- A group cannot be its own ancestor. A transaction must reject cycles.
- An atomic unit cannot be reachable through two immediate parents or through
  overlapping memberships that double-count it in one tree.
- Membership edges cannot cross Events.
- A represented Unit does not imply group authority, mutate its hierarchy, or
  automatically generate groups.
- Future General observations flatten unique atomic units and partition result
  values by Regular/Rifles/Cavalry/Artillery.

## History, Deletion, and Immutability

- Approved EventParticipation is not redefined as an atomic unit and remains
  the one persistent Unit/Event participation record.
- Atomic units, groups, and Audit rows must not be silently deleted as part of
  persistent Unit, Player, or Event cleanup once historical references exist.
- Creator-owned unfinished drafts may be discarded. An atomic Event unit with
  no finalized Audit and no command-group dependency may be deleted under
  proper Audit authority. Neither operation may erase finalized history.
- Finalized Audits and their player results/roles are immutable in the MVP.
- Player rows referenced by Audits remain protected by existing Players
  foreign-key/history rules. Ending UnitMembership never removes Audit credit.
- Event command groups may be edited, restructured, or deleted by Event
  managers, but those changes never mutate atomic units or finalized Audits.
- Event deletion must reject any Event with atomic units, groups, or Audits;
  this updates the current backlog rule that only mentions Audits.
- Persistent Unit deletion must reject any atomic-unit or command-group
  reference, in addition to current EventParticipation/history checks.

## Future Statistics Compatibility

The persistence design must preserve these source links without implementing
statistics:

- Every Audit Player result links to one persistent Player and one Audit.
- A Commander role links one Player to one Audit and inherits that atomic
  result's Unit type; persistent Unit Commander status is irrelevant.
- Every Audit links to an atomic Event unit, then to approved EventParticipation,
  Event, and persistent Unit.
- Every atomic result retains Regular, Rifles, Cavalry, or Artillery type.
- Every command group links to its Commander Player and unique descendant
  atomic Event units.
- Ranker observations include every Audit Player result, including mercenaries
  and never-rostered Players, and remain partitionable by Unit type.
- Commander observations derive from atomic Commander assignments and remain
  partitionable by Unit type.
- General eligibility remains at least two underlying atomic units regardless
  of type; nested groups flatten to unique Audits and partition combat values
  by Unit type rather than averaging child-group averages.

## Resolved RED Decisions

Human architecture approval has resolved:

1. Creating/registering the `audits` module and assigning it ownership of
   Event-scoped atomic units and command groups.
2. Creating cross-module contracts for Events approved participation and
   `canManageEvent`, Units `SUBMIT_AUDITS`, and Players resolve-or-create.
3. Defining that Unit-side `SUBMIT_AUDITS` applies to atomic-unit creation,
   Audit draft writes, finalization, or only some of those operations.

   Player but no alias/name is supplied, without inventing a canonical alias.
5. Approving public finalized-Audit reads and any visibility of creator,
   command-group, or draft metadata.
6. Approving deletion/protection behavior for Events, Units, atomic units,
   groups, drafts, and finalized Audits.
7. Approving database-enforced versus transactional enforcement for tree,
   role-cardinality, and finalization invariants where PostgreSQL constraints
   cannot express the rule directly.

route/component shape, exact names, terminal enum representation, and SQL
transaction decomposition. Ticket 20 is `READY` and must not enter `ACTIVE`

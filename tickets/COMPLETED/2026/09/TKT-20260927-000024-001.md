# Ticket: Statistics Architecture and Derived Performance Model

## Objective

Define the MVP Statistics architecture for public, read-derived Ranker,
Commander, General, persistent Unit, and attendance results over immutable
finalized Audit history. This ticket is architecture and planning only. It
creates no statistics queries, pages, leaderboards, caches, materialized views,
scheduled jobs, production schema, correction workflow, or premium analytics.

The approved owner is the new `statistics` module. Human RED approval is
recorded in the ADR and BCR created by this ticket.

## Main Success Scenario

1. A maintainer reviews one coherent Statistics architecture over the completed
   Audit source, Players membership history, Units hierarchy, and Event dates.
2. The architecture defines one effective-finalized-Audit source seam, one
   shared Event-date window policy, raw numerator/denominator aggregation, and
   explicit type/unit/attendance semantics.
3. The proposed Statistics module and minimum source contracts are registered
   without copying authoritative history or changing production persistence.
4. Human architectural approval can authorize bounded implementation tickets
   without reopening the core metric meanings.

## Approved Ownership

`statistics` owns only read-derived aggregation semantics, the shared trailing
14-day (default), trailing 30-day, and all-time window policy, derived metric
calculations, and public statistics query/read services. Audits owns the
semantic determination of the current effective finalized Audit for an atomic
Event unit and exposes it through `audits-statistics-effective-finalized-audit`;
Statistics consumes this seam and must not reproduce Audit lifecycle or future
supersession predicates. Events owns canonical Event occurrence time and its
normalization; Statistics applies its window policy to that Events-owned time.
Statistics owns no authoritative gameplay history, identity, membership,
hierarchy, Event date, participation, command group, or Audit persistence.

Audits remains authoritative for finalized battlefield results and command
structures. Players remains authoritative for Player identity and historical
UnitMembership. Units remains authoritative for persistent Unit identity and
hierarchy. Events remains authoritative for Event identity, canonical occurrence
time, and EventParticipation.

## Architectural Model

### Effective source

Audits semantically determines the current effective finalized Audit for an
atomic Event unit and exposes that decision through
`audits-statistics-effective-finalized-audit`. In MVP it returns the sole
finalized Audit for an atomic Event unit. Future superseded revisions remain
historical but are excluded from the effective result by Audits. Every
Statistics query consumes this seam rather than selecting or filtering Audit
revisions independently; Statistics must not reproduce Audit lifecycle or
future supersession predicates.

### Windows

Statistics owns the shared trailing 14-day (default), trailing 30-day, and
all-time window policy. Events owns canonical Event occurrence time and its
normalization; Statistics applies each window to that Events-owned time. Audit
creation, draft, finalization, correction, and supersession timestamps never
select a window.

### Ranker observations

Every Player result in every effective finalized Audit is one observation,
including mercenaries, Players rostered elsewhere, and never-rostered Players.
Audit appearance never creates or changes UnitMembership. Totals aggregate
kills, deaths, assists, KDR inputs, `(kills + assists) / deaths` inputs, and
Audit appearances; distinct Event participation counts one Event per Player,
even when multiple atomic Audits exist in that Event. Per-Audit averages divide
by Audit appearances. All combat outputs remain partitioned by Regular,
Rifles, Cavalry, and Artillery.

### Commander observations

Only the Player assigned the battlefield Commander role in an effective
finalized Audit creates an observation. Persistent Unit Commander status is
irrelevant. Each observation carries its Audit Unit type and represented Unit
context. Counts include battles commanded; totals include kills, deaths,
assists, tickets, flag captures, flag losses, and stars. Per-battle averages
include those measures and Player count. KDR is derived from pooled K/D
numerators and denominators, never summed or averaged from KDR values.

### General observations

A qualifying Event command group has a designated Commander Player and at least
TWO unique descendant atomic Event units. Nested groups flatten to unique
atomic units; exactly two qualifies. Each qualifying group is one observation.
Groups with fewer than two unique units do not qualify. Metadata may combine
counts of groups, distinct Events, total atomic units, and Regular/Rifles/
Cavalry/Artillery atomic-unit counts. Combat results are separate per Unit-type
population; mixed types are never silently blended and child-group averages are
never recursively averaged.

### Persistent Unit observations

Three explicitly named perspectives are required:

- **Direct Performance:** raw effective finalized Audit observations whose
  EventParticipation directly represents the selected persistent Unit only.
- **Organizational Performance:** raw observations for the selected Unit and
  every descendant Unit in its hierarchy, pooled before totals, ratios, or
  averages are calculated.
- **Average Unit Performance:** resolve qualifying Units directly in the
  selected subtree; derive each Unit's direct metric from raw observations,
  then give each qualifying Unit equal weight. Never average parent/child
  summaries or recursively average averages.

Historical Audit Unit-type partitions are retained in all applicable
perspectives.

### Ratios

The normal path aggregates raw numerators and denominators. KDR is total kills /
total deaths, and `(kills + assists) / deaths` uses the corresponding raw
population. If deaths are zero, the result preserves a zero-denominator state:
KDR presents the kill numerator as `K K`, and the combined ratio presents the
numerator as `K K+A`; it is not stored as an ordinary numeric ratio.

### Attendance

Attendance is scoped to Player + persistent Unit + Event. For each Unit/Event,
zero mandatory atomic units create no obligation; one or more create exactly one
obligation for every Player whose authoritative UnitMembership was active on
the canonical Event date. A Player joining afterward has no obligation; later
leaving does not remove it. Presence is satisfied by appearance in ANY effective
finalized Audit for a mandatory atomic unit of that same Unit/Event. A pending
obligation remains PENDING while any required mandatory atomic Audit is
unresolved/unfinalized, unless the Player is already PRESENT. Once all required
mandatory Audits are finalized, non-appearance is ABSENT. Mercenary appearances
count for Ranker/combat statistics but create no obligation and cannot satisfy
another Unit's obligation. Separate memberships create separate obligations.
Pending obligations are excluded from resolved attendance percentages.

### Visibility and storage

All MVP Ranker, Commander, General, Unit performance, and attendance summaries
are public and keyed to game Player/Unit identity, not Auth.js submitter
identity. Statistics owns no mutable authoritative or aggregate state. MVP uses
query-time indexed PostgreSQL aggregation, with no cache, materialized table,
scheduled recomputation, or incremental counters. Later optimization may cache
without changing metric semantics.

### Recommended access paths

These are architecture-level query access paths, not schema or migration
authorization. Implementations should validate them against real plans before
adding indexes:

- Audits-owned effective-finalized-Audit source operation by atomic Event unit,
  then joins its result to Events-owned canonical occurrence time; lifecycle
  and future supersession predicates remain inside Audits;
- Event occurrence time with Event identity for rolling-window filtering;
- finalized Audit represented persistent Unit plus Event time for direct and
  organizational Unit reads;
- Audit Player result Player identity plus Audit identity for Ranker reads and
  distinct-Event deduplication;
- Audit Unit type on result populations for Regular/Rifles/Cavalry/Artillery
  partitioning;
- Event command group Event/parent relationships for unique descendant
  flattening;
- UnitMembership Player/Unit periods with start/end boundaries for Event-date
  attendance eligibility;
- persistent Unit parent/root relationships for subtree resolution.

The Audits-owned effective-Audit operation and Events-owned canonical-time
contract remain the source seams; Statistics applies its shared window policy
to those source facts even if an implementation later changes physical indexes.

# Ticket: Effective Authorization and Capability Boundary

## Implementation Owner

Emil Estrada

## Objective

Implement the Units-owned, server-only authority-resolution layer that hides
ADR-20260915-002 persistence details from feature modules. The layer must
answer semantic Unit-scoped capability questions for the next parallel round,
while keeping feature workflows, UI, and downstream persistence out of scope.

This ticket is the authority boundary that Developer A and Developer B may
consume. Neither developer may reproduce PermissionGrant, scope, delegation,
RootUnit, Commander, or authority-level logic in a feature module.

## RED Reason

This work implements shared authority semantics, a module boundary, permission
evaluation, delegation invalidation, and server-side enforcement. It is
authorized by ADR-20260915-002 and depends on the completed persistence and
Commander contracts in TKT-20260920-000011-001 and TKT-20260920-000012-001.

## Current Authority-State Assessment

The current persistence model is sufficient for Unit-side effective
authorization without a Prisma change. It contains:

- a required `Unit.rootUnitId` and `RootUnit` designation;
- arbitrary-depth `Unit.parentId` hierarchy;
- required `Unit.commanderUserId` with final Commander/level-0 consistency;
- `AuthorizedUserMembership.authorityLevel` and unique User/Unit membership;
- the exact seven `Permission` values and three ordinary `PermissionScope`
  values;
- `PermissionGrant.delegatedFromGrantId` lineage;
- soft revocation metadata on grants; and
- server-side Auth.js User ID resolution through `getAuthenticatedUserId()`.

The evaluator and semantic capabilities do not yet exist. Commander status is
deliberately separate from operational grants. The current `Event` model has
no Unit, owner, or manager relationship, so `canManageEvent(userId, eventId)`
cannot be implemented honestly in this ticket without inventing Event
ownership semantics.

ADR-20260915-002 settles the authority rules used below. The remaining
architectural limitation is Event ownership/manager representation, not the
Unit authority persistence model.

## Proposed Semantic Capability Surface

The public application-level boundary is owned by the Units module and must
be server-only. Functions return `Promise<boolean>` for the initial boolean
questions; callers do not receive PermissionGrant records or evaluator
internals.

| Capability | Input | Output | Permission | Scope behavior | RootUnit behavior | Commander behavior | Consumer | This ticket |
|---|---|---|---|---|---|---|---|---|
| `canManageUnit(userId, unitId)` | Auth.js User ID and target Unit ID | `Promise<boolean>` | `MANAGE_UNIT` | Ordinary grant covers target according to its scope | Deny if grant and target are not in the same RootUnit | Commander alone is insufficient | Future Unit metadata workflow; no current feature workflow may implement it locally | Implement now as a resolver-backed seam |
| `canManageRoster(userId, unitId)` | Auth.js User ID and roster Unit ID | `Promise<boolean>` | `MANAGE_ROSTER` | Ordinary grant scope applies | Cross-RootUnit denied | Commander alone is insufficient | Developer A's roster workflow | Implement now |
| `canManageAuthorizedUsers(userId, unitId)` | Auth.js User ID and target Unit ID | `Promise<boolean>` | `MANAGE_AUTHORIZED_USERS` | Ordinary grant scope applies to the target Unit | Cross-RootUnit denied | Commander alone is insufficient; Commander level 0 matters only for administration comparison | Future authorized-user/delegation workflow, not this ticket's UI | Implement now as a capability check; action-specific comparison remains required |
| `canRequestEventParticipation(userId, unitId)` | Auth.js User ID and requesting Unit ID | `Promise<boolean>` | `REQUEST_EVENT_PARTICIPATION` | Ordinary grant scope applies to the requesting Unit | Cross-RootUnit denied | Commander alone is insufficient | Developer B's participation-request workflow | Implement now |
| `canManageEvent(userId, eventId)` | Auth.js User ID and Event ID | `Promise<boolean>` | `MANAGE_EVENTS` | Not definable until Event-to-Unit ownership/manager truth exists | No valid Unit boundary can be selected from current Event data | Commander behavior cannot be inferred | Future Event management/approval workflow | Define as deferred; do not implement or invent semantics |

`canManageAuthorizedUsers` means that the actor has applicable authority over
the target Unit. A workflow that creates, replaces, or removes an authorized
user must additionally compare the actor's applicable authority level and
structural position against the target operation. Equal non-Commander levels
cannot modify or remove one another. A boolean capability must not be treated
as a complete mutation policy for those actions.

The implementation may expose a richer internal decision object to avoid
repeating resolution work, but that object remains private unless a later
consumer-backed contract explicitly approves stable fields.

## Low-Level Resolver Design

Implement a private conceptual operation equivalent to:

```text
hasEffectiveUnitPermission(userId, unitId, permission)
```

The resolver must:

1. Accept a server-resolved Auth.js User ID; missing or empty identity denies.
2. Load the target Unit and complete parent ancestry, validating that every
   visited Unit has one consistent RootUnit.
3. Reject missing, malformed, cyclic, deleted, or cross-RootUnit targets.
4. Load the actor's memberships and grants for the requested permission.
5. Reject a grant whose membership is missing, whose grant is revoked, or
   whose delegation source chain is missing, revoked, cyclic, or otherwise
   invalid. Any invalid delegation lineage fails closed for that grant and its
   descendants; independent valid grants remain usable.
6. For ordinary permissions, require the grant membership Unit to be the
   target Unit or an ancestor, then calculate current hierarchy distance.
7. For `MANAGE_STRUCTURE`, treat the membership Unit as the structural anchor
   and require a strict descendant target. Structural source/destination
   territory checks belong to the operation-specific structural authorizer,
   which must use the same anchor rule.
8. Return allowed when at least one valid grant covers the target. Grants are
   additive; a narrower grant does not cancel a broader grant.
9. Deny by default when any required condition is absent.

The resolver must not copy inherited authority into descendant memberships or
use Commander status as a PermissionGrant bypass. Current ancestry is always
evaluated at decision time so moves change effective coverage without creating
new grants.

## Exact Resolution Rules

### Ordinary scopes

- `SELF`: the target Unit must equal the grant membership Unit, distance 0.
- `SELF_AND_CHILDREN`: the target may equal the grant membership Unit or be
  its immediate child, distance 0 or 1. A grandchild is denied.
- `SELF_AND_DESCENDANTS`: the target may equal the grant membership Unit or
  be any descendant at non-negative distance.
- Authority never propagates upward. A grant on a child does not cover its
  parent or an unrelated branch.

### `MANAGE_STRUCTURE`

`MANAGE_STRUCTURE` has null ordinary scope. Its membership Unit is the
structural anchor. The grant applies strictly below that anchor and cannot
authorize modifying, moving, deleting, or restructuring the anchor itself.
Creation must produce a strict descendant; a move must keep the source below
the anchor and place the destination parent at the anchor or below it; a
deletion target must be below the anchor. The complete operation territory
must remain within the same RootUnit.

### Revocation and delegation

- A revoked grant is never effective, regardless of its revocation timestamp
  or actor.
- A delegated grant is effective only while its complete source lineage is
  present, unrevoked, same-permission, RootUnit-valid, and within the source
  grant's effective authority.
- Revoking any source grant invalidates dependent delegated grants while
  preserving independent grants and the membership.
- Broken, cyclic, cross-root, self-referential, or otherwise invalid lineage
  fails closed.
- Delegation ceiling rules are validated by the authority-management writer;
  the resolver independently validates lineage and current source validity.

### RootUnit and Commander

- A grant and target in different RootUnit trees are denied even if their Unit
  IDs or ancestry data could otherwise appear to match.
- Commander status identifies the level-0 local authority identity but grants
  none of the seven operational permissions by itself.
- A Commander with no applicable operational grant is denied.
- An ordinary authorized User with a valid applicable grant is allowed even if
  they are not a Commander.
- RootUnit owner/Commander identity does not create a hidden global authority
  path; website-admin authority remains limited to ADR-20260915-003's bounded
  RootUnit operations.

## Authority-Level Rules

- Commander authority level is exactly `0`.
- Non-Commanders have authority level `>= 1`.
- Equal non-Commander levels are valid.
- A lower number is stronger local authority.
- Local authority level is relevant to authorized-user administration and
  delegation comparisons, not as a replacement for RootUnit, hierarchy, or
  grant-scope checks.
- The resolver must not invent global ranking, role inheritance, or a rule
  that makes a lower level automatically cover unrelated Units.
- For administration comparisons, first require applicable same-RootUnit,
  hierarchy, permission, and scope coverage; only then compare the relevant
  local authority levels and equal-authority restriction.

## Module and Contract Ownership Decision

Units owns the private resolver and the initial semantic capability functions,
as already assigned by ADR-20260915-002. A separate authorization module is
not justified for MVP. Auth.js/shared authentication owns identity resolution,
not Unit authority.

The initial implementation boundary is a Units server-side application
interface. Events remains the owner of Event identity and cannot consume an
invented Unit ownership relation. `canManageEvent` is therefore documented as
a deferred seam pending an approved Event ownership/manager decision.

No capability registry or `CONTRACTS.yaml` entry is required by this ticket:
the registries are discovery indexes, and no consumer-backed cross-module
contract currently exists. When Developer A or B actually imports the stable
boundary, the smallest consumer-backed contract must be created or updated
under the normal RED/BCR process and then registered. Feature modules must not
import Units' private Prisma queries or resolver internals in the meantime.

## Deliverables for Parallel Developers

capability for roster authorization. A must not inspect PermissionGrant,
PermissionScope, delegation, RootUnit, or authority-level persistence to make
that decision.

Developer B may depend on the server-only
`canRequestEventParticipation(userId, unitId)` capability for submitting a
participation request on behalf of a Unit. B must not implement local scope,
RootUnit, Commander, revocation, or delegation checks.

the server. Neither developer may depend on `canManageEvent` until Event

- Ordinary scopes are exact: `SELF` covers the membership Unit,
  `SELF_AND_CHILDREN` covers that Unit and immediate children only, and
  `SELF_AND_DESCENDANTS` covers descendants at any depth. Authority never

  revoked, cyclic, self-referential, cross-root, malformed, or otherwise
  inconsistent lineage fails closed while independent valid grants remain

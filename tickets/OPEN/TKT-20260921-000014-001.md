# Ticket: Players, Unit Memberships, and Roster Vertical Slice

## Implementation Owner

Developer A — Aiden Slabiak

## Objective

Deliver a usable MVP organization-side slice for persistent Napoleonic Wars
Players, Unit membership history, current rosters, protected roster mutations,
useful reads, and the minimum application UI needed to exercise the workflow.
Preserve Player identity and membership history independently of Auth.js website
Users and without adding authority semantics to Player records.

Tickets 15 and 16 are part of the local baseline. Build Player and membership
schema changes forward from the current Prisma schema and migrations.

## Approved Architecture Constraints

The RED design is approved by BCR-20260921-001. The Players module consumes
only the approved semantic contract
`docs/contracts/players-units-roster-authorization.md`. It must not inspect or
recreate Units authority internals.

## Main Success Scenario

1. A server-side workflow registers a persistent game Player.
2. An authenticated website User authorized by `canManageRoster(userId, unitId)`
   adds that Player to a valid Unit.
3. The active membership appears in the Unit's current roster.
4. The authorized User ends the membership.
5. The Player disappears from the current roster while the Player and ended
   membership remain queryable as history.

## Approved Data Design

- `Player` is a persistent Napoleonic Wars game identity with an internal
  database primary key, a unique externally supplied stable game `playerId`, a
  minimum product display/name field, and ordinary created/updated timestamps.
  It has no Auth.js User foreign key or authority fields.
- `UnitMembership` is an explicit Player-to-Unit record with membership start,
  nullable end, and inactive/history-preserving semantics.
- Current roster is derived from memberships whose end is null. No separate
  `Roster` persistence model is proposed because it would duplicate state.
- The schema must prevent duplicate active Player/Unit memberships with a
  PostgreSQL partial unique index on `(playerId, unitId)` where `endedAt IS
  NULL`, while permitting historical records.

## Approved Ownership and Boundary

The Players module owns Player persistence, UnitMembership persistence, current
roster derivation, Player/membership queries, and roster mutation workflows.
Units continues to own Unit identity, hierarchy, authority, and
`canManageRoster(userId, unitId)`. The approved consumer contract is
`docs/contracts/players-units-roster-authorization.md`; BCR-20260921-001 records
the boundary decision.

## Required Product Outcomes

### Player Workflow

- The application can register/create a persistent Player.
- Duplicate stable external Player identity is rejected safely.
- An existing Player can be located and reused later.

### Membership Workflow

- An existing Player can be added to a valid Unit as an active membership.
- An active membership can be ended without deleting the Player or history.
- A Player can later rejoin the same Unit, preserving prior ended records.
- A Player can belong to multiple Units where valid.

### Roster Workflow

- A Unit's current roster is derived from active UnitMembership records.
- Ended memberships are excluded from the current roster.
- Authorized Users can add and end memberships through the application.
- Unauthorized Users are denied server-side.

### Read-Side and UI

- Useful MVP access exists for current Unit rosters, Player identity/details,
  and Player membership history.
- The current roster is visible through the application.
- An authorized User can complete the roster management workflow through a
  minimum usable application interface, not only through server functions or
  tests.

## Required Server Guarantees

- Register/create a persistent Player after validating its stable game identity.
- Add an existing Player to a valid Unit transactionally.
- End an active membership transactionally without deleting Player or history.
- Resolve the authenticated website User server-side using existing auth
  patterns; never trust a client-provided authority User ID.
- Gate every protected roster mutation through
  `canManageRoster(userId, unitId)` and do not inspect authority persistence.
- Fail safely for missing Units, missing Players, missing memberships, and
  duplicate active memberships.

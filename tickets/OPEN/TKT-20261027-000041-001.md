# Ticket: Milestone 2 — Leaderboard Page and Statistics Presentation Expansion

- **Conceptual assignee:** Developer 1
- **Milestone:** 2

## Goal

Deliver a polished public Leaderboard experience that expands the working
Milestone 1 application. It must be a genuine feature, not just a renamed
Statistics screen. Select its information architecture only after investigating
the current Statistics readers and presentation.

## Main Success Scenario

1. A visitor opens the public Leaderboard and immediately understands the
   selected ranking, relevant data window, and how to interpret the results.
2. The visitor can move among useful supported categories or views, compare
   meaningful statistics, and navigate to public Player or Unit information.
3. The application derives displayed values from authoritative existing
   statistics semantics and preserves public identity boundaries.

## Context

The repository already has a public `/statistics` discovery surface and
query-time Statistics readers/presentations. The Statistics module currently
provides Ranker, Commander, General, Event Battle, Direct/Organizational/Average
Unit Performance, and Player+Unit attendance. Its shared windows are trailing
14-day (default), trailing 30-day, and all-time. Existing readers derive from
effective finalized Audits and canonical Event times, preserve raw
ratio-numerator/denominator semantics and zero-denominator states, and partition
applicable results by Unit type.

The existing Ranker result includes Player K/D/A totals, per-Audit-appearance
averages, K/D and (K+A)/D ratio states, Audit appearances, distinct Events, and
Unit-type partitions. Commander, General, and Unit readers expose additional
battle, command, organizational, and Unit result metrics. These are discovery
inputs, not a predetermined page specification. Reinspect the current branch
when implementation begins; repository truth wins.

## Module

- **Primary owner:** Statistics (`src/modules/statistics`).
- Preserve existing ownership and consume approved public readers/contracts.
- UI integration may use existing App Router and shared presentation patterns;
  do not rely on another module's private internals.

## Requirements

### Discovery and information architecture

Before implementation, inspect at least:

- existing Statistics readers, window policy, public DTOs, and relevant tests;
- the current `/statistics` page and Player, Unit, Event, and shared Statistics
  presentation patterns;
- current stable Player identity and public Player/Unit routing;
- relevant module manifests, contracts, and approved decisions.

Then record a concise recommendation covering:

- whether `/statistics` should become, contain, or coexist with a
  `/leaderboard` experience;
- which categories and metrics are supported by actual current read models;
- which audience/use case makes the selected information useful;
- windows, sorting, filters, and battle-type partitions to include or omit;
- any limitation that would otherwise make a displayed comparison misleading.

The recommendation is an implementation input, not authorization for a
boundary change.

### Candidate metrics to evaluate (not mandatory)

- **Player:** K/D/A, K/D or (K+A)/D, appearances, distinct Events, per-appearance
  averages, and Unit-type partitions.
- **Commander:** battles commanded, K/D/A, Tickets, Flag Captures/Losses,
  Stars, average player count, ratios, and Unit-type partitions.
- **Unit:** Direct, Organizational, or Average performance; Tickets, Flag
  Captures/Losses, Stars, K/D/A, ratios, and battle/Event counts where
  supported.
- **General/command group:** qualifying command observations, Events,
  subordinate atomic-unit counts, and type-specific combat/performance totals.

Choose a useful subset from repository truth. Do not imply that different
populations or time windows are directly comparable when they are not.

### Presentation and responsiveness

- Follow the established morale.gg visual language: restrained dark interface,
  compact information density, strong headings, fine separators, readable
  tables, limited decorative cards, and restrained accents.
- The initial view must communicate useful information without extensive
  interaction.
- Verify viewport widths of 390px, 768px, and 1440px. No page-level horizontal
  overflow; table-local scrolling is acceptable when needed. Keep filters,
  navigation, headings, labels, and key mobile metrics usable.

### Tests, docs, and PR

- Test reader/query behavior, sorting, supported windows/filters, empty results,
  zero-death/undefined ratios, Player identity fallback, public DTO boundaries,
  and rendering. Add practical responsive/presentation regression checks.
- Update requirements and demo/verification documentation as appropriate, and
  add a CHANGELOG entry.
- Work on an isolated feature branch; run focused verification; move the parent
  ticket to REVIEW; push and open a PR. Do not merge the PR yourself. A
  substantive peer review and requested-change/follow-up evidence are required
  before merge. Developer 2's substantive review is preferred if available;
  otherwise Emil reviews. Developer 2 may coordinate review timing around
  Ticket 42, but Ticket 42 remains independent and is not blocked by this
  review.

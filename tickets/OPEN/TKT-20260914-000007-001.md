# Ticket: Standardize Local PostgreSQL Development with Docker Compose

## Objective

Provide a repository-controlled PostgreSQL development environment that is reproducible for every developer using Docker Compose, without changing product-domain behavior or introducing a containerized Next.js app.

## Scope Owner

```yaml
scope_owner:
  type: repository
  id: local-development-environment
```

## Main Success Scenario

1. A developer installs Docker Desktop and clones the repository.
2. The developer copies `.env.example` to `.env` and sets local-only database values.
3. The developer runs `docker compose up -d`.
4. PostgreSQL starts in a repository-managed container with health checks and a named volume.
5. Prisma validation, generation, migration deployment, and seed all succeed against the Docker database.
6. The application connects successfully using the existing `DATABASE_URL` environment variable.
7. The developer can stop, restart, and reset the local database without touching product code.

## Scope Expansion and Rationale

The original write scope did not include `package.json`, but the repository required one necessary edit to make the existing Prisma workflow work reliably with the repo-managed Docker database:

- `db:*` scripts were updated from direct `prisma ...` calls to `dotenv -e .env -- prisma ...` so `DATABASE_URL` is loaded from the local development environment before Prisma reads it.
- `dotenv-cli` was added to `devDependencies` to provide the required environment-loading utility without changing application behavior.

This change was necessary because Prisma in this repo loads configuration from `prisma.config.ts` and requires `DATABASE_URL` to be present in the process environment. Without this, the existing developer workflow fails even when `.env` is present, which would block the Docker-backed local setup. The change is therefore appropriate and limited to the repository-controlled development infrastructure.

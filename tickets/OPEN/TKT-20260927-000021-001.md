# Ticket: Audit Foundation and Atomic Event Units

## Objective

Implement the approved Audits-module foundation required by the later Audit
submission and command-group tickets. Establish the cross-module contract
implementations, Player compatibility migration, atomic Event-unit persistence,
and a minimal management/read surface. Do not implement Audit paste/submission
or command groups.

## Main Success Scenario

1. An authorized User selects an approved EventParticipation.
2. The server resolves the approved Event and represented persistent Unit
   through the Events contract and checks `canSubmitAudit`.
3. The User creates and views multiple manually-created atomic Event units for
   that participation, each with explicit mandatory/optional status.
4. The server resolves or creates Player identities by stable game PlayerID
   without changing UnitMembership or aliases.
5. Unused atomic units can be safely deleted; protected history cannot cascade.

## Current Repository Truth

- Events owns Event/EventParticipation and `canManageEvent`.
- Units owns Unit identity and effective authority; `SUBMIT_AUDITS` exists but
  needs its approved Audits-facing capability implementation.
- Players owns Player and UnitMembership history; `Player.name` is currently
  required in Prisma but is approved to become nullable compatibility data.
- The new `audits` module and three contracts are registered and documented.
- Prisma has no atomic Event-unit model and no Audit result models yet.

## Required Implementation

### Player compatibility and contract seams

- Make `Player.name` nullable compatibility data through a forward migration.
  Preserve existing values; create no placeholders or canonical global names.
- Implement Events -> Audits approved-participation context and
  `canManageEvent` decision without exposing Event manager persistence or
  allowing participation mutation.
- Implement Units -> Audits server-only `canSubmitAudit(userId, unitId)` from
  effective `SUBMIT_AUDITS`, returning only a boolean.
- Implement Players -> Audits resolve-or-create by stable PlayerID. Reuse
  existing identity, create missing identity, and never create/modify
  UnitMembership or aliases.

### Atomic Event units

Create the exact model name as a GREEN choice. It must belong to exactly one
APPROVED EventParticipation, permit many units per participation, carry explicit
mandatory/optional metadata, retain the Event and persistent Unit relationship
through participation, and remain distinct from its future zero/one Audit.
Creation is manual and approval must not auto-create one. Enforce Event,
participation, and Unit integrity with foreign keys/domain validation.

Provide server workflows and minimal usable UI/read behavior to find an approved
participation, list/create atomic units, mark mandatory/optional, and delete an
unused unit. Deletion is allowed only with no finalized Audit, no command-group
dependency, and no protected historical dependency. Never cascade finalized
history.

## Acceptance Criteria

- [ ] Nullable Player.name migration preserves every existing value.
- [ ] Approved participation context rejects REQUESTED and DENIED records and
      cannot mutate EventParticipation.
- [ ] `canSubmitAudit` is server-only, fail-closed, and exposes no authority
      persistence.
- [ ] Player resolve existing/create missing is idempotent and creates no
      UnitMembership or alias side effect.
- [ ] Multiple atomic units can belong to one approved participation.
- [ ] Requested/denied participation cannot create an atomic unit.
- [ ] Approval does not automatically create an atomic unit.
- [ ] Mandatory/optional status persists explicitly.
- [ ] Atomic unit identity is separate from its future Audit and cannot cross
      EventParticipation or Event boundaries.
- [ ] Safe empty-unit deletion succeeds; protected deletion is rejected without
      cascading history.
- [ ] Minimal management/read surface is usable; Audit paste/submission and
      command groups are absent.
- [ ] Focused tests and existing EventParticipation, Event-management,
      Players/Roster, and Units authorization regressions pass.

## Explicitly Out of Scope

Audit parser, drafts/finalization, K/D/A, roles, Unit result statistics,
command groups, attendance calculations, and Ranker/Commander/General engines.
Do not change persistent Unit hierarchy or EventParticipation semantics.

# Ticket: Event Battle Structure Domain and Manager Editor

## Objective

Implement the approved Event Battle structure domain and Event-manager editor.
Add fixed side semantics, participation-backed claims, optional side image
references, the Events -> Audits mutation seam, side-safe hierarchy operations,
and history-preserving Event result storage. Do not broaden Audit submission or
implement an unapproved correction approver rule.

## Main Success Scenario

1. An Event owner or authorized Event manager opens the Event management Battle
   Structure editor.
2. The manager creates/configures groups and atomic units using only approved
   EventParticipations, fixed ATTACKER/DEFENDER sides, supported Audit types,
   mandatory state, names, and designated group commander fields.
3. The server enforces same-Event, approved-participation, same-side, strict
   tree, unique-descendant, cycle, and authority invariants.
4. A Unit Audit-authorized user discovers the exact claimed atomic unit in
   `/audits` without reselecting the Unit, while `canManageEvent` never grants
   Audit submission/finalization authority.
5. An eligible Event manager can record the initial Event result and the
   system retains immutable result history for a future correction workflow.

## Requirements

- Add relational representations equivalent to `BattlefieldSide` with exactly
  `ATTACKER` and `DEFENDER`; do not add configurable side names or coalitions.
- Add optional validated Event attacker/defender image references using the
  existing image-reference behavior; no upload or object storage.
- Add AtomicEventUnit name and side, preserving its required
  `eventParticipationId` as the sole represented Unit claim. Keep mandatory
  state and Audit Unit type in the approved ownership location.
- Replace or supersede EventCommandGroup's descriptive Unit field with an
  authoritative approved EventParticipation foreign key, add side, and keep
  group commander as a Player fact. Do not retain two authoritative Unit IDs.
- Implement `events-audits-event-battlefield-management` using
  `canManageEvent(userId, eventId)`. Keep `canSubmitAudit` independent.
- Permit Event managers to create/configure/place/move/remove atomic units and
  groups, but keep Audits responsible for invariant validation and persistence.
- Enforce same Event, approved participation, same-side parent/child, no
  cycles, one immediate parent, unique atomic contribution, unique flattened
  descendants, and existing General qualification semantics server-side.
- Provide drag/drop plus accessible `Move to...` fallback without authoritative
  client-only optimistic mutations.
- Add `/audits` discovery filtered to atomic units whose represented Unit is
  authorized for the current user through existing `canSubmitAudit`. Do not
  require Unit reselection or expose unrelated atomic units.
- Add immutable Event result/revision persistence with effective-result
  cardinality, `ATTACKER_WIN | DEFENDER_WIN | DRAW`, initial result eligibility
  after scheduled time, and manager authorization through `canManageEvent`.
- Preserve every prior effective result. A currently authorized Event manager
  may propose a different correction, but only another currently authorized
  Event manager may approve or reject it. Proposers cannot review their own
  proposals, including as owner; single-manager corrections remain pending.
- Define a safe legacy state for Events/structures without explicit sides;
  never infer sides from participating Units or ordering.
- Do not add historical Rank fields or pre-battle Commander semantics.

## Acceptance Criteria

- [x] Fixed sides and all schema/domain invariants are tested, including
      same-side root and reparent rejection.
- [x] Approved participation is required for group and atomic claims, and
      foreign/requested/denied/arbitrary Units are rejected.
- [x] Event managers can manage structure through `canManageEvent`; Unit
      Audit users cannot manage Event structure through `canSubmitAudit`.
- [x] `/audits` discovers only relevant atomic units through the represented
      participation Unit and existing Audit authority.
- [x] Initial Event result accepts only the three approved values and only
      after the Event is concluded by existing scheduled-time semantics.
- [x] Result history is immutable and has at most one effective result.
- [x] Correction proposals require a different currently authorized Event
  manager for approval/rejection; proposer self-review and owner bypass are
  rejected, and single-manager corrections remain pending.
- [x] Legacy Events remain valid and render an explicit unconfigured-side
      state until a manager assigns sides.
- [x] No production Statistics aggregation or public Battle DTO is added here.
- [x] Focused domain/authorization/migration tests, Prisma validation and
      generation, lint, type-check, build, and `git diff --check` pass.

# Ticket: Event Management and Participation Approval Vertical Slice

## Implementation Owner

Developer B — Chandler Lovely (GitHub: ChanMan64)

## Objective

Deliver a usable MVP Event-management vertical slice on top of Tickets 15 and
16. An authorized Event manager must be able to operate an Event through the
application: manage ordinary Event information, administer Event managers when
owner-authorized, review Unit participation requests, approve or deny pending
requests, and observe the resulting participation state. Protected operations
must remain unavailable to unauthorized Users, while existing public Event
browsing remains functional.

This is an application workflow, not only a collection of server functions.
Build forward from the current local Prisma schema and migrations. Do not
implement the feature before this ticket is assigned for implementation.

## Main Success Scenario

1. An Event exists with an owner and, optionally, explicit Event managers.
2. The owner or an explicit manager opens an Event-management workflow and can
   perform ordinary allowed Event management.
3. The owner can add or revoke explicit Event managers; explicit managers cannot
   administer other managers.
4. A Unit submits a participation request through the existing Ticket 15 path.
5. An Event manager sees the pending request and approves or denies it.
6. The resulting participation state is visible through the appropriate
   management/read-side surfaces, without exposing pending or denied management
   information through public browsing.
7. Unauthorized Users are denied every protected operation server-side.

## Required Product Outcomes

### Event Management

- An Event owner or explicit Event manager can perform ordinary MVP Event
  management through the existing `canManageEvent(userId, eventId)` boundary.
- Existing Event editing behavior is usable through the application and
  current Event timing/lifecycle rules are preserved.
- If Event creation already has UI, integrate it without disrupting it. If it
  exists only server-side and minimal UI work is required for a usable Events
  workflow, that work is GREEN within Events.
- Do not redesign unrelated public Event browsing.

### Event Authorized-User Administration

- The owner can add an existing website User as an explicit Event manager.
- The owner can revoke an explicit Event manager.
- Duplicate Event/User authorization is rejected safely.
- The owner cannot receive a duplicate explicit manager row.
- An explicit manager cannot add or revoke other managers.
- Ownership transfer is not supported.
- Manager self-removal is optional only if Ticket 16 already supports it or it
  follows naturally without broadening manager-administration authority.

### Participation Review and Decision

- Event managers can inspect EventParticipation records for Events they can
  manage, with `REQUESTED` records visible and actionable.
- The owner or explicit Event manager can approve a `REQUESTED` participation.
- The owner or explicit Event manager can deny a `REQUESTED` participation.
- Authorization for both decisions uses `canManageEvent(userId, eventId)`.
- Valid lifecycle transitions remain only:
  `REQUESTED -> APPROVED` and `REQUESTED -> DENIED`.
- Invalid or terminal transitions fail safely. Do not add approval reversal,
  denial reversal, re-request/reset behavior, or duplicate EventParticipation
  rows without a later RED decision.

### Read-Side and UI

Provide the minimum usable interface, using existing application conventions,
so an authorized manager can:

- identify Events they can manage;
- open and manage an Event;
- inspect relevant Event information and explicit Event managers;
- review pending participation requests;
- approve or deny pending requests; and
- observe the resulting participation state.

The owner must additionally be able to add and revoke Event managers through
the UI. Exact routes, components, layouts, forms, and interaction design are
Developer B's GREEN responsibility.

### Public and Privacy Behavior

- Preserve existing public Event browsing and approved participation behavior
  where consistent with the existing Event read-side.
- Do not expose pending or denied management information publicly merely because
  the management interface needs it.
- Make reasonable MVP presentation decisions within Events; escalate only when
  a genuine product or privacy boundary must change.

## Approved Architecture Boundaries

### Existing Event Management

Every protected ordinary Event-management operation must use the existing
server-only semantic capability:

```ts
canManageEvent(userId, eventId)
```

Do not reconstruct Event authorization downstream or inspect Unit permissions,
`PermissionGrant`, `PermissionScope`, `RootUnit`, `Commander`,
`authorityLevel`, delegation lineage, or participating-Unit authority.

### Event Manager Administration

Use the Ticket 16 approved owner-only Event-manager administration boundary.
`canManageEvent` is not permission to administer the manager list. The owner
may add and revoke explicit managers; explicit managers may not administer
other managers.

### Participation Requests

Unit-side request creation remains owned by Ticket 15 and continues to use:

```ts
canRequestEventParticipation(userId, unitId)
```

Do not modify that authorization model. Developer B owns Event-side request
review and decision behavior and must use `canManageEvent` for approval/denial.
Participation grants no Event authority.

### Persistence Baseline

Before changing persistence, inspect the actual current Prisma schema and
migrations. Preserve `EventParticipation`, Event ownership, and
`EventAuthorizedUser`, as well as Units authority and Auth.js data. Build
forward only if a genuine in-scope persistence adjustment is required; do not
create redundant authority or participation state, reset the database, or
rebuild migrations for convenience.

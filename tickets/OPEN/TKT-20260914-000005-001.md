# Ticket: Establish Events Module and Public Event Browsing

## Implementation Owner

Developer B — Chandler Lovely (GitHub: ChanMan64)

## Objective

Establish the initial Events product module, introduce the minimal Event
persistence required by the MVP, and implement public read-only Event
browsing.

This ticket establishes the Event concept before EventParticipation,
authorization, and Audits are introduced.

## New-Module Exception

This is the first Events ticket. It explicitly authorizes creation of the
new `events` module, so the absence of `src/modules/events/MODULE.md` is not
a blocking condition under `AGENT_WORKFLOW.md` Section 5. Developer B must:

1. Read `docs/templates/MODULE_TEMPLATE.md`.
2. Define the module's purpose, ownership, non-ownership, and public boundary.
3. Create `src/modules/events/MODULE.md` from the canonical template.
4. Register the Events module in `docs/registry/MODULES.yaml`.
5. Create only contracts justified by an actual cross-module consumer.

## Scope Owner

```yaml
scope_owner:
  type: module
```

Rationale: this ticket establishes the Events module, its minimal approved
Event persistence, and its public read-side presentation. The new-module
exception applies because an Events `MODULE.md` does not yet exist.

## Human-Approved Event Persistence Scope

Human architectural authority explicitly approves the following minimal
Event representation for this ticket:

- stable primary key;
- name;
- scheduled date/time;
- event type represented simply for the MVP;
- optional description;
- optional opponent information;
- optional map information;
- created timestamp;
- updated timestamp.

This approval is a shared/RED schema artifact and must be recorded and
implemented exactly within this boundary. It does **not** authorize:

- Unit relationships;
- EventParticipation;
- event ownership;
- event-manager relationships;
- permission relationships;
- Audits;
- generalized event types;
- multi-game abstractions;
- any additional persistent relationship or model.

Any additional persistent structure must be escalated before implementation.

## Main Success Scenario

1. The approved minimal Event representation exists in PostgreSQL.
2. Its migration applies successfully.
3. Controlled server-side verification can create and read an Event.
4. An unauthenticated visitor opens the Events area.
5. Existing Events are displayed.
6. The visitor selects an Event.
7. The Event detail view shows its basic information.
8. No authentication is required for public browsing.
9. Temporary verification Event data can be removed.

## Module Responsibilities

The Events module owns, for this ticket:

- Event identity;
- Event name;
- scheduled date/time;
- basic Event metadata;
- Event read/query behavior;
- public Event presentation.

It explicitly does **not** own yet:

- Unit participation requests;
- EventParticipation;
- participation approval;
- Unit authority;
- Event-manager permissions;
- Audit lifecycle;
- audit statistics;
- leaderboards;
- event-management UI;
- general Event create/edit/delete controls for application users.

## Required Work

Developer B should:

- create `src/modules/events/MODULE.md` from the canonical template;
- register the Events module in `docs/registry/MODULES.yaml`;
- introduce only the approved minimal Event Prisma representation;
- create the corresponding migration;
- preserve server-only Prisma access through an appropriate server-side module
  boundary;
- implement a public Events list;
- implement Event detail;
- display the name, date/time, event type, description when present, opponent
  when present, and map when present;
- provide useful empty and error states;
- use `/events` and `/events/[eventId]` when consistent with repository
  conventions.

The normal Event creation rule is that a domain-level Event creation path may
not create an Event scheduled in the past, provided this validator can be
added without establishing authorization or unrelated architecture.

Controlled server-side Event creation is permitted only for persistence
verification. It must not become public product behavior.

## Write Behavior

This ticket does not expose general Event create, edit, or delete controls to
application users. The MVP will later allow appropriately authorized Unit
managers to manage Events, but that permission model is being designed
separately.

Do not introduce a temporary rule that allows any authenticated user to create
Events. That would establish incorrect authorization behavior.

### Deviations and Known Limitations

- Event type persists as a plain string; presentation styles the well-known
  values (internal/external/mixed/grand battle) and neutrally renders
  anything else.
- Times render in the visitor's local time zone on the client; the server
  render (and no-JS view) shows UTC.
- Dedicated map banners exist for Austerlitz, Barraux, and Borodino; other
  maps get one of two generic in-game fallback banners. Extending is one
  image + one lookup entry.
- The calendar grid renders on the client (so days follow the visitor's
  time zone); before hydration it shows a skeleton.
- The detail page's statistics and participation sections are static
  placeholders labeled as future functionality; no models or behavior.
- A temporary untracked verification script and local demo Event rows were
  used during verification and review; both were removed before the
  implementation commit.

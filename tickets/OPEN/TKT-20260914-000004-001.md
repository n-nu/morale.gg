# Ticket: Establish Units Module and Public Unit Hierarchy

## Implementation Owner

Developer A <- replace your name here

## Objective

Establish the first product-domain module for morale.gg using the existing persisted `Unit` representation.

This ticket creates the Units module and implements public, read-only browsing of the organizational hierarchy. The purpose is to establish a stable Unit identity/hierarchy capability that later Player, Membership, EventParticipation, permissions, and Audit work can build against.

This ticket does NOT authorize changes to the Unit schema, unit ownership, permissions, invites, creation, Player identity, memberships, rosters, Events, EventParticipation, Audits, or statistics.

## New-Module Exception

This ticket explicitly authorizes creation of the first `units` module. `MODULE.md` does not yet exist for this module, so per `AGENT_WORKFLOW.md` Section 5 (New-Module Exception), its absence is not a blocking condition. Developer A must:

1. Read `docs/templates/MODULE_TEMPLATE.md`.
2. Read `docs/SYSTEM.md`, `BACKLOG.md` (US-03, US-05), and `docs/architecture.md`.
3. Define the module's initial purpose, ownership, non-ownership, and public boundary (see Module Responsibilities below).
4. Create `src/modules/units/MODULE.md`.
5. Register the module in `docs/registry/MODULES.yaml`.
6. Create only contracts justified by an actual cross-module consumer (none currently exists — see Contracts section below).

## Main Success Scenario

1. An unauthenticated visitor opens the Units area.
2. Existing Units are displayed.
3. The seeded root Unit is visible.
4. The visitor opens a Unit.
5. The Unit detail view displays the Unit and its hierarchy context.
6. Direct child Units are visible.
7. The parent Unit is visible when one exists.
8. The visitor can navigate between parent and child Units.
9. Repeated navigation supports hierarchy deeper than one level.
10. No authentication is required for any step above.

## Module Responsibilities

The new `units` module owns, for this ticket:

- Unit identity;
- Unit name;

- hierarchy queries/traversal;
- public read-side Unit presentation.

The module explicitly does NOT own yet:

- Unit ownership;
- delegated permissions;

- child-unit invites;

- EventParticipation;

`MODULE.md` must document these boundaries clearly under Ownership / Non-Ownership.

## Required Work

Developer A should:

- create `src/modules/units/MODULE.md` from `docs/templates/MODULE_TEMPLATE.md`;
- register the Units module in `docs/registry/MODULES.yaml`;
- establish the Units source structure under `src/modules/units/` (e.g. a server-side data-access boundary plus any supporting types/queries) consistent with the existing `src/modules/<name>/server` convention already present in the repository;
- access Unit persistence (`prisma.unit`) only through an approved server-side application boundary inside the module (do not import `src/lib/prisma.ts` directly from route/page components — route through the module's server boundary), consistent with the pattern in `src/lib/prisma.ts` (`server-only`);
- implement a public Units list;
- implement a public Unit detail view;
- display/allow navigation to the parent relationship when present;
- display/allow navigation to child relationships;
- support arbitrary-depth hierarchy through repeated navigation or an appropriate recursive presentation (repeated single-level navigation is acceptable; a full recursive tree view is not required);
- implement useful empty/error states (e.g. no children, unit not found);
- maintain reasonable public mobile readability, consistent with `BACKLOG.md`'s statement that public read-only viewing should work on mobile.

Suggested public routes, if compatible with existing conventions:

- `/units`
- `/units/[unitId]`

An empty route directory already exists at `src/app/units/[unitId]/`; do not force these exact paths if implementation reveals existing repository conventions require something different, but prefer them absent a concrete reason to deviate.

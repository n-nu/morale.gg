# Ticket: Design Unit Ownership, Delegated Permissions, and Child-Unit Invite Architecture

## Implementation Owner

Emil Estrada

## Objective

Produce an implementation-ready MVP architecture for:

1. exactly-one Unit ownership;
2. delegated Unit-management permissions;
3. parent-authorized child-Unit creation using temporary invites;
4. the server-side authority checks later required by Units, Events,
   rosters, and Audits.

This ticket is DESIGN ONLY. Its purpose is to resolve RED architecture
decisions before the next implementation round. It must not implement the
design or treat a recommendation as an accepted decision.

## Established Requirements

The design must treat the following as established product requirements,
not as open questions.

### Identity

- Auth.js `User` represents website identity.
- User and Player are separate concepts.
- Ownership and management authority belongs to User, not Player.
- Authentication alone grants no management authority.

### Unit Ownership

- Every Unit has exactly one owner.
- The owner may grant supported management permissions to additional
  authenticated Users.
- A User may potentially manage more than one Unit.

### Unit Hierarchy

- Unit hierarchy has arbitrary depth.
- Root Units are manually seeded.
- Normal non-root Unit creation requires an invite from the intended parent
  Unit.

### Child Creation

- A parent Unit issues a temporary invite.
- An authenticated User redeems the invite.
- Redemption establishes the parent-child relationship.
- The redeeming User becomes the new child Unit's initial owner.

### Parent Authority

- A child Unit owner can be removed or changed by the parent Unit owner.
- Any ambiguity about how far parent authority propagates must be surfaced
  for human decision rather than invented.

### Public Access

- Public read-only Unit information requires no authentication.
- All protected write authority is enforced server-side.

## Required Design Questions

### A. Ownership Representation

Determine the smallest clean relational representation for exactly one User
owning one Unit. Evaluate options such as:

- `ownerUserId` directly on Unit;
- a dedicated Unit management or authority relation;
- another minimal approach.

Address:

- cardinality and exactly-one enforcement;
- uniqueness and whether a User may own multiple Units;
- ownership transfer and transaction boundaries;
- foreign-key behavior and deletion policy;
- bootstrap ownership for manually seeded roots;
- compatibility with the existing minimal Unit representation.

Do not pre-decide the answer in this ticket. Recommend one option and retain
credible alternatives with their tradeoffs.

### B. Delegated Manager Representation

Design the minimum manager/permission system and avoid generalized enterprise
RBAC. Evaluate an MVP permission set approximately covering:

- manage Unit;
- manage roster;
- manage Events;
- submit Audits.

Determine:

- how the owner receives implicit authority;
- how additional managers are added;
- how permissions are granted and revoked;
- how duplicate assignments are prevented;
- how one User manages multiple Units;
- whether child-invite creation remains owner-only.

The current product direction favors owner-only invite creation unless a
specific requirement justifies delegation. Treat that as a direction to
assess, not as an accepted architectural decision.

### C. Parent Authority

Resolve or present options for:

- direct-parent owner authority only versus inherited authority through all
  ancestors;
- whether a parent owner may replace only the child owner or also manage the
  child's delegated managers;
- behavior after ownership transfer;
- behavior when a parent relationship or owner is changed;
- safeguards against authority escalation through deep hierarchies.

Recommend the smallest MVP behavior, or present the specific alternatives
that require human choice where the requirements do not determine an answer.

### D. Invite Representation

Design a temporary `UnitInvite` concept addressing:

- parent Unit;
- issuing User;
- secure token or code;
- expiration;
- one-time use;
- revocation;
- redemption;
- redeeming User;
- resulting child Unit;
- safe token storage.

The conceptual flow is:

```text
Parent Unit
    |
    v
temporary invite
    |
    v
authenticated User redeems
    |
    v
Child Unit created
    |
    +--> parent link established
    |
    +--> redeeming User becomes owner
```

Define lifecycle states, replay behavior, expiration behavior, concurrent
redemption behavior, and transaction/atomicity expectations conceptually.

### E. Authorization Semantics

Define how future server-side product code should conceptually answer:

- can User manage Unit?
- can User manage roster?
- can User manage Events for this Unit?
- can User submit Audits for this Unit?
- can User generate a child invite?
- can parent owner replace child owner?

Specify the relevant subject, target Unit, permission, hierarchy context,
ownership state, and failure behavior. Do not use frontend visibility as
authoritative security. Authorization must remain in the approved Next.js
server-side boundary.

### F. Module Ownership

Consider the Units module being established concurrently. Recommend:

- which authority behavior belongs to Units;
- whether a separate authorization module is actually justified;
- what authentication infrastructure remains shared;
- what semantic capability Events and Audits may eventually need.

Prefer the smallest module structure appropriate for the MVP. Do not create
speculative contracts. If a real future cross-module capability is needed,
identify its consumer, producer, minimum semantics, and the point at which it
should be formalized.

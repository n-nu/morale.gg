# Ticket: Event Command Group Management

## Objective

Implement Event-scoped historical command groups over Ticket A's atomic Event
units. Event managers administer a strict tree of groups and atomic units;
public readers can inspect the resulting command structure. Do not mutate the
persistent Unit hierarchy, roster memberships, atomic units, or finalized
Audits. Do not calculate General statistics.

- Parent architecture: `TKT-20260927-000020-001` (COMPLETED).
- Hard dependency: Ticket A, `TKT-20260927-000021-001`, must be locally

- Ticket B, `TKT-20260927-000022-001`, is not required for group persistence or
  UI. If B is merged, run its finalized-Audit regressions; do not create hidden

- Approved governance: `ADR-20260927-006` (Accepted), `BCR-20260927-004`

  `players-audits-player-resolution`; only the Events contract authorizes group
  administration.

## Main Success Scenario

1. An Event manager opens an Event's command-structure view.
2. The server authorizes the operation through Events-owned `canManageEvent`.
3. The manager creates groups, assigns represented Units and Commander Players,
   and attaches atomic units or child groups.
4. The server rejects cycles, overlaps, duplicate parents, and cross-Event
   edges, while allowing safe reparenting.
5. Group edits/deletion leave atomic units, finalized Audits, persistent Units,
   and rosters unchanged. Public readers can view the tree.

## Approved References and Current Truth

Audits owns Event command groups. Events owns Event identity, approved
participation, and `canManageEvent`; `SUBMIT_AUDITS` and represented Unit
ownership do not authorize group administration. Groups are manually
reconstructed Event metadata. Each group has an Event, descriptive persistent
Unit, Commander Player, optional parent, and child atomic units/groups.

## Required Implementation

### Authority and model

Use Events `canManageEvent` through the approved contract for every protected
command-group mutation. Do not use `SUBMIT_AUDITS`, persistent Unit authority,
represented Unit ownership, or persistent Unit Commander status. Persist Event,
descriptive represented Unit, Commander Player, optional parent group, and
membership to child atomic units and/or groups using a GREEN exact shape.

### Strict tree

Enforce at most one immediate parent for each child group and atomic unit; no
cycles or self-parenting; no cross-Event group or atomic-unit edges; no
overlapping ancestry that double-counts an atomic unit; and no duplicate atomic
contribution. Groups may contain atomic units, child groups, or both. Safe
reparenting is allowed when the resulting graph remains a strict tree.

### Lifecycle and reads

Managers may create, edit, restructure, detach, and delete groups. Group
operations never mutate/delete atomic units, finalized Audits, persistent Unit
hierarchy, or UnitMembership. Event command structure is public. Preserve
unique descendant atomic-unit traversal for future General observations.

### General compatibility

Do not calculate statistics. Preserve designated group Commander as future
General-stat Player; eligibility at two or more unique underlying atomic units,
including mixed Unit types; nested flattening to unique atomic units/Audits; and
partitionable Regular, Rifles, Cavalry, and Artillery result populations. Never
average child-group averages.

## Acceptance Criteria

- [ ] Event owner/authorized manager may create and manage groups; unauthorized
      users and represented-Unit-only users are rejected.
- [ ] Group Commander is a persistent Player identity.
- [ ] Groups and atomic units cannot cross Event boundaries.
- [ ] Child groups and atomic units have at most one immediate parent.
- [ ] Cycles, self-parenting, duplicate-parent, overlap, and duplicate atomic
      contribution attempts are rejected transactionally.
- [ ] Safe reparenting preserves the strict tree.
- [ ] Group deletion preserves atomic units and finalized Audits.
- [ ] Persistent Unit hierarchy and roster membership remain unchanged.
- [ ] Command structure is publicly readable.
- [ ] Unique descendant atomic-unit traversal preserves future General
      eligibility and Unit-type partitioning without statistics calculation.
- [ ] Ticket A regressions and applicable Event-management regressions pass;
      Ticket B Audit regressions run when B is already merged.
